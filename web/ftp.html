Gumdrop FTP Server

← Back to Main Page

Gumdrop provides a complete FTP server implementation following RFC 959 and its security extensions (RFC 4217 for FTP-TLS). Like all Gumdrop protocol implementations, the FTP server uses the event-driven, non-blocking architecture that enables high concurrency with minimal resource consumption.

Protocol Support

The FTP server implements the File Transfer Protocol as defined in RFC 959, with modern extensions for security and IPv6.

Supported Commands

All standard FTP commands are implemented:

  • Access Control: USER, PASS, ACCT, CWD, CDUP, SMNT, QUIT, REIN
  • Transfer Parameters: PORT, PASV, TYPE, STRU, MODE
  • Service Commands: RETR, STOR, STOU, APPE, ALLO, REST, RNFR, RNTO, ABOR, DELE, RMD, MKD, PWD, LIST, NLST, SITE, SYST, STAT, HELP, NOOP

Extended Commands

  • EPRT/EPSV – extended port commands for IPv6 (RFC 2428)
  • FEAT – feature negotiation (RFC 2389)
  • SIZE – file size query (RFC 3659 section 4)
  • MDTM – file modification time as YYYYMMDDhhmmss UTC (RFC 3659 section 3)
  • MLST/MLSD – machine-readable directory listings with standardised facts (size, modify, type, perm) per RFC 3659 section 7. MLST sends a single entry over the control connection; MLSD sends the full directory over the data connection.
  • AUTH, PBSZ, PROT, CCC – TLS negotiation and data protection (RFC 4217), described below
  • OPTS UTF8 ON – switches the control connection to UTF-8 encoding for non-ASCII pathnames (RFC 2640)
  • STAT with directory path – directory listing over the control connection without a data connection (RFC 959 section 4.1.3)

Data Connection Modes

Both active and passive modes are supported:

  • Active (PORT/EPRT) - server connects to client-specified address
  • Passive (PASV/EPSV) - client connects to server-specified address; preferred for firewalled clients

Security Extensions

The server implements RFC 4217 (Securing FTP with TLS):

AUTH TLS

Upgrades the control connection to TLS. After successful AUTH TLS, credentials and commands are encrypted: 

C: AUTH TLS
S: 234 AUTH TLS successful
[TLS negotiation]
C: USER alice
...

Implicit FTPS

When the listener is configured with secure(true), the server expects TLS from connection establishment. The listening port automatically defaults to 990 (per RFC 4217) unless an explicit port is set.

Data Connection Protection

  • PBSZ 0 – protection buffer size (required before PROT)
  • PROT P – enable protected (encrypted) data connections
  • PROT C – clear (unencrypted) data connections

Use requireTLSForData(true) to mandate encrypted data transfers. It can be set on the listener or on the composer.

Data Connection Security (RFC 4217 section 10)

The server verifies that each data connection uses the same client IP as the control connection. In passive mode, incoming data connections from a mismatched address are rejected. In active mode (PORT/EPRT), the server refuses to connect to a client-supplied address that does not match the control client, blocking FTP bounce and port-scanning abuse.

To restore legacy active-mode behaviour (server connects to any address given in PORT/EPRT), call allowActiveModeBounce(true) on the listener. This should be used only in explicitly trusted deployments.

Authentication

Authentication uses Gumdrop's centralised Realm interface. The FTP server supports traditional USER/PASS authentication: 

C: USER alice
S: 331 User name okay, need password
C: PASS secret123
S: 230 User logged in

Pass the realm to the composer with realm(...). See Using a realm for how to build one, and Role-based access control for how groups become the roles described below.

Handlers and File Systems

A server is assembled with FtpServer.compose(), which takes listeners and a session provider: a factory that returns a fresh handler for each connection. FtpServerSessionProviders offers three ready-made providers:

  • fileSystem() - serves a directory (rootDirectory), optionally readOnly, authenticating against a realm, with an optional quotaManager and welcomeMessage
  • anonymous() - read-only anonymous access to a rootDirectory
  • roleBased() - as fileSystem() but enforcing the FTP roles described below

Custom handlers

To add policy or serve something other than a local directory, supply your own provider. The protocol is staged, as in the SMTP server: each stage gives you an interface offering only what is legal at that point, and a state object to accept or reject.

  • ClientConnected - connected(ConnectedState, Endpoint) accepts the connection with a greeting, or rejects it
  • NotAuthenticatedHandler - user(LoginState, username) asks for a password or an account, or logs in; tlsEstablished is called after AUTH TLS
  • PasswordHandler and AccountHandler - receive PASS and ACCT, and log the user in or refuse
  • AuthenticatedHandler - the logged-in session. It supplies the FtpFileSystem (getFileSystem()) and has hooks you override: isAuthorized(operation, path) to allow or refuse a command, transferStarting, transferProgress and transferCompleted to observe transfers, handleSiteCommand for SITE, and the quota methods

DefaultFtpHandler implements the whole login pipeline (with an optional Realm), so a handler usually extends it and overrides the hooks it wants. For example, to refuse uploads of Windows executables: 

public class NoExecutablesHandler extends DefaultFtpHandler {

    public NoExecutablesHandler(FtpFileSystem fileSystem, Realm realm) {
        super(fileSystem, realm);
    }

    @Override
    public boolean isAuthorized(FtpOperation operation, String path) {
        if (operation == FtpOperation.WRITE && path != null
                && path.toLowerCase().endsWith(".exe")) {
            return false;
        }
        return true;
    }
}

FtpServerSessionProvider provider = new FtpServerSessionProvider() {
    @Override
    public ClientConnected openSession(TcpListener listener) {
        return new NoExecutablesHandler(
                new BasicFTPFileSystem("/srv/ftp"), realm);
    }
};

BasicFTPFileSystem is the local-directory FtpFileSystem; implement the interface to serve files from elsewhere.

Role-Based Access Control

The roleBased() provider enforces fine-grained access control based on user roles defined in the realm, through RoleBasedFTPHandler.

FTP Roles

  • ftp-read - read files and list directories
  • ftp-write - create and modify files (implies ftp-read)
  • ftp-delete - delete files and directories (implies ftp-write)
  • ftp-admin - full access including SITE commands

Operation Mapping

CommandsRequired Role
RETR, LIST, NLST, STATftp-read
STOR, STOU, APPE, MKDftp-write
DELE, RMDftp-delete
RNFR, RNTOftp-write (source) + ftp-delete (if replacing)
SITE commandsftp-admin

Configuration Example

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");

FtpServer server = FtpServer.compose()
        .listener(new FtpListener().port(21).bindWildcard()
                .secure(true).tls(tls))
        .realm(ftpRealm)
        .sessionProvider(FtpServerSessionProviders.roleBased()
                .realm(ftpRealm)
                .rootDirectory(Path.of("/srv/ftp")))
        .server();

Filesystem-Level Enforcement

When filesystemEnforcement(true) is set on RoleBasedFtpSessionProvider, each session's file system is wrapped in RoleAwareFTPFileSystem. This enforces read/write/delete roles at the filesystem operation level as a defence-in-depth layer, complementing the command-level checks in RoleBasedFTPHandler.

Configuration

FtpServer.compose() settings

  • listener(FtpListener) - add a listener; at least one is required
  • sessionProvider(FtpServerSessionProvider) - the handler factory
  • realm(Realm) - realm for authentication
  • requireTLSForData(boolean) - mandate TLS for data connections

FtpListener settings

  • port(int) - listening port (default: 21, or 990 when secure)
  • bindWildcard() and addresses(InetAddress...) - where to bind
  • secure(boolean) - implicit TLS (FTPS)
  • tls(TlsConfig) - certificate and key; also enables AUTH TLS
  • requireTLSForData(boolean) - mandate TLS for data connections
  • allowActiveModeBounce(boolean) - permit PORT/EPRT data addresses other than the control client IP (default: false; enables legacy FTP bounce when true)
  • pasvMinPort(int) and pasvMaxPort(int) - port range for passive data connections (default: 0, any free port); open this range in your firewall
  • maxConnections(int) and maxConnectionsPerIP(int) - connection caps
  • rateLimit(String), maxAuthFailures(int), authLockoutTimeMs(long) - abuse protection
  • allowedNetworks and blockedNetworks - CIDR allow and block lists
  • idleTimeoutMs, readTimeoutMs, connectionTimeoutMs - timeouts

Session provider settings

RoleBasedFtpSessionProvider (from FtpServerSessionProviders.roleBased()):

  • realm(Realm) - realm for authentication and RBAC
  • rootDirectory(Path) - filesystem root for FTP access
  • fileSystem(FtpFileSystem) - serve a custom file system instead
  • readOnly(boolean) - refuse every write
  • welcomeMessage(String) - greeting banner text
  • quotaManager(QuotaManager) - quota manager
  • filesystemEnforcement(boolean) - wrap filesystem in RoleAwareFTPFileSystem (default: false)

Example Configuration

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");

// FTP with explicit TLS (port 21 + AUTH TLS)
FtpListener explicitTls = new FtpListener().port(21).bindWildcard().tls(tls);
explicitTls.pasvMinPort(50000);
explicitTls.pasvMaxPort(50100);
explicitTls.requireTLSForData(true);

FtpServer server = FtpServer.compose()
        .listener(explicitTls)
        .realm(ftpRealm)
        .sessionProvider(FtpServerSessionProviders.roleBased()
                .realm(ftpRealm)
                .rootDirectory(Path.of("/srv/ftp")))
        .server();

// FTPS with implicit TLS (port defaults to 990 when secure)
FtpServer ftps = FtpServer.compose()
        .listener(new FtpListener().bindWildcard().secure(true).tls(tls))
        .realm(ftpRealm)
        .sessionProvider(FtpServerSessionProviders.roleBased()
                .realm(ftpRealm)
                .rootDirectory(Path.of("/srv/ftp")))
        .server();

Quota Management

The FTP server supports storage quotas to limit disk usage per user. Quotas are enforced on upload operations and can be queried via SITE commands.

SITE QUOTA Command

Users can query their current quota status: 

ftp> quote SITE QUOTA
211-Quota Status for user 'alice'
211-Source: Role-based quota (premium)
211-Storage: 2.5 GB used of 10 GB (25%)
211 End

Administrators with the ftp-admin role can check other users: 

ftp> quote SITE QUOTA bob
211-Quota Status for user 'bob'
211-Source: System default quota
211-Storage: 45 MB used of 100 MB (45%)
211 End

SITE SETQUOTA Command

Administrators can set per-user quotas: 

ftp> quote SITE SETQUOTA alice 20GB
200 Quota set for user 'alice': 20 GB

Sizes accept standard suffixes: KB, MB, GB, TB. Use unlimited for no limit.

Upload Quota Enforcement

When a user attempts to upload a file that would exceed their quota, the server returns a 552 error: 

ftp> put largefile.zip
552 Quota exceeded: 98 MB used of 100 MB

QuotaManager Configuration

Quotas are managed through a QuotaManager composed onto the session provider: 

RoleBasedQuotaManager ftpQuota = new RoleBasedQuotaManager();
ftpQuota.realm(ftpRealm);
ftpQuota.storageDir(Path.of("/var/ftp/quota"));
ftpQuota.defaultQuota("100MB");
ftpQuota.addRoleQuota("premium", "10GB");
ftpQuota.addRoleQuota("enterprise", "unlimited");

FtpServer server = FtpServer.compose()
        .listener(new FtpListener().port(21).bindWildcard())
        .realm(ftpRealm)
        .sessionProvider(FtpServerSessionProviders.roleBased()
                .realm(ftpRealm)
                .rootDirectory(Path.of("/srv/ftp"))
                .quotaManager(ftpQuota))
        .server();

Quota Policy Hierarchy

The RoleBasedQuotaManager determines a user's quota by checking:

  1. User-specific quota - set via SITE SETQUOTA
  2. Role-based quota - from addRoleQuota(role, size); the most generous of the user's roles wins
  3. System default - from defaultQuota(size)

Telemetry

Quota operations integrate with Gumdrop's telemetry:

  • QUOTA_CHECK - SITE QUOTA queries
  • QUOTA_SET - SITE SETQUOTA changes
  • QUOTA_EXCEEDED - upload denied with limit details
