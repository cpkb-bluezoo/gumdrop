Gumdrop Security

← Back to Main Page

This document covers security features available across all Gumdrop servers, including identity and access management, rate limiting, and transport security. For the in-tree TLS/DTLS stack (scope, cipher profiles, version pinning, configuration, and RFC conformance), see the dedicated TLS & DTLS page.

HTTP services add default security headers (X-Frame-Options, X-Content-Type-Options) to responses unless the application sets them. Optional RFC 6797 HSTS (Strict-Transport-Security) is available on TLS listeners. See HTTP Configuration for add-security-headers and HSTS properties.

Transport Layer Security

See TLS & DTLS for full documentation of supported protocol versions, TLS 1.2 profile limits, cipher suites, named groups, ALPN/SNI/mTLS configuration, and RFC conformance matrices. The sections below cover certificate setup and cross-transport comparisons.

TLS Certificates for Local Development

All secure listeners (TCP/TLS, DTLS, and QUIC) use the same in-tree TLS stack and accept the same server-identity configuration. See Server identity across transports. Certificate material is not checked in to the repository; you generate it once, locally.

The simplest form: three PEM files

The lowest-overhead way to give a listener an identity is plain PEM files. No keystore, no password, no format conversion, and the files are readable by curl, openssl, browsers and most other tools as they stand. Gumdrop’s build, tests and documentation use one layout:

FileHoldsUsed by
key.pem The server’s private key (unencrypted PKCS#8) The server: key-file / TlsConfig.pem
cert.pem The server’s certificate (and any intermediates) The server: cert-file / TlsConfig.pem
ca.pem The certificate of the CA that signed cert.pem Clients, as their trust anchor (curl --cacert, PemCredentials.loadTrustManager)

Only ca.pem is ever given to clients. key.pem stays on the server. 

// Server: the identity from two PEM files
TlsConfig tls = TlsConfig.pem(Path.of("etc/tls/cert.pem"), Path.of("etc/tls/key.pem"));
HttpServer http = HttpServer.compose()
    .secureEndpoint(8443, tls)
    .streamHandler(new MyStreamHandler())
    .server();

// Client: trust the CA in ca.pem, and nothing else
X509TrustManager trust = PemCredentials.loadTrustManager(Path.of("etc/tls/ca.pem"));

In server.xml for the servlet container, the same identity is: 

<listener port="8443" secure="true" cert-file="tls/cert.pem" key-file="tls/key.pem"/>

Generating them: ant tls-certs

From a checkout, one command creates the three files in etc/tls/ (gitignored), valid for localhost, 127.0.0.1 and ::1: 

ant tls-certs

It uses mkcert when it is installed, and openssl with a private CA otherwise. If neither is found the build stops and tells you how to install them for your system:

mkcert (recommended)openssl (fallback)
macOSbrew install mkcertbrew install openssl
Debian / Ubuntusudo apt install mkcertsudo apt install openssl
Fedorasudo dnf install mkcertsudo dnf install openssl
Windowswinget install FiloSottile.mkcert winget install ShiningLight.OpenSSL.Light, or the copy that comes with Git for Windows (found automatically)

mkcert is preferred because its CA can be added to your operating system’s trust store, which makes browsers and other tools trust the certificate with no further steps. With openssl you add ca.pem to the trust store yourself, or point a client at it directly. Programs installed somewhere unusual can be named with -Dmkcert.executable=... and -Dopenssl.executable=....

Ant targetWhat it does
tls-certs Creates key.pem, cert.pem and ca.pem; does nothing if they exist (-Dtls.force=true renews the certificate, keeping the CA)
tls-keystore Also builds keystore.p12 and truststore.p12 (see below)
tls-trust-install Adds the CA to the operating system trust store (mkcert only; may ask for your password)
tls-trust-uninstall Removes it again
tls-clean Deletes everything generated, including the CA and its key

Useful properties: -Dtls.dir= (output directory), -Dtls.names="localhost example.test 10.0.0.5" (host names and addresses), -Dtls.keytype=rsa (default is EC P-256) and -Dtls.generator=openssl. The header of ant/tls.xml lists them all.

The CA is created inside the checkout (etc/tls/ca/), not in mkcert’s per-user location, so nothing outside the checkout changes until you run tls-trust-install. After that, anyone who can read etc/tls/ca/rootCA-key.pem can create certificates your browser trusts: keep it private, and run ant tls-trust-uninstall tls-clean when you are finished with it.

To check a running server without touching the trust store, give curl the CA: 

curl --cacert etc/tls/ca.pem https://localhost:8443/

Without Ant

The files are ordinary PEM, so any tool can make them. With mkcert: 

mkcert -ecdsa -cert-file cert.pem -key-file key.pem localhost 127.0.0.1 ::1
cp "$(mkcert -CAROOT)/rootCA.pem" ca.pem

With only OpenSSL 1.1.1 or later, a self-signed certificate is a single command (it signs itself, so it is also its own trust anchor): 

openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 365 \
    -keyout key.pem -out cert.pem -subj "/CN=localhost" \
    -addext "subjectAltName=DNS:localhost,IP:127.0.0.1,IP:::1"
cp cert.pem ca.pem

Using Java keystores and truststores instead

Everything above also works with Java keystores, which suit deployments that already manage certificates that way. A keystore (PKCS#12, or JKS) holds the identity, and a truststore holds the trust anchors, in place of key.pem + cert.pem and ca.pem:

PEMJava keystore
Server identity cert-file, key-file; TlsConfig.pem(cert, key) keystore-file, keystore-pass, optional keystore-format (PKCS12 by default, or JKS); TlsConfig.keystore(path, pass)
Trust anchors PemCredentials.loadTrustManager(Path) TlsUtils.loadTrustManagers(path, pass, format)
Passwordnonerequired
Several identities in one file (SNI)no, one pair per listener yes, selected by alias

A listener takes one form or the other, not both. To build the keystore and truststore from the PEM files: 

ant tls-keystore          # etc/tls/keystore.p12 and etc/tls/truststore.p12, password "changeit"

or by hand: 

# PKCS#12 keystore: the server key and certificate, with the CA in the chain
openssl pkcs12 -export -in cert.pem -inkey key.pem -certfile ca.pem \
    -name server -out keystore.p12 -passout pass:changeit

# PKCS#12 truststore: the CA as a trust anchor (needs only the JDK)
keytool -importcert -noprompt -alias ca -file ca.pem \
    -keystore truststore.p12 -storetype PKCS12 -storepass changeit

# JKS, if something still wants it
keytool -importkeystore -srckeystore keystore.p12 -srcstoretype PKCS12 \
    -destkeystore keystore.jks -deststoretype JKS

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "changeit");
X509TrustManager trust = (X509TrustManager)
        TlsUtils.loadTrustManagers(Path.of("truststore.p12"), "changeit", "PKCS12")[0];

Going the other way, from an existing keystore back to PEM: 

openssl pkcs12 -in keystore.p12 -nokeys -out cert.pem                 # certificate(s)
openssl pkcs12 -in keystore.p12 -nocerts -nodes -out key.pem          # private key (PKCS#8)

TCP/TLS Configuration

Implicit TLS

Connection is encrypted from the start (e.g., SMTPS port 465, IMAPS port 993): 

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
ImapServer imaps = ImapServer.compose()
    .listener(new ImapListener().port(993).secure(true).tls(tls))
    .realm(realm)
    .sessionProvider(ImapServerSessionProviders.mailbox(maildirFactory))
    .server();

STARTTLS

Connection starts unencrypted and upgrades to TLS on client request: 

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
SmtpServer smtp = SmtpServer.compose()
    // Advertises STARTTLS capability
    .listener(new SmtpListener().port(25).tls(tls))
    .sessionProvider(SmtpServerSessionProviders.relay()
        .hostname("relay.example.com"))
    .server();

Client Certificate Authentication (mTLS)

Servers can require or request client certificates for mutual TLS (mTLS):

The trust anchors are the CA that signed the clients’ certificates, as a PEM file or a truststore (see above): 

SmtpListener listener = new SmtpListener();
listener.setNeedClientAuth(true);
// From a PEM file (simplest):
listener.setTrustManager(PemCredentials.loadTrustManager(Path.of("client-ca.pem")));
// or from a Java truststore:
// listener.setTrustManager((X509TrustManager)
//         TlsUtils.loadTrustManagers(Path.of("truststore.p12"), "secret", "PKCS12")[0]);
SmtpServer smtp = SmtpServer.compose()
    .listener(listener)
    .sessionProvider(SmtpServerSessionProviders.relay()
        .hostname("relay.example.com"))
    .server();

SNI (Server Name Indication)

SNI allows a server to present different certificates based on the hostname the client requests during the TLS handshake. This enables hosting multiple secure domains on a single IP address and port. 

Map<String, String> sniHostnames = new HashMap<>();
sniHostnames.put("example.com", "example-cert");
sniHostnames.put("*.example.com", "example-wildcard");
sniHostnames.put("other.com", "other-cert");

Http2Listener listener = new Http2Listener().port(443).secure(true);
listener.setKeystoreFile("multi-domain.p12");
listener.setKeystorePass("secret");
listener.setSniHostnames(sniHostnames);
listener.setSniDefaultAlias("default-cert");
HttpServer https = HttpServer.compose()
    .listener(listener)
    .streamHandler(new MyStreamHandler())
    .server();

The sniHostnames map specifies hostname-to-certificate-alias mappings. Hostnames can be exact (example.com) or wildcard patterns (*.example.com). The keystore must contain certificates with the specified aliases. If no match is found, sniDefaultAlias is used.

Server identity across transports

Gumdrop uses one in-tree TLS implementation (org.bluezoo.gumdrop.tls) for TCP/TLS, DTLS, and QUIC-TLS. Server certificate configuration is therefore the same regardless of transport: either a Java keystore or a PEM certificate chain plus private key. There is no separate “QUIC TLS engine” with different credential rules.

QUIC mandates TLS 1.3 — there is no unencrypted mode and no STARTTLS upgrade. The handshake is integrated into QUIC connection establishment, so every QUIC packet is encrypted. That is a protocol requirement, not a difference in how you load keys.

TCP/TLS (HTTP/1.x, HTTP/2, SMTP, …) UDP (DTLS, DoQ) / QUIC (HTTP/3)
TLS engine In-tree org.bluezoo.gumdrop.tls Same engine (TlsRecordEngine, Dtls13RecordEngine, QuicTlsServerEngine, …)
Keystore keystore-file, keystore-pass, optional keystore-format (PKCS#12 or JKS)
PEM files cert-file (full chain) and key-file (unencrypted private key)
Protocol version TLS 1.2 or TLS 1.3 per listener (tls-version) DTLS 1.2/1.3 (dtls-version) or TLS 1.3 only for QUIC

Use one identity for co-located listeners (e.g. HTTPS on TCP and HTTP/3 on UDP on port 443): the same keystore-file or the same cert-file/key-file pair on both listeners. Browsers require matching certificate identity when upgrading via Alt-Svc.

PEM file format

When using cert-file and key-file, the certificate file must contain the full chain (leaf followed by intermediates). The private key file must be unencrypted PEM in PKCS#8 form (a -----BEGIN PRIVATE KEY----- block, RSA or EC). The older traditional format (-----BEGIN RSA PRIVATE KEY-----) is not supported; convert it with openssl pkcs8 -topk8 -nocrypt -in old.pem -out key.pem. This applies on every transport, not only QUIC. See the standard three-file layout, and converting to and from keystores.

Example: Co-located HTTPS and HTTP/3 Listeners

A typical deployment shares the same port (443 or 8443) between an HTTPS listener on TCP and an HTTP/3 listener on UDP, using the same server identity on both: 

// secureEndpoint() pairs a TCP HTTP/2 listener and a UDP HTTP/3 listener
// on the same port, both presenting the same TlsConfig identity.
TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
HttpServer http = HttpServer.compose()
    .secureEndpoint(8443, tls)
    .streamHandler(new ServletRequestHandler(container))
    .server();

Both listeners must present the same certificate identity (same subject/SAN) to avoid browser warnings when upgrading from HTTP/2 to HTTP/3. The browser discovers HTTP/3 support via the Alt-Svc response header on the initial HTTP/2 connection and will only attempt QUIC if the certificate matches.

Cipher Suite and Named Group Configuration

Cipher suite and named group configuration applies to all transports using the in-tree engine (TCP/TLS, DTLS, QUIC). On TLS 1.2 / DTLS 1.2 listeners, use TLS 1.2 cipher suite names; setNamedGroups is ignored. See TLS & DTLS — cipher suites. 

Http3Listener listener = new Http3Listener().port(443);
listener.setKeystoreFile("keystore.p12");
listener.setKeystorePass("secret");
listener.setCipherSuites("TLS_AES_256_GCM_SHA384");
listener.setNamedGroups("X25519");

The default cipher suites are ChaCha20-Poly1305, then AES-128-GCM, then AES-256-GCM (see TLS & DTLS). The default named group is X25519; hybrid post-quantum groups (e.g. X25519MLKEM768) are available on Java 25+ when configured.

Certificate Pinning

PinnedCertTrustManager wraps an X509TrustManager and validates server certificates against a set of SHA-256 fingerprints. If the presented certificate does not match any pinned fingerprint, the TLS handshake is rejected.

All client classes support certificate pinning via setTrustManager(X509TrustManager): HttpClient, SmtpClient, ImapClient, Pop3Client, WebSocketClient, RedisClient, LdapClient.

Identity and Access Management (IAM)

Gumdrop provides a unified identity and access management framework used across all protocol implementations. At its core is the Realm interface, which abstracts credential storage and verification.

The Realm Interface

A Realm represents a collection of authenticatable principals with associated passwords and roles. The interface supports multiple authentication mechanisms without exposing stored credentials: 

public interface Realm {
    Realm forSelectorLoop(SelectorLoop loop);
    Set<SaslMechanism> getSupportedSASLMechanisms();
    boolean passwordMatch(String username, String password);
    String getDigestHA1(String username, String realmName);
    boolean isUserInRole(String username, String role);
    boolean userExists(String username);
    String getCramMD5Response(String username, String challenge);
    ScramCredentials getScramCredentials(String username);
    TokenValidationResult validateBearerToken(String token);
    TokenValidationResult validateOAuthToken(String accessToken);
    CertificateAuthenticationResult authenticateCertificate(X509Certificate cert);
    boolean authorizeAs(String authenticatedUser, String requestedUser);
}

Most methods are default and throw UnsupportedOperationException — realms need only implement the mechanisms they support. This design allows the realm to store passwords in any form (plaintext, hashed, or derived keys) without requiring the authentication layer to know the storage format.

BasicRealm Implementation

The built-in BasicRealm reads users and groups from an XML file: 

<realm>
  <!-- Group definitions -->
  <group id="readers" name="mail-read imap-read pop3-read"/>
  <group id="writers" name="mail-read mail-write imap-read imap-write"/>
  <group id="admins" name="admin mail-admin ftp-admin"/>
  
  <!-- User definitions -->
  <user name="alice" password="secret123" groups="#readers #writers"/>
  <user name="bob" password="password456" groups="#readers"/>
  <user name="admin" password="adminpass" groups="#admins"/>
  
  <!-- Inline roles (legacy format) -->
  <user name="guest" password="guest" roles="guest read-only"/>
</realm>

Group References

Groups are defined with an id for referencing and a name containing space-separated role names. Users reference groups using the #id syntax in their groups attribute.

Configuration

BasicRealm mailRealm = new BasicRealm();
mailRealm.setHref(Path.of("users.xml"));

setHref parses the users.xml-format file shown above directly — it's a standalone SAX parser, independent of any application composition code. Attach the realm to a server with .realm(realm) on the composer.

Production Use

BasicRealm with plaintext passwords is intended for development and testing only. For production, use LdapRealm or OAuthRealm. A warning is logged at startup when plaintext passwords are loaded.

Hashed Passwords (RFC 2307)

Passwords may use LDAP-style hashed formats for improved security. Supported schemes: {SHA}, {SSHA}, {SHA256}, {SSHA256}. Values can be exported from LDAP userPassword and used directly. Hashed users support only PLAIN and LOGIN SASL mechanisms; CRAM-MD5, SCRAM, Digest, and APOP require plaintext and will not work. 

<user name="alice" password="{SSHA256}base64digest+salt" groups="readers"/>

Use slappasswd -h {SSHA256} -s password (OpenLDAP) or equivalent tools to generate hashed values.

OAuthRealm

Scope and non-goals

Gumdrop is not an OAuth 2.0 authorization server. It does not implement authorization endpoints, authorization codes, refresh-token issuance, PKCE (RFC 7636), or DPoP (RFC 9449). Those flows exist to paper over weaknesses of bearer tokens (any holder can replay a stolen token). Gumdrop does not aim to grow a large in-tree OAuth server or sender-constrained token stack on top of that model.

What is supported is narrow and conformant for a resource server that already receives tokens from an external authorization server you operate separately:

  • RFC 6750 Bearer usage on protected HTTP resources (and related mail SASL OAUTHBEARER where configured)
  • RFC 7662 token introspection, and optional local RFC 7519 JWT validation for access tokens issued elsewhere

For deployments that care about proof of client identity rather than bearer replay, prefer mechanisms Gumdrop implements directly, such as mTLS, HTTP Digest, or SASL with channel binding, instead of expecting Gumdrop to become an OAuth authorization server.

OAuthRealm validates OAuth 2.0 tokens via RFC 7662 (token introspection) and optionally via local RFC 7519 JWT validation. Constructed with a Properties instance specifying the introspection endpoint, client credentials, and role-scope mappings. Not directly DI-instantiable; use a factory or programmatic setup.

Local JWT Validation (RFC 7519)

When oauth.jwt.enabled=true, tokens that look like JWTs (three Base64url-encoded dot-separated segments) are validated locally before falling back to the introspection endpoint. This eliminates the round-trip for self-contained JWTs.

Supported signature algorithms (RFC 7518 §3):

  • HS256 — HMAC-SHA256 with shared secret (oauth.jwt.secret)
  • RS256 — RSA PKCS#1 v1.5 SHA-256 with public key (oauth.jwt.public.key)
  • ES256 — ECDSA P-256 SHA-256 with public key (oauth.jwt.public.key)

Standard claims are verified: exp (expiration), nbf (not-before) with configurable clock skew tolerance, iss (issuer), and aud (audience).

# Enable local JWT validation
oauth.jwt.enabled=true
oauth.jwt.secret=my-shared-secret

# Optional claim validation
oauth.jwt.issuer=https://auth.example.com
oauth.jwt.audience=my-service
oauth.jwt.clock.skew=30

isUserInRole() checks cached token scopes against role-scope mappings. See the oauth-servlet-auth example for a working configuration.

Custom Realm Implementations

For production deployments, implement the Realm interface to integrate with your identity provider:

  • LDAP/Active Directory - query directory for authentication
  • Database - store credentials in SQL/NoSQL database
  • OAuth 2.0/OIDC - validate tokens via OAuthRealm or custom implementation
  • PAM - integrate with system authentication

SASL Authentication

SMTP, IMAP, POP3, and FTP servers support SASL (Simple Authentication and Security Layer) mechanisms for secure credential exchange.

Supported Mechanisms

Mechanism Security Requirements Recommended
PLAIN Password transmitted (base64) TLS required Over TLS only
LOGIN Password transmitted (base64) TLS required Legacy compatibility
CRAM-MD5 Challenge-response, no password sent Realm must store plaintext No
DIGEST-MD5 Digest authentication Realm must provide H(A1) No (deprecated)
SCRAM-SHA-256 Mutual auth, no password sent Realm provides derived keys Yes
OAUTHBEARER Bearer token OAuth 2.0 infrastructure For OAuth deployments
GSSAPI Kerberos V5 mutual auth Keytab + service principal For Kerberos/enterprise SSO
EXTERNAL TLS client certificate mTLS configured For certificate-based auth

SCRAM-SHA-256 (Recommended)

SCRAM-SHA-256 is the recommended mechanism because:

  • Password is never transmitted, even encrypted
  • Mutual authentication (server proves identity too)
  • Realm can store only derived keys (no plaintext)
  • Protection against server compromise

The realm stores StoredKey and ServerKey instead of the password. Even if the credential store is compromised, attackers cannot recover the original password.

GSSAPI/Kerberos (RFC 4752)

GSSAPI enables Kerberos V5 single sign-on authentication for IMAP, POP3, and SMTP. Each service requires a keytab file and service principal.

Server-side GSSAPI authentication is event-loop safe: the acceptSecContext() operation decrypts the service ticket using the local keytab with no KDC network I/O. The LDAP client's GSSAPI bind automatically offloads the first initSecContext() call to a worker thread since it may contact the KDC.

Gumdrop negotiates "no security layer" (RFC 4752 §3.1) since TLS already provides confidentiality and integrity.

Configuration
// Programmatic
imapListener.configureGSSAPI(
    Path.of("/etc/krb5.keytab"),
    "imap/mail.example.com@EXAMPLE.COM");

// Or via setGSSAPIServer() for shared keytab
GssapiServer gss = new GssapiServer(
    Path.of("/etc/krb5.keytab"),
    "imap/mail.example.com@EXAMPLE.COM");
imapListener.setGSSAPIServer(gss);

After successful GSSAPI authentication, the authenticated Kerberos principal (e.g. user@EXAMPLE.COM) is mapped to a local username via the Realm's mapKerberosPrincipal() method. The default implementation strips the realm portion.

Role-Based Access Control

Many Gumdrop servers support role-based access control (RBAC) for fine-grained authorization. Roles are assigned to users in the realm and checked by the server during operations.

Protocol-Specific Roles

ProtocolRolesDescription
FTP ftp-read Download files, list directories
ftp-write Upload files (implies ftp-read)
ftp-delete Delete files/directories (implies ftp-write)
ftp-admin Full access, SITE commands, quota management
Servlet (custom) Roles defined in web.xml security constraints
manager Access to manager application

Example: FTP Role Configuration

<!-- Define role groups -->
<realm>
  <group id="readers" name="ftp-read"/>
  <group id="uploaders" name="ftp-read ftp-write"/>
  <group id="managers" name="ftp-read ftp-write ftp-delete"/>
  <group id="admins" name="ftp-admin"/>
  
  <user name="guest" password="guest" groups="#readers"/>
  <user name="contributor" password="secret" groups="#uploaders"/>
  <user name="editor" password="secret" groups="#managers"/>
  <user name="admin" password="secret" groups="#admins"/>
</realm>

Rate Limiting

Gumdrop provides comprehensive rate limiting to protect servers from abuse, denial-of-service attacks, and brute-force authentication attempts.

Connection Rate Limiting

The ConnectionRateLimiter provides two types of protection:

Concurrent Connection Limits

Limits the number of simultaneous connections from a single IP address, preventing resource exhaustion from connection flooding. 

SmtpListener listener = new SmtpListener().port(25);
listener.setMaxConnectionsPerIP(10);
SmtpServer smtp = SmtpServer.compose()
    .listener(listener)
    .sessionProvider(SmtpServerSessionProviders.relay()
        .hostname("relay.example.com"))
    .server();

Connection Rate Limits

Limits the number of connection attempts per IP address within a time window, preventing rapid reconnection attacks. 

FtpListener listener = new FtpListener().port(21);
listener.setRateLimit("100/60s");
FtpServer ftp = FtpServer.compose()
    .listener(listener)
    .realm(realm)
    .sessionProvider(FtpServerSessionProviders.fileSystem()
        .rootDirectory(Path.of("/var/ftp")))
    .server();

Rate Limit Format

setRateLimit accepts the format count/duration:

  • 100/60s - 100 per minute
  • 1000/1h - 1000 per hour
  • 50/30s - 50 per 30 seconds

Implementation

Rate limiting uses a sliding window algorithm that efficiently tracks connection timestamps. Old entries are automatically expired, and a background cleanup task removes stale tracking data to prevent memory leaks.

Authentication Rate Limiting

The AuthenticationRateLimiter protects against brute-force password attacks by tracking failed authentication attempts and temporarily locking out offending clients. 

ImapListener listener = new ImapListener().port(143);
listener.setMaxAuthFailures(5);
listener.setAuthLockoutTime("5m");
ImapServer imap = ImapServer.compose()
    .listener(listener)
    .realm(realm)
    .sessionProvider(ImapServerSessionProviders.mailbox(maildirFactory))
    .server();

Exponential Backoff

By default, lockout duration increases exponentially for repeat offenders:

  • 1st lockout: 5 minutes
  • 2nd lockout: 10 minutes
  • 3rd lockout: 20 minutes
  • ... up to maximum (default: 1 hour)

Tracking Keys

Authentication failures can be tracked by:

  • IP address - protects against distributed attacks from one source
  • Username - protects against credential stuffing
  • IP + Username - most precise tracking

Network Filtering (CIDR)

SMTP servers support CIDR-based network filtering for allow/block lists: 

SmtpListener listener = new SmtpListener().port(25);
listener.setAllowedNetworks("192.168.0.0/16,10.0.0.0/8,2001:db8::/32");
listener.setBlockedNetworks("192.168.100.0/24,2001:db8:bad::/48");
SmtpServer smtp = SmtpServer.compose()
    .listener(listener)
    .sessionProvider(SmtpServerSessionProviders.relay()
        .hostname("relay.example.com"))
    .server();

Blocked networks are checked first, then allowed networks. If allowed networks are configured, only connections from those networks are accepted.

Security Telemetry

Security-related events are integrated with Gumdrop's telemetry system for monitoring and alerting:

Error Categories

  • ErrorCategory.RATE_LIMITED - connection/command rate limiting
  • ErrorCategory.AUTHENTICATION_FAILED - auth failures
  • ErrorCategory.AUTHORIZATION_DENIED - permission denied
  • ErrorCategory.TLS_ERROR - TLS handshake failures

Telemetry Events

  • AUTH_SUCCESS - successful authentication
  • AUTH_FAILURE - failed authentication attempt
  • AUTH_LOCKED - account locked out
  • CONNECTION_REJECTED - rate limit or policy rejection

Example: Monitoring Authentication Failures

Configure your OpenTelemetry backend to alert on authentication failures: 

// Prometheus query example
sum(rate(span_events{event="AUTH_FAILURE"}[5m])) by (server) > 10
