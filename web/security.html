Identity and access management

Every Gumdrop protocol that authenticates users does so through one abstraction, org.bluezoo.gumdrop.auth.Realm. A realm is a collection of principals with credentials and roles. SMTP, IMAP, POP3, FTP, HTTP (including WebDAV and the servlet container), MQTT and SOCKS all take the same realm, so one user store can serve every service you run.

Using a realm

Give a realm to a server with realm() on its composer: 

BasicRealm realm = new BasicRealm().href(Path.of("users.xml"));

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
ImapServer imaps = ImapServer.compose()
    .listener(new ImapListener().port(993).secure(true).tls(tls))
    .realm(realm)
    .sessionProvider(ImapServerSessionProviders.mailbox(maildirFactory))
    .server();

SmtpServer, Pop3Server, FtpServer, HttpServer, SocksServer and MqttServer composers all have the same realm(Realm) method, and so does the WebDAVRequestHandler builder (where it supplies the privilege roles, see below). The servlet container declares its realms in server.xml: 

<realm name="myRealm" class="org.bluezoo.gumdrop.auth.BasicRealm" href="realm.xml"/>

and web applications refer to one by name from web.xml. The class needs a public no-argument constructor, and href is only understood for BasicRealm. See Servlet container.

What each protocol asks of the realm:

ProtocolAuthentication
SMTP, IMAP, POP3 SASL (see below). IMAP also has LOGIN (refused on a plaintext connection unless the server is composed with allowPlaintextLogin(true)), POP3 also has USER/PASS.
FTPUSER/PASS checked with passwordMatch; the FTP roles are then resolved once at login.
HTTPBasic, Digest or Bearer, chosen from the realm (see HTTP authentication).
MQTTThe username and password in CONNECT.
SOCKSRFC 1929 username/password.

The Realm interface

A realm never blocks the thread that calls it. A realm backed by a directory server or a token service has to talk to the network to answer, and a server must not make an event-loop thread wait while it does. So every lookup takes a RealmCallback and returns at once: 

public interface RealmCallback<T> {
    void completed(T result);
    void failed(Throwable cause);
}

The callback is called exactly once. It is delivered on the thread of the loop the realm was bound to with forSelectorLoop, so a protocol handler can touch its connection state directly; a realm whose answer is already in memory may call it before the method returns. failed means the realm could not answer (directory unreachable, timeout), and every server treats that as a refusal: authentication fails and the user holds no role. A wrong password or an unknown user is not a failure; it completes with false. 

Realm bound = realm.forSelectorLoop(endpoint.getSelectorLoop());
bound.passwordMatch("alice", "secret", new RealmCallback<Boolean>() {
    public void completed(Boolean matched) { /* on the connection's loop */ }
    public void failed(Throwable cause)    { /* treat as not authenticated */ }
});

You rarely write this yourself: the protocol handlers do it, and the servlet container bridges to the blocking Servlet API on its own worker threads. The operations are:

Method (each takes a RealmCallback)ResultBacks

getDigestHA1(user, realmName)String HTTP Digest only: lowercase hex SHA-256 of user:realm:password; guarded by supportsDigestHA1() (default: false)

A realm also declares the mechanisms it can serve with getSupportedSASLMechanisms(); servers advertise only those. A realm stores credentials however it likes (plaintext, hashed, or derived keys), because the authentication layer only ever asks it questions and never reads a stored password.

Writing a realm

If every answer is already in memory (a map, a file read at start-up), extend SynchronousRealm. You write ordinary methods that return their answer, and it adapts them to the callback contract. A runtime exception from a lookup is reported as failed. 

public class MapRealm implements SynchronousRealm {
    private final Map<String, String> passwords;
    private final Map<String, Set<String>> roles;
    ...
    public Set<SaslMechanism> getSupportedSASLMechanisms() {
        return EnumSet.of(SaslMechanism.PLAIN, SaslMechanism.LOGIN);
    }
    public boolean passwordMatch(String user, String password) {
        return password.equals(passwords.get(user));
    }
    public String getDigestHA1(String user, String realmName) { return null; }
    public boolean isUserInRole(String user, String role) {
        Set<String> held = roles.get(user);
        return held != null && held.contains(role);
    }
}

Only quick lookups belong there. If answering takes real work, a network round trip or a deliberately slow password hash, implement Realm directly and call the callback from where the work finishes. A forSelectorLoop that returns this is fine when the realm needs no loop; a realm that makes its own client connections returns a copy whose connections run on the given loop, as LdapRealm does. For slow work, StorageExecutor.submit runs a blocking task off the loop and delivers its result back on it.

BasicRealm

BasicRealm is the built-in realm. It reads users and groups from an XML file with a standalone SAX parser, and it is the one realm server.xml can load from a file: 

<realm>
  <!-- id is what users refer to; name is the role checked at run time -->
  <group id="readers" name="ftp-read"/>
  <group id="writers" name="ftp-read ftp-write"/>
  <group id="admins"  name="ftp-admin"/>

  <user name="alice" password="secret123" groups="readers writers"/>
  <user name="bob"   password="password456" groups="readers"/>
  <user name="admin" password="adminpass" groups="admins"
        cert-fingerprint="SHA-256:ab:cd:..."/>
</realm>

A group has an id and a name. A user lists the ids of its groups, separated by spaces (XML IDREFS: no # prefix), and holds each group's name as a role. A group with only an id uses it as the role name too. The older nested form still works, with the users inside the group: 

<group name="admin">
  <user name="root" password="secret"/>
</group>

A user's cert-fingerprint (the SHA-256 of the DER certificate, as colon-separated hex, with or without a SHA-256: prefix) lets a client certificate authenticate as that user with SASL EXTERNAL. 

BasicRealm realm = new BasicRealm().href(Path.of("users.xml"));   // or href(String)
realm.defineGroup("ops", "ops-role");    // programmatic group: id, role name
realm.addToRole("alice", "ops-role");    // grant a role to a user

Users can only be created from the XML; the programmatic methods manage groups and roles.

Passwords and hashing

A plaintext password is for development and testing, and a warning is logged when one is loaded. Use a hash instead. The recommended format is {PBKDF2}, a salted, iterated PBKDF2WithHmacSHA256: {PBKDF2}<iterations>$<base64-salt>$<base64-hash>, generated with BasicRealm.createPbkdf2Hash(password) (210,000 iterations). The LDAP-style RFC 2307 formats {SHA256} and {SSHA256} are also accepted so that values exported from a directory's userPassword can be reused, but they are weak: fast, unsalted ({SHA256}) or single-iteration hashes that are cheap to brute-force. The SHA-1 formats {SHA} and {SSHA} are no longer supported: a user stored with one cannot authenticate.

  • A hashed user can only use PLAIN and LOGIN (and the password-based protocols such as FTP and HTTP Basic). SCRAM and HTTP Digest need the plaintext password, so they fail for hashed users.
  • Checking a hashed password is deliberately slow. Once the realm is bound to a loop, BasicRealm runs it on the storage executor, so it never stalls the loop. The same goes for the first SCRAM derivation of a plaintext user, which is then cached.

BasicRealm advertises PLAIN, LOGIN, SCRAM-SHA-256 and EXTERNAL, and supports HTTP Digest (SHA-256) through supportsDigestHA1() for users with plaintext passwords. For production user stores prefer LdapRealm or OAuthRealm.

LdapRealm

LdapRealm (module gumdrop-ldap) authenticates against an LDAP or Active Directory server, and reads roles from a user attribute such as memberOf. It is fully asynchronous: each operation opens its own connection on the caller's loop, with a timeout, and fails closed. See LDAP client & realm for configuration, STARTTLS, SASL binds and certificate lookup.

OAuthRealm

Scope and non-goals

Gumdrop is not an OAuth 2.0 authorisation server. It does not implement authorisation endpoints, authorisation codes, refresh-token issuance, PKCE (RFC 7636) or DPoP (RFC 9449). Those flows exist to paper over weaknesses of bearer tokens, where any holder can replay a stolen token, and Gumdrop does not aim to grow an OAuth server or a sender-constrained token stack on top of that model.

What is supported is narrow, for a resource server that receives tokens from an authorisation server you operate separately:

  • RFC 6750 Bearer usage on protected HTTP resources, and the mail SASL OAUTHBEARER mechanism (RFC 7628)
  • RFC 7662 token introspection, and optional local RFC 7519 JWT validation for access tokens issued elsewhere

Where proof of client identity matters more than bearer replay, prefer mechanisms Gumdrop implements directly: mutual TLS (see client certificates), HTTP Digest, or SCRAM.

Configuration

org.bluezoo.gumdrop.auth.oauth.OAuthRealm is built from a Properties object. Introspection is non-blocking: the token is posted to the authorisation server with Gumdrop's own HTTP client, and the request fails, and so the token is rejected, if no answer arrives within oauth.http.timeout. 

Properties config = new Properties();
config.setProperty("oauth.authorization.server.url", "https://auth.example.com");
config.setProperty("oauth.client.id", "my-service");
config.setProperty("oauth.client.secret", "secret123");
config.setProperty("oauth.cache.enabled", "true");
config.setProperty("oauth.scope.mapping.admin", "admin,superuser");
OAuthRealm realm = new OAuthRealm(config);

Local JWT validation (RFC 7519)

With oauth.jwt.enabled=true, tokens that look like JWTs (three Base64url segments) are validated locally before the introspection endpoint is tried, which saves the round trip for self-contained tokens. Supported signatures (RFC 7518 §3) are HS256, RS256 and ES256. The exp and nbf claims (with the configured skew), iss and aud are checked.

isUserInRole maps the token's scopes to roles through oauth.scope.mapping.*. See the oauth-servlet-auth example.

SASL authentication

SMTP, IMAP and POP3 authenticate with SASL (RFC 4422). A server offers the mechanisms its realm lists in getSupportedSASLMechanisms(), and does not offer those that need a secure connection (requiresTLS) until the connection is encrypted. FTP, MQTT and SOCKS do not use SASL.

MechanismNeeds TLSRealm must provideNotes
PLAIN (RFC 4616)yespasswordMatch Password sent (Base64); fine over TLS
LOGINyespasswordMatch Legacy clients
SCRAM-SHA-256 (RFC 5802, 7677)nogetScramCredentials Recommended. No password sent, the server proves itself, and the realm can hold derived keys instead of the password.
OAUTHBEARER (RFC 7628)yesvalidateBearerToken For OAuth deployments (see OAuthRealm)
GSSAPI (RFC 4752)noa configured GssapiServer Kerberos single sign-on (see below)
EXTERNAL (RFC 4422 App. A)yesauthenticateCertificate Identity from the TLS client certificate (mutual TLS must be on)

CRAM-MD5 and DIGEST-MD5 are intentionally not supported (offline dictionary attack on a captured exchange, the server must hold the plaintext or a password-equivalent, no channel binding; DIGEST-MD5 is Historic per RFC 6331), and POP3 APOP has been removed. Use SCRAM-SHA-256, or PLAIN or OAUTHBEARER over TLS.

SCRAM-SHA-256

SCRAM is the best choice for password logins. The password never crosses the wire, the client also verifies the server, and a stolen credential store does not reveal passwords. The realm supplies a salt, an iteration count, a StoredKey and a ServerKey in a Realm.ScramCredentials. A realm that keeps only these derived keys cannot be used to recover the passwords. BasicRealm derives them from a plaintext password with 210,000 PBKDF2 iterations (off the loop thread, then cached).

GSSAPI and Kerberos

GSSAPI gives Kerberos V5 single sign-on on SMTP, IMAP and POP3. Each service needs a keytab and a service principal. Configure it on the listener: 

ImapListener listener = new ImapListener().port(143);
listener.configureGSSAPI(
    Path.of("/etc/krb5.keytab"),
    "imap/mail.example.com@EXAMPLE.COM");        // throws IOException

// or build one GssapiServer and share it
GssapiServer gss = new GssapiServer(Path.of("/etc/krb5.keytab"),
    "imap/mail.example.com@EXAMPLE.COM");
listener.gssapiServer(gss);

SmtpListener and Pop3Listener have the same two methods. The keytab is read when the GssapiServer is created, so do that at start-up. Gumdrop negotiates no SASL security layer (RFC 4752 §3.1), because TLS already provides confidentiality and integrity. After a successful exchange the Kerberos principal (user@EXAMPLE.COM) becomes a local user name through the realm's mapKerberosPrincipal, which by default strips the Kerberos realm. For GSSAPI as a client of an LDAP server, see LDAP client & realm.

HTTP authentication

Give an HttpServer a realm and it authenticates requests with a DefaultHttpAuthenticationProvider over that realm, in the first of these schemes the realm supports:

  1. Bearer if the realm supports OAUTHBEARER
  2. Digest if realm.supportsDigestHA1() is true
  3. Basic otherwise

Basic sends the password, so use it only over TLS. Note that BasicRealm supports Digest, so an HTTP server over a BasicRealm uses Digest (RFC 7616, algorithm SHA-256 with qop=auth only; MD5 variants are rejected), and Digest needs the plaintext password: users stored as hashes cannot log in over HTTP that way. Either keep those users in a realm that answers Digest, or supply your own HttpAuthenticationProvider (subclass it and implement the callback-based passwordMatch, getDigestHA1, validateBearerToken and validateOAuthToken hooks).

The realm may take time to answer. The server does not process a request until authentication has finished, and holds any request events that arrive meanwhile (on HTTP/1.1, HTTP/2 and HTTP/3 alike). A failed or timed-out lookup answers 401. The authenticated principal is then available to the request handler (HttpResponse.getPrincipal(), and the servlet user principal). The servlet container authenticates per web application from web.xml login-config, against the realm it names.

Role-based access control

Authentication says who a user is; roles say what they may do. Roles are assigned in the realm and asked of it with isUserInRole. Servers ask without blocking and carry on when the answer arrives: FTP resolves its four roles once at login, a quota manager resolves quota roles at login, and WebDAV resolves its privilege roles when a request starts.

ServiceRolesMeaning
FTP ftp-read Download files and list directories
ftp-writeUpload and create directories (includes read)
ftp-delete Delete, remove directories and rename (includes write and read)
ftp-adminEverything, plus SITE commands and quota management
IMAPadmin Read another user's quota, and SETQUOTA
SMTPadmin, postmaster Use an envelope sender other than your own address
WebDAV ACLwebdav:all, webdav:write, webdav:read, webdav:write-properties, webdav:write-content, webdav:bind, webdav:unbind, webdav:unlock, webdav:read-acl, webdav:write-acl, webdav:read-current-user-privilege-set The RFC 3744 privileges reported for the signed-in user. all grants every privilege and write grants write-properties, write-content, bind and unbind.
Servlet(your own) Roles named in web.xml security constraints

The FTP role names are constants on FtpRoles. A realm that cannot answer a role check counts as not holding the role. For example, the FTP roles above in a BasicRealm file: 

<realm>
  <group id="readers"   name="ftp-read"/>
  <group id="uploaders" name="ftp-read ftp-write"/>
  <group id="managers"  name="ftp-read ftp-write ftp-delete"/>
  <group id="admins"    name="ftp-admin"/>

  <user name="guest"       password="{PBKDF2}..." groups="readers"/>
  <user name="contributor" password="{PBKDF2}..." groups="uploaders"/>
  <user name="editor"      password="{PBKDF2}..." groups="managers"/>
  <user name="admin"       password="{PBKDF2}..." groups="admins"/>
</realm>

Rate limiting and network filtering

These controls are set on a listener and are checked when a connection is accepted, before any protocol handler sees it. They work the same for every protocol.

Connection limits

Listener methodEffect
maxConnections(int) A cap on all simultaneous connections to the listener (0 is unlimited). The hard backstop against file-descriptor and memory exhaustion.
maxConnectionsPerIP(int) A cap on simultaneous connections from one address (0 disables it).
rateLimit(String) A cap on new connections from one address per time window, written count/duration: 100/60s, 1000/1h, 50/30s, 500/250ms, 20/5m. The units are ms, s, m and h. An invalid string throws IllegalArgumentException.

Each returns the listener, so they chain: 

SmtpServer smtp = SmtpServer.compose()
    .listener(new SmtpListener().port(25)
        .maxConnections(5000)
        .maxConnectionsPerIP(10)
        .rateLimit("100/60s"))
    .sessionProvider(SmtpServerSessionProviders.relay()
        .hostname("relay.example.com"))
    .server();

The two per-address limits come as a pair. The first call to either maxConnectionsPerIP or rateLimit switches on per-address limiting with both defaults: 10 simultaneous connections and 100 new connections per 60 seconds from each address. Set both if you want different numbers. The rate uses a sliding window, and stale per-address entries are discarded as connections arrive so the tables stay bounded. A connection over a limit is refused at accept time.

Authentication lockout

A listener can lock a client out of authenticating after repeated failures, which stops password guessing without involving the realm. Configure it on the listener:

Listener methodEffect
maxAuthFailures(int) Failed attempts from one address before it is locked out (default 5 once lockout is enabled).
authLockoutTimeMs(long) How long the first lockout lasts (default 5 minutes).
ImapListener listener = new ImapListener().port(993).secure(true).tls(tls)
    .maxAuthFailures(5)
    .authLockoutTimeMs(5 * 60 * 1000L);

Calling either method switches lockout on; with neither, nothing is locked out. Failures are counted per client address (and per address and user name). Each further lockout of the same client doubles the time, up to one hour, and a successful login clears the failure count. A client that is locked out is refused before the realm is asked, even with the right password, so a guesser learns nothing during the lockout. Every protocol that authenticates enforces it:

ProtocolA locked-out client gets
SMTP454 4.7.0 to AUTH
IMAPNO [UNAVAILABLE] to LOGIN and AUTHENTICATE
POP3-ERR [SYS/TEMP] to PASS and AUTH
FTP421 to PASS
HTTP (1.1, 2 and 3), WebDAV 429 Too Many Requests to a request that carries credentials; a request with none still gets the 401 challenge
MQTTCONNACK "not authorised", then close
SOCKS5username/password failure, then close

Only a bad credential counts as a failure. A realm that cannot answer (a directory outage, say) does fail the login, and counts like any other failure, so a long outage can lock out clients that were trying valid passwords; keep the threshold high enough to tolerate that.

Network filtering (CIDR)

Any listener can restrict who may connect by network, with IPv4 or IPv6 CIDR blocks: 

SmtpListener listener = new SmtpListener().port(25)
    .allowedNetworks(CidrNetwork.parseList("192.168.0.0/16,10.0.0.0/8,2001:db8::/32"))
    .blockedNetworks(CidrNetwork.parseList("192.168.100.0/24,2001:db8:bad::/48"));

Order of checks: the global cap, then the blocked list (a match is refused), then the allowed list (if one is set, only a match gets in), then the per-address limits above. CidrNetwork (org.bluezoo.gumdrop.util) parses a single block with its constructor, a comma-separated list with parseList, and tests an address with matches.

Storage quotas

Quotas bound how much storage a user may consume, and in a mail store how many messages. The FTP and IMAP servers enforce them: FTP checks uploads against the quota and offers SITE QUOTA and (to ftp-admin) SITE SETQUOTA, and IMAP implements the QUOTA extension (RFC 9208: GETQUOTA, GETQUOTAROOT, SETQUOTA) and refuses an APPEND that would exceed it.

Both take a QuotaManager (org.bluezoo.gumdrop.quota). The one that ships is RoleBasedQuotaManager, which resolves a user's quota in this order:

  1. a user quota set for that user (SITE SETQUOTA, IMAP SETQUOTA or setUserQuota)
  2. a role quota, from the roles the user holds in the realm; if several apply the most generous wins
  3. the default quota
  4. otherwise unlimited
RoleBasedQuotaManager quotas = new RoleBasedQuotaManager();
quotas.realm(realm);                         // to find out which roles a user holds
quotas.storageDir(Path.of("/var/gumdrop/quota"));
quotas.defaultQuota("100MB");
quotas.addRoleQuota("premium", "10GB");
quotas.addRoleQuota("standard", "1GB", "50000");   // storage limit, message limit
quotas.addRoleQuota("staff", "unlimited");

// FTP
FtpServer ftp = FtpServer.compose()
    .listener(new FtpListener().port(21))
    .realm(realm)
    .sessionProvider(FtpServerSessionProviders.roleBased()
        .realm(realm)
        .rootDirectory(Path.of("/srv/ftp"))
        .quotaManager(quotas))
    .server();

// IMAP
ImapServer imap = ImapServer.compose()
    .listener(new ImapListener().port(143))
    .realm(realm)
    .sessionProvider(ImapServerSessionProviders.mailbox(maildirFactory))
    .quotaManager(quotas)
    .enableQUOTA(true)
    .server();

Sizes are a number with an optional K/KB, M/MB, G/GB or T/TB suffix, or unlimited (or -1). QuotaPolicy.parseSize and formatSize do the conversions.

  • Roles are resolved at login. A server calls QuotaManager.prepare(user, loop, done) once the user has authenticated. The role manager asks the realm which of its configured roles the user holds, without waiting, and then answers every later quota check from memory. A realm that cannot answer leaves the user with the default quota rather than a role quota.
  • Usage is tracked. The server reports bytes and messages added and removed (recordBytesAdded, recordMessageAdded, and so on), and canStore and canStoreMessage answer from the user's Quota. recalculateUsage discards a user's cached figures so the next lookup reloads them.
  • Usage persists in the storage directory (*.usage files, and *.policy for user overrides). Writes happen off the loop and are coalesced, so a burst of uploads for one user causes one pending write rather than one per file. Call loadUsageData() at start-up and saveUsageData() at shutdown.
  • A quota's getSource() (QuotaSource: USER, ROLE, DEFAULT or NONE) says where its limits came from, which IMAP and FTP report to the client.

To enforce quotas some other way, implement QuotaManager; its prepare method has a default that does nothing, which suits a manager that needs no per-user setup.

HTTP security headers

An HttpServer adds X-Frame-Options: SAMEORIGIN and X-Content-Type-Options: nosniff to responses by default, unless the application sets them itself. RFC 6797 HSTS is opt-in and only takes effect on TLS listeners: 

HttpServer http = HttpServer.compose()
    .secureEndpoint(443, tls)
    .addSecurityHeaders(true)                       // the default
    .hsts(HstsPolicy.enabled(31536000L)             // max-age in seconds
        .includeSubDomains(true).preload(false))
    .streamHandler(handler)
    .server();

Security events

Authentication and access decisions feed Gumdrop's telemetry. A realm that cannot answer (an unreachable directory, an introspection timeout) is logged as a warning with the cause, and the connection fails closed. Each connection's session span records authentication outcomes as events: FTP and POP3 add AUTH_SUCCESS and AUTH_FAILURE, SMTP records the mechanism that succeeded, and IMAP records AUTHENTICATED. Quota and rate-limiter housekeeping is logged through the same event logger.
