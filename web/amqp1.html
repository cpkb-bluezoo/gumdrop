Gumdrop AMQP 1.0 Client

← Back to Main Page

This page describes the AMQP 1.0 client in package org.bluezoo.gumdrop.amqp1.client. AMQP 1.0 is a different protocol from AMQP 0-9-1; the two clients share only the four-octet AMQP protocol header prefix. Use this client for brokers that speak AMQP 1.0 natively, such as RabbitMQ 4's AMQP 1.0 listener or ActiveMQ Artemis's amqp:// acceptor. For RabbitMQ's classic 0-9-1 port, see the AMQP 0-9-1 client.

Gumdrop provides a fully asynchronous AMQP 1.0 client built on the same reactor model as HTTP, SMTP, and the other protocol clients: non-blocking I/O, ProtocolHandler callbacks on a SelectorLoop, and push framing via Amqp1FrameParser so partial reads never assume a full frame is available. Messaging uses AMQP 1.0 links (sender and receiver) with link credit, session flow control, and explicit settlement rather than 0-9-1 channels and basic.publish.

Architecture

The recommended entry point is Amqp1Client: it dials the broker, runs the SASL security layer and connection handshake, opens a session, and reconnects with exponential backoff if the connection is lost, re-attaching recorded links on each new session. Lower-level control is available through Amqp1ClientProtocolHandler and a ClientEndpoint.

Key components

  • Amqp1Client - connection facade with recovery and a single recoverable session
  • Amqp1RecoverableSession - stable across reconnects; attachSender / attachReceiver record links for replay
  • Amqp1Sender / Amqp1Receiver - link handles; stable references that move to each new attachment after reconnect
  • Amqp1SenderHandler / Amqp1ReceiverHandler - link lifecycle, credit, and message events
  • Amqp1OutgoingDelivery / Amqp1IncomingDelivery - streaming send and receive with settlement
  • Amqp1RecoveryHandler - onFirstConnect fires once; attach links there
  • Amqp1RecoveryListener - optional connection-lost / reconnecting / recovered / recovery-failed callbacks
  • Amqp1RecoveryPolicy - backoff timing and attempt limits
  • The org.bluezoo.gumdrop.amqp1.codec package - AMQP 1.0 type system, performatives, and message encoding (usable without the client classes)

The connection handshake is expressed as typed states (SASL, open, begin) so illegal call ordering is rejected at compile time. Wire encoding uses push parsers and incremental ByteBuffer feeds throughout.

Basic usage

In the examples below, gumdrop is the Gumdrop instance from Gumdrop.boot(), passed to connect. 

Amqp1Client client = new Amqp1Client("broker.example.com", 5672)
        .credentials("guest", "guest")
        .containerId("my-app");

client.connect(gumdrop, new Amqp1RecoveryHandler() {
    public void onFirstConnect(Amqp1RecoverableSession session) {
        session.attachReceiver("in", "/queues/orders", receiverHandler);
        session.attachSender("out", "/queues/orders", senderHandler);
    }
});

A sender handler holds the link and sends when the broker grants credit: 

Amqp1SenderHandler senderHandler = new Amqp1SenderHandler() {
    public void handleAttached(Amqp1Sender sender, Attach peerAttach) { }

    public void handleCredit(Amqp1Sender sender) {
        // credit is available: sender.send(...) may be called
    }

    public void handleWritable(Amqp1OutgoingDelivery delivery) { }

    public void handleOutcome(Amqp1OutgoingDelivery delivery,
            DeliveryState state, boolean settled) { }

    public void handleDetached(Amqp1Error error, boolean closed) { }
};

Attach links from onFirstConnect (or from a link handler's handleAttached). The sender must wait for Amqp1SenderHandler.handleCredit before calling send; the receiver must call Amqp1Receiver.addCredit in handleAttached (and again after every reconnect) to receive messages.

Threading

The API is single-threaded with respect to each connection: handler callbacks and link operations run on the connection's event loop. Call links only from those callbacks, or submit work with client.execute(Runnable) from any other thread (for example a servlet worker that must publish to the broker).

SelectorLoop affinity

Like other Gumdrop clients, Amqp1Client can be bound to a specific worker SelectorLoop so broker I/O shares the reactor thread with an HTTP request handler or upstream client: 

SelectorLoop loop = endpoint.getSelectorLoop();
Amqp1Client client = new Amqp1Client(loop, "broker.example.com", 5672)
        .credentials("guest", "guest");

If no loop is supplied, the client uses Gumdrop's default selector pool. As with the 0-9-1 client, reconnect backoff uses a small dedicated timer thread (gumdrop-amqp1-recovery) so delays still fire when no connections are active and worker loops may be idle; the reconnect dial itself uses the configured SelectorLoop.

Node addresses

AMQP 1.0 addresses are broker-specific strings passed to attachSender and attachReceiver. The queue must typically exist before a link attaches.

  • RabbitMQ 4 - v2 addresses such as /queues/<name> (URL-encoded queue name). Integration tests declare queues via the management HTTP API before attaching links.
  • ActiveMQ Artemis - commonly queue://<name> or broker-specific paths (see Artemis documentation for the acceptor you use).
  • Tests / mocks - the in-repo MockAmqp1Broker uses queue://<name> addresses.

For full control of source, target, settle modes, and capabilities, pass a copied Attach performative to attachSender(Attach, …) or attachReceiver(Attach, …).

Sending

Small messages fit in one call; large bodies stream without assembling the payload in memory: 

// After handleCredit:
byte[] tag = "msg-1".getBytes(StandardCharsets.UTF_8);
MessageProperties props = new MessageProperties();
props.setSubject("greeting");
sender.send(tag, props, null, ByteBuffer.wrap(body));

// Large payload:
Amqp1OutgoingDelivery d = sender.startDelivery(tag, null, props, null, false);
for (int off = 0; off < body.length; off += 65536) {
    int len = Math.min(65536, body.length - off);
    d.write(ByteBuffer.wrap(body, off, len));
}
d.finish();

If write returns false, the session transfer window is full; continue when handleWritable fires. Unsettled deliveries report outcomes through handleOutcome when the receiver settles them.

Receiving

Amqp1ReceiverHandler extends MessageHandler: a delivery begins with startDelivery, message sections arrive as events (properties, dataChunk, and so on), and endMessage marks completion. data bodies stream in chunks; amqp-value / amqp-sequence sections are decoded whole with a size cap (see MessageParser.DEFAULT_MAX_SECTION_SIZE). Dispose of each delivery with accept(), release(), reject(...), or dispose(state, settled).

A receiver handler therefore implements both the link methods and every MessageHandler method (empty bodies for the sections you do not need). The ones that matter for a data message: 

public void handleAttached(Amqp1Receiver receiver, Attach peerAttach) {
    receiver.addCredit(10);
}

public void startDelivery(Amqp1IncomingDelivery delivery) {
    current = delivery;
}

public void dataChunk(ByteBuffer chunk) {
    // append to application buffer
}

public void endMessage() {
    process();
    current.accept();
    current = null;
}

public void handleAborted(Amqp1IncomingDelivery delivery) {
    // the sender aborted a partly received message: discard what you collected
    current = null;
}

public void handleDetached(Amqp1Error error, boolean closed) { }

TLS connections

Implicit TLS (AMQPS, typically port 5671) is enabled with secure(true) before connecting: 

Amqp1Client client = new Amqp1Client("broker.example.com", 5671)
        .credentials("guest", "guest")
        .secure(true)
        .tls(TlsConfig.keystore(Path.of("/path/to/keystore.p12"), "changeit",
                KeystoreFormat.PKCS12));

A custom trust manager and client credentials go on the TlsConfig passed to tls(). UNIX domain socket constructors (new Amqp1Client("/var/run/broker.sock")) follow the same patterns as other Gumdrop clients. TLS is negotiated at connect time; there is no STARTTLS upgrade on the AMQP 1.0 port.

Authentication

credentials(username, password) selects SASL PLAIN. With no credentials, the client uses ANONYMOUS. Choose a mechanism explicitly with mechanism(...), which accepts PLAIN, ANONYMOUS and EXTERNAL and throws IllegalArgumentException for anything else. EXTERNAL takes the identity from the TLS client certificate, so it needs secure(true) and a keystore holding that certificate; credentials are ignored: 

Amqp1Client client = new Amqp1Client("broker.example.com", 5671)
        .secure(true)
        .tls(TlsConfig.keystore(Path.of("/path/to/client-cert.p12"), "changeit"))
        .mechanism("EXTERNAL");

Other SASL mechanisms are available through the lower-level Amqp1ClientProtocolHandler: its Amqp1SaslHandshake state takes any SaslClientMechanism (see SaslUtils.createClient), optionally with an executor for mechanisms that block. Rejected credentials end recovery permanently, because retrying cannot succeed.

Automatic connection recovery

Amqp1Client reconnects after transport failures or broker closes, using Amqp1RecoveryPolicy (defaults: 1 s initial delay, doubling multiplier, 30 s cap, unlimited attempts, which is withMaxAttempts(0), unless a maximum is set).

  • onFirstConnect runs only once; on later reconnects the client re-attaches every link recorded on the Amqp1RecoverableSession
  • Link handlers receive handleDetached on loss and handleAttached again when the link is restored; receivers must re-grant credit on each attachment
  • Deliveries in flight are not resumed: senders may need to resend for at-least-once semantics; receivers may see duplicates after reconnect
  • Links the broker closed deliberately (detach with closed true) are not re-attached
  • Amqp1RecoveryListener reports lost, reconnecting, recovered, and failed recovery events (onConnectionLost(Exception), onReconnecting(attempt, delayMs), onRecovered(), onRecoveryFailed(Exception)); every method is a default, so implement only the ones you need
  • close() stops further attempts and shuts down the connection
Amqp1Client client = new Amqp1Client("broker.example.com", 5672)
        .credentials("guest", "guest")
        .recoveryPolicy(new Amqp1RecoveryPolicy()
                .withInitialDelayMs(500)
                .withMaxDelayMs(15000)
                .withMaxAttempts(20))
        .recoveryListener(myListener);
