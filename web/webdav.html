Gumdrop File Server & WebDAV

← Back to Main Page

Gumdrop 3 serves static files and WebDAV through an HttpServer composed with a WebDAVRequestHandler (WebDAV is a tradename — use WebDAV, not Webdav, in public API names). It is a complete, production-ready HTTP file server: it serves static files from a filesystem directory with high performance, and optionally provides full WebDAV (RFC 4918) distributed authoring support.

Because the handler runs on the shared HTTP stack, any combination of HTTP/3, HTTP/2, and HTTP/1.1 listeners can be attached to the same HttpServer.

Composition (Gumdrop 3)

HttpServer server = HttpServer.compose()
    .listener(new Http2Listener().port(8080))
    .streamHandler(WebDAVRequestHandler.builder()
        .rootPath(Path.of("/var/www/html"))
        .welcomeFile("index.html")
        .allowWrite(false)
        .webdavEnabled(true)
        .build())
    .server();

See Application composition.

File Server

Features

  • NIO-based transfers - uses Java NIO for efficient file-to-socket data transfer
  • Content type detection - automatic MIME type detection based on file extension
  • Directory listings - configurable welcome file for directory requests
  • HTTP methods - GET, HEAD, and optionally PUT/DELETE for writes
  • Range requests - partial content delivery for large files
  • Conditional requests - ETag and Last-Modified support
  • Path security - prevents directory traversal attacks

Configuration

HttpServer server = HttpServer.compose()
    .listener(new Http2Listener().port(8080))
    .streamHandler(WebDAVRequestHandler.builder()
        .rootPath(Path.of("/var/www/html"))
        .welcomeFile("index.html")
        .allowWrite(false)
        .build())
    .server();

Builder methods:

  • rootPath(Path) - filesystem directory to serve (required)
  • welcomeFile(String) - default file for directory requests (default: index.html)
  • allowWrite(boolean) - enable PUT and DELETE methods (default: false)

Security

The file server validates all paths to ensure they remain within the configured root directory. Symbolic links are resolved to their real paths before access checks. The root path must be a readable directory; if write operations are enabled, the server logs a warning if the directory is not writable.

Performance

File transfers use Java NIO's FileChannel.transferTo() where possible, enabling zero-copy transfers directly from the filesystem to the socket. This minimises memory allocation and CPU usage for large file transfers.

For HTTP/3 and HTTP/2 connections, the file server benefits from stream multiplexing when serving mixed content (HTML, CSS, JavaScript, images).

HTTP/3 Support

To serve files over HTTP/3 as well as HTTP/2 and HTTP/1.1, use secureEndpoint to wire both transports on the same port and shared TLS material: 

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "changeit");

HttpServer server = HttpServer.compose()
    .secureEndpoint(443, tls)
    .streamHandler(WebDAVRequestHandler.builder()
        .rootPath(Path.of("/var/www/html"))
        .build())
    .server();

The service automatically advertises HTTP/3 availability via the Alt-Svc response header on TCP connections.

WebDAV Support

The file server supports WebDAV (RFC 2518) distributed authoring when enabled via the webdavEnabled property. This allows WebDAV clients such as Windows Explorer, macOS Finder, or dedicated clients like Cyberduck to access the file server as a network drive.

Enabling WebDAV

HttpServer server = HttpServer.compose()
    .listener(new Http2Listener().port(8080))
    .streamHandler(WebDAVRequestHandler.builder()
        .rootPath(Path.of("/var/www/dav"))
        .allowWrite(true)
        .webdavEnabled(true)
        .build())
    .server();

When WebDAV is enabled, the server advertises DAV: 1,2 in OPTIONS responses and supports the following additional HTTP methods:

WebDAV Methods

  • PROPFIND - Query properties of resources. Supports allprop, propname, or specific property requests. The Depth header controls recursion (0, 1, or infinity).
  • PROPPATCH - Set or remove dead (custom) properties on resources. Each property operation returns an individual status code (200 on success, 403 for protected live properties). See Dead Properties for storage configuration.
  • MKCOL - Create a new collection (directory). The request must not have a body. The parent directory must exist.
  • COPY - Copy a resource or collection to a new location. Uses the Destination header for the target URL. The Overwrite header controls whether existing resources are replaced (default: true). For collections, Depth controls whether children are copied.
  • MOVE - Move a resource or collection. Semantically equivalent to COPY followed by DELETE. Requires valid lock tokens if resources are locked.
  • LOCK - Lock a resource to prevent concurrent modifications. Supports exclusive and shared write locks. Returns an opaque lock token that must be included in subsequent modifying requests.
  • UNLOCK - Release a lock using its token. The token is passed in the Lock-Token header.

Live Properties

The following live properties are computed from the filesystem and returned by PROPFIND requests:

  • creationdate - file creation time (ISO 8601 format)
  • displayname - filename
  • getcontentlength - file size in bytes (files only)
  • getcontenttype - MIME type
  • getetag - entity tag for conditional requests
  • getlastmodified - last modification time (HTTP date format)
  • lockdiscovery - active locks on the resource
  • resourcetype - empty for files, <collection/> for directories
  • supportedlock - supported lock types (exclusive and shared write locks)

Dead Properties

Dead (custom) properties are arbitrary name/value pairs stored on resources by WebDAV clients via PROPPATCH. Gumdrop persists dead properties using a dual-strategy backend:

  • Extended attributes (xattr) - Primary storage. Properties are stored as filesystem extended attributes with names prefixed user.webdav.. Properties travel with the file on copy/move and are deleted automatically. Requires filesystem xattr support.
  • Sidecar files - Fallback for filesystems without xattr support or when a value exceeds the xattr size limit. Sidecar files are named .webdav_filename and contain XML serialized with the Gonzalez library. Sidecar I/O is fully non-blocking via AsynchronousFileChannel.

Configuration

The dead property storage mode is configurable: 

HttpServer server = HttpServer.compose()
    .listener(new Http2Listener().port(8080))
    .streamHandler(WebDAVRequestHandler.builder()
        .rootPath(Path.of("/var/www/dav"))
        .allowWrite(true)
        .webdavEnabled(true)
        .deadPropertyStorage("auto")
        .build())
    .server();
ValueBehaviour
autoUse xattr when available, fall back to sidecar (default)
xattrExtended attributes only; fails if unsupported
sidecarSidecar files only
noneDead properties disabled (PROPPATCH returns 403)

Content, lock and sidecar roots

A handler has three storage roots, each configured on its own:

RootDefaultShared across servers
Content: rootPaththe path you give no
Locks: lockRootunset: locks are held in memory only when a lock root is set
Sidecars: sidecarRootunset: .webdav_* files beside the resources only when the content tree is shared too

With neither set, one server on a private tree is a complete WebDAV server. When a lock root or a sidecar root is set, every record is keyed by the resource's path relative to that server's content root, so servers that mount the same logical tree at different absolute paths agree. 

WebDAVRequestHandler.builder()
    .rootPath(Path.of("/var/www/dav"))
    .allowWrite(true)
    .webdavEnabled(true)
    .lockRoot(Path.of("/mnt/dav-locks"))
    .sidecarRoot(Path.of("/mnt/dav-props"))
    .build()

Lock root

Locks are files under the lock root, at the resource's relative path: an exclusive file for the exclusive lock and one shared/<token> file per shared lock (each path component is prefixed _ so a resource called exclusive or shared is not mistaken for a record). A lock is granted by creating its record and then checking ancestors for a lock covering the path and descendants for one this lock would cover; on any conflict, including a record another server created at the same moment, the new record is removed and the client gets 423 Locked. If two servers each see the other, both refuse and the clients retry. An expired record is not a lock, and the next grant removes it.

The lock root must be on a file system where creating a file exclusively is atomic and one server's record is visible to the others before they finish the conflict check: a local disk or a typical ReadWriteOnce volume. NFS attribute caching can hide a record, so both servers may grant an exclusive lock; use a coherent file system there, or run WebDAV at one replica.

Sidecar root

With a sidecar root, sidecars (mode sidecar, or auto where extended attributes are unavailable or too small) are written to <sidecar-root>/<relative-path> instead of beside the resource; a collection's own properties are the .webdav_. file in its directory there. Nothing is added to the content tree, which may be read-only, and a content file called .webdav_report.pdf is an ordinary file. COPY and MOVE carry the keys, and DELETE of a collection removes its subtree. Extended attributes and mode none are unchanged. The sidecar root is not the lock root, though both may name the same directory in a small deployment.

Sidecar files are hidden from PROPFIND responses, HTML directory listings, and direct GET requests. They are automatically copied, moved, and deleted alongside their parent resource.

Locking

WebDAV locks prevent conflicting modifications when multiple clients access the same resource. Locks are:

  • In-memory by default - locks are not persisted and are lost on server restart. With a lock root they are files, shared by every server that uses it
  • Thread-safe - lock management is safe for concurrent access
  • Time-limited - locks have a configurable timeout (default: 1 hour, maximum: 1 week)
  • Depth-aware - locks can cover a resource only (depth 0), a collection and its immediate children (depth 1), or an entire subtree (depth infinity)

When a resource is locked, modifying operations (PUT, DELETE, MOVE, PROPPATCH) require a valid lock token in the If or Lock-Token header.

Collection DELETE (RFC 4918 §9.6.1)

DELETE on a collection (directory) recursively deletes all member resources depth-first. If all deletions succeed, 204 No Content is returned. If any individual deletion fails, a 207 Multi-Status response lists the failed resources: 

DELETE /documents/old-project/ HTTP/1.1
Host: example.com

HTTP/1.1 207 Multi-Status
Content-Type: application/xml

<?xml version="1.0" encoding="utf-8"?>
<D:multistatus xmlns:D="DAV:">
  <D:response>
    <D:href>/documents/old-project/locked-file.txt</D:href>
    <D:status>HTTP/1.1 403 Forbidden</D:status>
  </D:response>
</D:multistatus>

If Header (RFC 4918 §10.4)

The If header supports the full grammar defined in RFC 4918 §10.4, including tagged-list and no-tag-list syntax with ETag conditions and Not negation. Multiple lists for the same resource are OR'd; conditions within a list are AND'd. 

// No-tag-list with lock token:
If: (<opaquelocktoken:a1b2c3d4-...>)

// Tagged-list for a specific resource:
If: </documents/file.txt> (<opaquelocktoken:a1b2c3d4-...> ["etag-value"])

// Not condition (lock token must NOT be present):
If: (Not <opaquelocktoken:old-token>)

// Multiple conditions (OR'd):
If: (<token-a>) (<token-b>)

Protocol Examples

PROPFIND Request

PROPFIND /documents/ HTTP/1.1
Host: example.com
Depth: 1
Content-Type: application/xml

<?xml version="1.0" encoding="utf-8"?>
<propfind xmlns="DAV:">
  <prop>
    <displayname/>
    <getcontentlength/>
    <getlastmodified/>
  </prop>
</propfind>

Response (207 Multi-Status): 

<?xml version="1.0" encoding="utf-8"?>
<D:multistatus xmlns:D="DAV:">
  <D:response>
    <D:href>/documents/</D:href>
    <D:propstat>
      <D:prop>
        <D:displayname>documents</D:displayname>
      </D:prop>
      <D:status>HTTP/1.1 200 OK</D:status>
    </D:propstat>
  </D:response>
  <D:response>
    <D:href>/documents/report.pdf</D:href>
    <D:propstat>
      <D:prop>
        <D:displayname>report.pdf</D:displayname>
        <D:getcontentlength>245678</D:getcontentlength>
        <D:getlastmodified>Tue, 06 Jan 2026 12:00:00 GMT</D:getlastmodified>
      </D:prop>
      <D:status>HTTP/1.1 200 OK</D:status>
    </D:propstat>
  </D:response>
</D:multistatus>

LOCK Request

LOCK /documents/report.pdf HTTP/1.1
Host: example.com
Timeout: Second-3600
Content-Type: application/xml

<?xml version="1.0" encoding="utf-8"?>
<lockinfo xmlns="DAV:">
  <lockscope><exclusive/></lockscope>
  <locktype><write/></locktype>
  <owner>user@example.com</owner>
</lockinfo>

Response includes the lock token: 

HTTP/1.1 200 OK
Lock-Token: <opaquelocktoken:a1b2c3d4-e5f6-7890-abcd-ef1234567890>
Content-Type: application/xml

<?xml version="1.0" encoding="utf-8"?>
<D:prop xmlns:D="DAV:">
  <D:lockdiscovery>
    <D:activelock>
      <D:locktype><D:write/></D:locktype>
      <D:lockscope><D:exclusive/></D:lockscope>
      <D:depth>infinity</D:depth>
      <D:owner>user@example.com</D:owner>
      <D:timeout>Second-3600</D:timeout>
      <D:locktoken>
        <D:href>opaquelocktoken:a1b2c3d4-e5f6-7890-abcd-ef1234567890</D:href>
      </D:locktoken>
    </D:activelock>
  </D:lockdiscovery>
</D:prop>
