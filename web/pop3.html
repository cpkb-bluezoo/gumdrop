Gumdrop POP3 Server

← Back to Main Page

Gumdrop provides a complete POP3 server implementation following RFC 1939 with modern extensions. POP3 (Post Office Protocol version 3) provides simple, download-oriented mailbox access - clients retrieve messages and optionally delete them from the server. Like all Gumdrop protocol implementations, the POP3 server uses the event-driven, non-blocking architecture.

Protocol Support

The POP3 server implements the base protocol as defined in RFC 1939 with extensions from RFC 2449 (POP3 Extension Mechanism) and RFC 5034 (SASL Authentication).

Protocol States

POP3 sessions progress through three states:

  • AUTHORIZATION - initial state; client must authenticate using USER/PASS, APOP, or AUTH with a SASL mechanism
  • TRANSACTION - authenticated; client can retrieve messages, mark deletions, and query mailbox status
  • UPDATE - after QUIT; server commits deletions and releases the mailbox lock

Required Commands (RFC 1939)

  • USER/PASS - basic username/password authentication
  • STAT - returns message count and total size
  • LIST - lists messages with their sizes
  • RETR - retrieves a complete message
  • DELE - marks a message for deletion
  • NOOP - keeps connection alive
  • RSET - unmarks all deletions
  • QUIT - ends session, commits deletions

Optional Commands (RFC 1939)

  • APOP - challenge-response authentication (MD5-based)
  • TOP - retrieves headers and first N lines of body
  • UIDL - returns unique identifiers for messages

Extension commands

  • CAPA (RFC 2449) - lists the server's capabilities
  • STLS (RFC 2595) - upgrades the connection to TLS
  • AUTH (RFC 5034) - SASL authentication
  • UTF8 (RFC 6816) - switches the session to UTF-8 mode

Extensions

CAPA (RFC 2449)

The CAPA command allows clients to discover server capabilities. The server responds with a list of supported extensions. What it lists depends on the configuration: SASL names the mechanisms the realm supports (those that require TLS only once the connection is secure), APOP appears when APOP is enabled, STLS only on a cleartext connection with TLS configured, and PIPELINING only when enabled. 

C: CAPA
S: +OK Capability list follows
S: USER
S: UIDL
S: TOP
S: SASL PLAIN LOGIN CRAM-MD5 SCRAM-SHA-256
S: APOP
S: STLS
S: UTF8
S: RESP-CODES
S: AUTH-RESP-CODE
S: EXPIRE NEVER
S: LOGIN-DELAY 5
S: IMPLEMENTATION gumdrop
S: .

STLS (RFC 2595)

Upgrades a cleartext connection to TLS. After successful STLS, the client should re-issue CAPA to discover post-TLS capabilities (authentication mechanisms may change). 

C: STLS
S: +OK Begin TLS negotiation
(TLS handshake)
C: CAPA
...

AUTH (RFC 5034)

SASL authentication mechanism support. The server advertises available mechanisms in CAPA response. See Authentication for supported mechanisms.

UTF8 (RFC 6816)

Enables UTF-8 mode for international mailbox content. When enabled, message headers and bodies may contain UTF-8 encoded text. 

C: UTF8
S: +OK UTF-8 mode enabled

PIPELINING (RFC 2449)

When enabled with enablePipelining(true) (off by default), clients can send multiple commands without waiting for responses. This reduces round-trip latency for batch operations.

RESP-CODES (RFC 2449 section 8)

The server includes extended response codes in -ERR replies to help clients provide meaningful error messages. Supported codes:

  • [AUTH] — authentication failures (wrong password, bad credentials, unsupported mechanism)
  • [SYS/TEMP] — temporary server errors (mailbox I/O, timeouts, connection issues)
  • [SYS/PERM] — permanent configuration errors (auth or mailbox not configured)

AUTH-RESP-CODE (RFC 3206)

Extends RESP-CODES with authentication-specific [AUTH] response codes. All authentication failure -ERR replies include the [AUTH] code, allowing clients to distinguish credential errors from server-side failures.

EXPIRE (RFC 2449 section 6.5)

Declares the message retention policy. Configured via expireDays(int) on Pop3Listener: 0 means messages may be expired immediately, a positive value is the minimum retention in days, and Integer.MAX_VALUE advertises EXPIRE NEVER. Set to -1 to suppress the capability.

LOGIN-DELAY (RFC 2449 section 6.6)

Advertises the minimum delay between authentication attempts. When loginDelayMs is greater than zero, the server advertises LOGIN-DELAY <seconds> so clients can avoid premature retries.

Authentication

Authentication uses Gumdrop's centralised Realm, shared with IMAP, SMTP, and other servers; see Using a realm and pass it with realm(...). Multiple authentication methods are supported.

Basic Authentication (USER/PASS)

The simplest method - the client sends its username and password in cleartext. Should only be used over TLS. 

C: USER alice
S: +OK User accepted
C: PASS secret
S: +OK Mailbox locked and ready

APOP (RFC 1939)

Challenge-response authentication using MD5. The server includes a unique timestamp in its greeting; the client responds with MD5(timestamp + password). The password is never transmitted. 

S: +OK POP3 server ready <1896.697170952@example.com>
C: APOP alice c4c9334bac560ecc979e58001b3e22fb
S: +OK Mailbox locked and ready

The AUTH command supports multiple SASL mechanisms:

LOGIN-Legacy base64 username/password; requires TLS
CRAM-MD5RFC 2195HMAC-MD5 challenge-response
DIGEST-MD5RFC 2831HTTP Digest-style authentication
SCRAM-SHA-256RFC 7677Salted challenge-response; recommended

SCRAM-SHA-256 is recommended as it provides mutual authentication and never transmits the password. The realm can store only derived keys without keeping plaintext passwords.

Authentication Example (SCRAM-SHA-256)

C: AUTH SCRAM-SHA-256
S: + (server first message, base64)
C: (client first message, base64)
S: + (server final message, base64)
C: (client final message, base64)
S: +OK Authentication successful

Handlers

The protocol work (CAPA, NOOP, STLS, the USER/PASS, APOP and AUTH exchanges) is handled for you. Your code decides policy through a staged handler, in the same style as the SMTP and IMAP servers. A server is assembled with Pop3Server.compose(): 

Pop3Server server = Pop3Server.compose()
        .listener(new Pop3Listener().port(110))
        .sessionProvider(Pop3ServerSessionProviders.mailbox(mailboxFactory))
        .realm(realm)
        .enableAPOP(true)
        .server();

Gumdrop gumdrop = Gumdrop.boot();
gumdrop.addServer(server);
gumdrop.join();

Pop3ServerSessionProviders.mailbox(factory) is the stock provider: it serves each authenticated user's INBOX from a MailboxFactory and accepts every request. A complete, compiled example is in examples/pop3-server/POP3Example.java. To add policy, supply a provider that returns your own handler.

Handler interfaces

  • ClientConnected - connected(ConnectedState, Endpoint) accepts the connection with a greeting (acceptConnection, or acceptConnectionWithApop to offer APOP) or rejects it; disconnected() is called when it closes
  • AuthorizationHandler - authenticate(AuthenticateState, Principal, MailboxFactory) is called once the client has proved its identity; proceed lets the protocol open the mailbox, reject refuses the login
  • TransactionHandler - mailboxStatus (STAT), list, retrieveMessage, markDeleted, reset, top, uidl and quit, each with the open Mailbox and the command's arguments

Each method receives a state object for that command. A handler lets a command through with proceed where there is one, or answers it itself, and refuses it with error(message, handler) or a more specific method such as noSuchMessage. The handler passed in receives the next command. A handler may keep the state and answer later, but the answer must be made on the connection's SelectorLoop thread.

DefaultPOP3Handler accepts everything, so a handler usually extends it and overrides the commands it wants to police. For example, to keep every message on the server by refusing DELE: 

public class KeepMessagesHandler extends DefaultPOP3Handler {

    public KeepMessagesHandler() {
        super("Mail server ready");
    }

    @Override
    public void markDeleted(MarkDeletedState state, Mailbox mailbox,
            int messageNumber) {
        state.error("Messages are kept on the server", this);
    }
}

Pop3ServerSessionProvider provider = new Pop3ServerSessionProvider() {
    @Override
    public ClientConnected openSession(TcpListener listener) {
        ((Pop3Listener) listener).mailboxFactory(mailboxFactory);
        return new KeepMessagesHandler();
    }
};

Mailbox Integration

The POP3 server accesses mail storage through the Mailbox API. A MailboxFactory provides MailboxStore instances for authenticated users.

Store lifecycle

  1. User authenticates successfully and your handler's authenticate method calls proceed
  2. The protocol creates the user's MailboxStore from the factory, opens it, and opens the user's INBOX, off the I/O thread
  3. Client retrieves messages, marks deletions
  4. On QUIT, the deletions are committed (the mailbox is expunged)
  5. The store is closed

Mailbox locking

POP3 expects exclusive access to the mailbox during a session. How that is achieved is up to the mailbox format: an mbox mailbox is held under a file lock for the session, and a second session on the same file waits for the first to finish, whereas Maildir has no whole-mailbox lock. See the Mailbox API documentation.

Message Identifiers

The UIDL command returns unique identifiers for each message. These identifiers are persistent across sessions, allowing clients to track which messages have been downloaded.

Configuration

Mail servers are configured in Java. The composer holds the settings shared by every listener, and each Pop3Listener holds its own transport settings and may override the shared ones.

Pop3Server.compose() settings

  • listener(Pop3Listener) - add a listener; at least one is required
  • sessionProvider(Pop3ServerSessionProvider) - the handler factory
  • realm(Realm) - realm for authentication
  • enableAPOP(boolean) - enable APOP authentication (default: true)
  • enableUTF8(boolean) - enable UTF-8 support (default: true)
  • enablePipelining(boolean) - enable command pipelining (default: false)
  • loginDelayMs(long) - minimum delay between authentication attempts after a failure, in milliseconds (default: 0); helps mitigate brute-force attacks
  • transactionTimeoutMs(long) - session timeout in milliseconds (default: 600000 / 10 minutes); RFC 1939 requires at least 10 minutes

Pop3Listener settings

  • port(int) - listening port (default: 110, or 995 when secure)
  • bindWildcard() and addresses(InetAddress...) - where to bind
  • secure(boolean) - implicit TLS (POP3S)
  • tls(TlsConfig) - certificate and key; also enables STLS
  • maxConnections(int) and maxConnectionsPerIP(int) - connection caps
  • rateLimit(String), maxAuthFailures(int), authLockoutTimeMs(long) - abuse protection
  • allowedNetworks and blockedNetworks - CIDR allow and block lists
  • idleTimeoutMs, readTimeoutMs, connectionTimeoutMs - timeouts
  • configureGSSAPI(Path keytab, String principal) - Kerberos for AUTH GSSAPI
  • expireDays(int) - message retention policy advertised in CAPA: 0 or more for days, Integer.MAX_VALUE for NEVER, -1 to suppress (default: -1); set on the listener only
  • The composer's enableAPOP, enableUTF8, enablePipelining, loginDelayMs and transactionTimeoutMs, as per-listener overrides

Example configuration

POP3 with STLS on port 110 and POP3S on port 995, sharing one realm and an mbox store: 

TlsConfig tls = TlsConfig.pem(Paths.get("cert.pem"), Paths.get("key.pem"));
MailboxFactory mbox = new MboxMailboxFactory(Paths.get("/var/mail"));

Pop3Server server = Pop3Server.compose()
        .listener(new Pop3Listener().port(110).tls(tls))
        .listener(new Pop3Listener().port(995).secure(true).tls(tls))
        .sessionProvider(Pop3ServerSessionProviders.mailbox(mbox))
        .realm(realm)
        .enableAPOP(true)
        .loginDelayMs(3000)
        .server();

Gumdrop gumdrop = Gumdrop.boot();
gumdrop.addServer(server);
gumdrop.join();

Security

Transport Security

  • POP3S (port 995) - implicit TLS; connection is encrypted from the start
  • STLS (port 110) - upgrade cleartext connection to TLS

RFC 8314 recommends implicit TLS (port 995) over STLS for new deployments. STLS remains available for compatibility with older clients.

Credential Protection

  • APOP - password never transmitted; MD5(timestamp + password)
  • CRAM-MD5 - HMAC-MD5 challenge-response
  • SCRAM-SHA-256 - mutual authentication with derived keys

USER/PASS and AUTH PLAIN transmit credentials in cleartext and should only be used over TLS. The server does not offer the SASL mechanisms that require TLS (PLAIN, LOGIN, OAUTHBEARER, EXTERNAL) until the connection is secure.

Brute-Force Mitigation

The loginDelayMs setting introduces a delay after failed authentication attempts:

  • Set to 3000 (3 seconds) to slow down automated attacks
  • Applies per connection: after a failure, the next attempt on that connection is held back until the delay has passed
  • Does not affect successful authentications

Session Timeout

The transactionTimeoutMs setting closes idle connections:

  • Default 10 minutes per RFC 1939 recommendation
  • Prevents resource exhaustion from abandoned connections
  • Timer resets on each client command
