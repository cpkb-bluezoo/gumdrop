Gumdrop provides a complete IMAP server implementation following RFC 9051 (IMAP4rev2). Like all Gumdrop protocol implementations, the IMAP server uses the event-driven, non-blocking architecture that enables high concurrency with minimal resource consumption.

Protocol Support

The IMAP server implements the IMAP4rev2 protocol as defined in RFC 9051, the modernised successor to RFC 3501. IMAP4rev2 incorporates lessons learned from two decades of IMAP deployment and mandates several previously optional features.

Protocol States

IMAP sessions progress through four states:

  • NOT_AUTHENTICATED - initial state; authentication required before accessing mailboxes
  • AUTHENTICATED - logged in; can list, create, delete, and select mailboxes
  • SELECTED - mailbox selected; can access messages, flags, and perform searches
  • LOGOUT - connection closing

Supported Commands

All standard IMAP4rev2 commands are implemented, with the extension commands listed below:

  • Any state: CAPABILITY, NOOP, LOGOUT, ID. When a mailbox is selected, NOOP returns untagged * N EXISTS responses if the message count has changed since the last check.
  • NOT_AUTHENTICATED: STARTTLS, AUTHENTICATE, LOGIN
  • AUTHENTICATED: SELECT, EXAMINE, CREATE, DELETE, RENAME, SUBSCRIBE, UNSUBSCRIBE, LIST, LSUB, STATUS, APPEND, NAMESPACE, ENABLE, IDLE, COMPRESS, NOTIFY, GETMETADATA, SETMETADATA, GETQUOTA, GETQUOTAROOT, SETQUOTA
  • SELECTED: CHECK, CLOSE, UNSELECT, EXPUNGE, SEARCH, SORT, THREAD, FETCH, STORE, COPY, MOVE, UID

Extensions

The server supports several IMAP extensions that enhance functionality:

IDLE (RFC 2177)

Push notifications for mailbox changes. When a client issues the IDLE command, the server holds the connection open and sends unsolicited responses when new messages arrive or flags change. This eliminates the need for polling. 

C: A001 IDLE
S: + idling
... (server sends updates as mailbox changes)
S: * 4 EXISTS
C: DONE
S: A001 OK IDLE terminated

NAMESPACE (RFC 2342)

Exposes the mailbox hierarchy structure, including personal, shared, and other-users' namespaces when configured. The MailboxStore can return shared and other-users namespace prefixes via getSharedNamespace() and getOtherUsersNamespace(). Helps clients discover the hierarchy delimiter and namespace prefixes.

MOVE (RFC 6851)

Atomic move operation combining COPY and STORE \Deleted + EXPUNGE. More efficient than the three-command sequence and avoids race conditions.

QUOTA (RFC 9208)

Storage quota reporting. Clients can query quota roots and current usage, enabling display of storage limits in mail client interfaces.

Capabilities

The server advertises these capabilities in its greeting and in reply to CAPABILITY. Those marked with a toggle can be switched off on the listener (see Configuration); all the toggles default to on.

  • IDLE (RFC 2177, enableIDLE), NAMESPACE (RFC 2342, enableNAMESPACE), QUOTA (RFC 9208, enableQUOTA) and MOVE (RFC 6851, enableMOVE)
  • CONDSTORE and QRESYNC (RFC 7162) - modification sequences and quick resynchronisation (enableCONDSTORE, enableQRESYNC)
  • COMPRESS=DEFLATE (RFC 4978, enableCOMPRESS) - advertised until compression is switched on
  • UTF8=ACCEPT (RFC 6855, enableUTF8ACCEPT)
  • SORT (RFC 5256) with THREAD=ORDEREDSUBJECT and THREAD=REFERENCES (enableSORT)
  • OBJECTID (RFC 8474, enableOBJECTID)
  • NOTIFY (RFC 5465, enableNOTIFY) and METADATA (RFC 5464, enableMETADATA)
  • BINARY (RFC 3516) and PREVIEW (RFC 8970)
  • UIDPLUS - extended UID responses for APPEND, COPY, MOVE
  • CHILDREN - mailbox \HasChildren and \HasNoChildren attributes
  • UNSELECT - unselect mailbox without expunge
  • LIST-EXTENDED and LIST-STATUS - enhanced LIST with selection options and STATUS data
  • STATUS=SIZE (RFC 8438)
  • LITERAL- (RFC 7888) - non-synchronising literals up to 4096 bytes for reduced round-trips on APPEND
  • ID (RFC 2971) - server identification; configurable via serverIdFields()

Both IMAP4rev1 and IMAP4rev2 are advertised, so clients that look only for IMAP4rev1 will connect. The commands the server implements are those of IMAP4rev2 (RFC 9051).

Authentication

Authentication uses Gumdrop's centralised Realm interface, which provides a unified credential store across all servers. The IMAP server supports multiple SASL mechanisms.

Pass the realm to the composer with realm(...). See Using a realm and BasicRealm for how to build one.

SASL Mechanisms

The server advertises the mechanisms the realm supports in the CAPABILITY response. Mechanisms marked as requiring TLS are advertised only on a secure connection:

  • PLAIN - simple username/password (RFC 4616); requires TLS
  • LOGIN - legacy base64-encoded username/password; requires TLS
  • CRAM-MD5 - challenge-response; password not transmitted
  • DIGEST-MD5 - digest authentication (RFC 2831)
  • SCRAM-SHA-256 - salted challenge-response (RFC 7677); recommended
  • GSSAPI - Kerberos V5 authentication (RFC 4752); keytab-based
  • OAUTHBEARER - OAuth 2.0 bearer tokens (RFC 7628); requires TLS
  • EXTERNAL - TLS client certificate (RFC 4422)

SCRAM-SHA-256 is the recommended mechanism as it provides mutual authentication and does not transmit the password in any form. The realm can store only the derived keys (StoredKey, ServerKey) without keeping the plaintext password.

LOGINDISABLED

By default, the LOGIN command is disabled over unencrypted connections. The server advertises LOGINDISABLED in capabilities until TLS is established via STARTTLS or implicit IMAPS. This prevents credential exposure over plaintext connections. allowPlaintextLogin(true) lifts the restriction for testing.

Handlers

The protocol work (tags, CAPABILITY, NOOP, LOGOUT, STARTTLS, IDLE and the LOGIN and AUTHENTICATE exchanges) is handled for you. Your code decides policy through a staged handler, in the same style as the SMTP server. A server is assembled with ImapServer.compose(), which takes listeners and a session provider: a factory that returns a fresh ClientConnected handler for each connection. 

ImapServer server = ImapServer.compose()
        .listener(new ImapListener().port(143))
        .sessionProvider(ImapServerSessionProviders.mailbox(mailboxFactory))
        .realm(realm)
        .server();

Gumdrop gumdrop = Gumdrop.boot();
gumdrop.addServer(server);
gumdrop.join();

ImapServerSessionProviders.mailbox(factory) is the stock provider: it serves each authenticated user's mailboxes from a MailboxFactory and accepts every request. To add policy, supply your own provider that returns a handler.

Handler interfaces

  • ClientConnected - connected(ConnectedState, Endpoint) accepts the connection with a greeting, or rejects it; disconnected() is called when it closes
  • NotAuthenticatedHandler - authenticate(AuthenticateState, Principal, MailboxFactory) is called once the client has proved its identity; accept or reject the login
  • AuthenticatedHandler - SELECT, EXAMINE, CREATE, DELETE, RENAME, SUBSCRIBE, UNSUBSCRIBE, LIST, LSUB, STATUS, APPEND and the quota commands, each with the MailboxStore and the command's arguments
  • SelectedHandler - the above plus CLOSE, UNSELECT, EXPUNGE, STORE, COPY, MOVE, FETCH and SEARCH, with the selected Mailbox

Each method receives a state object for that command. Calling proceed(handler) authorises it and lets the protocol do the work, and other methods refuse it with the appropriate response, for example DeleteState.cannotDelete(message, handler), SelectState.accessDenied(message, handler) or AuthenticatedStatusState.deny(message, handler). The handler passed in is the one that receives the next command. As with SMTP, a handler may keep the state and answer later; the answer must be made on the connection's SelectorLoop thread.

DefaultIMAPHandler accepts everything, so a handler usually extends it and overrides the commands it wants to police. The compiled example in examples/imap-server/ImapExample.java logs every SELECT and refuses to delete INBOX: 

private static final class PolicyHandler extends DefaultIMAPHandler {

    @Override
    public void select(SelectState state, MailboxStore store, String mailboxName) {
        System.out.println("SELECT " + mailboxName);
        state.proceed(this);
    }

    @Override
    public void delete(DeleteState state, MailboxStore store, String mailboxName) {
        if ("INBOX".equalsIgnoreCase(mailboxName)) {
            state.cannotDelete("INBOX cannot be deleted", this);
        } else {
            state.proceed(this);
        }
    }
}

ImapServerSessionProvider provider = new ImapServerSessionProvider() {
    @Override
    public ClientConnected openSession(TcpListener listener) {
        ((ImapListener) listener).mailboxFactory(mailboxFactory);
        return new PolicyHandler();
    }
};

A handler can also take over a command completely. For example, SelectState.selectOk(...) and AppendState.readyForData(...) let it serve a mailbox from its own storage instead of the MailboxStore.

Mailbox Integration

The IMAP server accesses mail storage through the Mailbox API. A MailboxFactory is configured to provide MailboxStore instances for authenticated users.

Store lifecycle

When a user authenticates successfully:

  1. Your handler's authenticate method is called and calls proceed (or accept with a store of its own)
  2. The protocol creates and opens the user's MailboxStore from the MailboxFactory, off the I/O thread
  3. Each mailbox command is passed to your handler with that store
  4. On logout or disconnect, the store is closed

Available Implementations

  • MboxMailboxFactory - Unix mbox file format
  • MaildirMailboxFactory - Maildir++ directory format (recommended for IMAP due to concurrent access support)

See the Mailbox API documentation for details on each format's characteristics and configuration.

Configuration

Mail servers are configured in Java. The composer holds the settings shared by every listener, and each ImapListener holds its own transport settings and may override the shared ones.

ImapServer.compose() settings

  • listener(ImapListener) - add a listener; at least one is required
  • sessionProvider(ImapServerSessionProvider) - the handler factory
  • realm(Realm) - realm for authentication
  • quotaManager(QuotaManager) - quotas (see Quota Management)
  • loginTimeoutMs(long) - maximum time for authentication (default: 60000)
  • commandTimeoutMs(long) - maximum time per command (default: 300000)
  • maxLineLength(int) - maximum command line length (default: 8192)
  • maxLiteralSize(int) - maximum literal size for APPEND (default: 25MB)
  • allowPlaintextLogin(boolean) - allow LOGIN over a non-TLS connection (default: false; testing only)
  • enableIDLE, enableNAMESPACE, enableQUOTA, enableMOVE, enableCOMPRESS, enableUTF8ACCEPT, enableSORT - extension toggles (default: true)

ImapListener settings

  • port(int) - listening port (default: 143, or 993 when secure)
  • bindWildcard() and addresses(InetAddress...) - where to bind
  • secure(boolean) - implicit TLS (IMAPS)
  • tls(TlsConfig) - certificate and key; also enables STARTTLS
  • maxConnections(int) and maxConnectionsPerIP(int) - connection caps
  • rateLimit(String), maxAuthFailures(int), authLockoutTimeMs(long) - abuse protection
  • allowedNetworks and blockedNetworks - CIDR allow and block lists
  • idleTimeoutMs(long) - connection idle timeout (default: 300000 / 5 minutes)
  • readTimeoutMs, connectionTimeoutMs - further timeouts
  • configureGSSAPI(Path keytab, String principal) - Kerberos for AUTH=GSSAPI
  • serverIdFields(Map) - key/value pairs returned by the ID command (RFC 2971). Default: name=gumdrop, version from package manifest.
  • The extension toggles above, plus enableCONDSTORE, enableQRESYNC, enableOBJECTID, enableNOTIFY and enableMETADATA, which are set on the listener only

Example configuration

Cleartext IMAP with STARTTLS on port 143 and IMAPS on port 993, sharing one realm and a Maildir store: 

TlsConfig tls = TlsConfig.pem(Paths.get("cert.pem"), Paths.get("key.pem"));
MailboxFactory maildir = new MaildirMailboxFactory(Paths.get("/var/mail"));

ImapServer server = ImapServer.compose()
        .listener(new ImapListener().port(143).tls(tls))
        .listener(new ImapListener().port(993).secure(true).tls(tls))
        .sessionProvider(ImapServerSessionProviders.mailbox(maildir))
        .realm(realm)
        .server();

Gumdrop gumdrop = Gumdrop.boot();
gumdrop.addServer(server);
gumdrop.join();

Security

Transport Security

  • IMAPS (port 993) - implicit TLS; connection is encrypted from the start
  • STARTTLS (port 143) - upgrade cleartext connection to TLS

TLS is required before credentials are transmitted. The server advertises LOGINDISABLED until encryption is established.

Credential Protection

Challenge-response mechanisms (CRAM-MD5, DIGEST-MD5, SCRAM-SHA-256) never transmit the password, even over cleartext. SCRAM additionally protects against server compromise by using derived keys.

Literal Size Limits

The maxLiteralSize setting (default 25MB) prevents denial-of-service attacks via oversized APPEND commands. The default 25MB limit can be adjusted based on expected message sizes.

Connection Limits

Timeouts prevent resource exhaustion from idle or slow connections (idleTimeoutMs, loginTimeoutMs and commandTimeoutMs). RFC 9051 asks servers not to drop an authenticated session sooner than 30 minutes, so raise idleTimeoutMs for listeners that serve long-lived IDLE sessions. The listener also enforces maxConnections, maxConnectionsPerIP, rateLimit and an authentication lockout.

Quota Management

The IMAP server supports storage quotas via the QUOTA extension (RFC 9208). Users can query their quota status, and administrators can set per-user storage limits.

QUOTA Commands

Three commands provide quota functionality:

  • GETQUOTAROOT - returns quota roots for a mailbox
  • GETQUOTA - returns quota limits and usage for a quota root
  • SETQUOTA - sets quota limits (users in the admin role only)
C: A001 GETQUOTAROOT INBOX
S: * QUOTAROOT INBOX user/alice
S: * QUOTA user/alice (STORAGE 52428 102400)
S: A001 OK GETQUOTAROOT completed

C: A002 GETQUOTA user/alice
S: * QUOTA user/alice (STORAGE 52428 102400)
S: A002 OK GETQUOTA completed

The STORAGE resource reports usage and limits in kilobytes.

QuotaManager Configuration

Quotas are enforced through a QuotaManager configured on the composer (or a listener). The RoleBasedQuotaManager supports user-specific overrides, role-based policies, and a system default: 

RoleBasedQuotaManager mailQuota = new RoleBasedQuotaManager();
mailQuota.realm(mailRealm);
mailQuota.storageDir(Path.of("/var/mail/quota"));
mailQuota.defaultQuota("100MB");
mailQuota.addRoleQuota("premium", "10GB");
mailQuota.addRoleQuota("enterprise", "unlimited");

ImapServer imap = ImapServer.compose()
    .listener(new ImapListener().port(143))
    .realm(mailRealm)
    .sessionProvider(ImapServerSessionProviders.mailbox(maildirFactory))
    .quotaManager(mailQuota)
    .enableQUOTA(true)
    .server();

See Security - Storage quotas for how quotas are resolved, persisted and enforced.

Quota Policy Hierarchy

When determining a user's quota, the manager checks in order:

  1. User-specific quota - set via SETQUOTA or direct configuration
  2. Role-based quota - from the user's roles; the most generous wins
  3. System default - fallback for users without role quotas

Sizes can be specified with standard suffixes: KB, MB, GB, TB. Use unlimited or -1 for no limit.

APPEND Quota Enforcement

When a client issues an APPEND command, the server checks whether adding the message would exceed the user's quota. If so, the server returns an [OVERQUOTA] response code: 

C: A003 APPEND INBOX {1048576}
S: A003 NO [OVERQUOTA] Quota exceeded

IMAP Client

Gumdrop includes a fully asynchronous IMAP client supporting IMAPS, STARTTLS, and the full range of RFC 9051 commands. The client uses a callback-driven design with typed reply handler interfaces for each command category. Like the SMTP client, it is driven by stages: you pass a RemoteGreeting to ImapClient.connect(gumdrop, handler), and each stage hands you an interface offering only the commands that are legal at that point, together with a reply handler for the answer.

  • ClientNotAuthenticatedState - capability, login, authenticate, authenticateWithAccessToken, starttls, logout
  • ClientAuthenticatedState - select, examine, create, delete, rename, list, status, append, idle, namespace, enable, compress, getQuota, and others
  • ClientSelectedState - fetch, store, search, sort, thread, copy, move, expunge, close, with UID variants

A minimal session that connects over IMAPS, logs in, selects INBOX and logs out. In real code you would implement the reply handlers as named classes rather than nesting them; the nesting here shows the order of the stages: 

ImapClient client = new ImapClient("imap.example.com", 993).secure(true);
client.connect(gumdrop, new RemoteGreeting() {

    public void handleGreeting(ClientNotAuthenticatedState auth,
            String greeting, List<String> preAuthCapabilities) {
        auth.login("alice", "secret", new LoginReplyHandler() {
            public void handleAuthenticated(ClientAuthenticatedState session,
                    List<String> capabilities) {
                session.select("INBOX", new SelectReplyHandler() {
                    public void handleSelected(ClientSelectedState selected,
                            MailboxInfo info) {
                        System.out.println(info.getExists() + " messages");
                        selected.logout();
                    }
                    public void handleFailed(ClientAuthenticatedState session,
                            String message) {
                        session.logout();
                    }
                    public void handleServiceClosing(String message) { }
                });
            }
            public void handleAuthFailed(ClientNotAuthenticatedState auth,
                    String message) {
                auth.logout();
            }
            public void handleServiceClosing(String message) { }
        });
    }

    public void handlePreAuthenticated(ClientAuthenticatedState auth,
            String greeting) { }
    public void handleServiceUnavailable(String message) { }

    // ClientHandler lifecycle
    public void onConnected(Endpoint endpoint) { }
    public void onSecurityEstablished(SecurityInfo info) { }
    public void onError(Exception cause) { cause.printStackTrace(); }
    public void onDisconnected() { }
});

To upgrade a cleartext connection instead, call auth.starttls(...) in handleGreeting; on success the reply handler receives a ClientPostStarttls from which to log in. Message bodies from fetch arrive in pieces through the handleFetchLiteralBegin, handleFetchLiteralContent and handleFetchLiteralEnd methods of FetchReplyHandler, so a large message is never held in memory, and wantsPause() lets the handler apply back-pressure. ImapClient.tls(TlsConfig) configures the outbound TLS, including trust and certificate pinning.

Client QUOTA Support (RFC 9208)

The client provides getQuota() and getQuotaRoot() commands via the ClientAuthenticatedState interface. Responses are delivered through the QuotaReplyHandler callback:

  • handleQuota(quotaRoot, resourceName, usage, limit) — called for each resource triplet in a QUOTA response
  • handleQuotaRoot(mailbox, quotaRoots) — called for QUOTAROOT untagged responses
  • handleQuotaComplete() / handleQuotaError(msg) — completion callbacks
