Gumdrop TLS & DTLS

← Back to Main Page

Gumdrop ships a complete in-tree transport-security stack in org.bluezoo.gumdrop.crypto and org.bluezoo.gumdrop.tls. TCP listeners, UDP listeners, and QUIC all use this implementation — there is no dependency on JSSE SSLEngine or third-party TLS libraries on the data path. JCA is used only for primitive operations (signatures, key agreement, AEAD via Cipher, PKIX path validation).

This page describes scope, deliberate design choices, security practices, configuration for protocol-handler authors, and pointers to RFC conformance matrices. For keystore setup, certificate pinning, IAM, and rate limiting, see Security.

Architecture

The stack splits cleanly into cryptography and protocol state:

  • org.bluezoo.gumdrop.crypto — HKDF, TLS 1.2 PRF, ECDHE key exchange, named groups (including RFC 10024 hybrid post-quantum groups on Java 25+), signature schemes, and PKIX certificate verification helpers.
  • org.bluezoo.gumdrop.tls — handshake state machines (HandshakeEngine for TLS 1.3, Tls12HandshakeEngine for TLS 1.2), record layers for TCP and DTLS, session tickets, ALPN, SNI credential dispatch, and alert handling.

Transport endpoints wire engines into the reactor model:

  • TCP — TCPEndpoint → TlsRecordState / Tls12RecordState → TlsRecordEngine / Tls12RecordEngine
  • UDP — UDPEndpoint → one Dtls12Session or Dtls13Session per remote peer → Dtls12RecordEngine / Dtls13RecordEngine
  • QUIC — QuicTlsClientEngine / QuicTlsServerEngine share the same TLS 1.3 HandshakeEngine core (RFC 9001 profile)

Handshake CPU work (key exchange, certificate verification, signatures) can be offloaded to CryptoExecutor while record AEAD stays on the connection’s SelectorLoop thread. Event callbacks from the handshake always marshal back to the loop thread before touching connection state.

Protocol versions and deployment model

Transport Supported Default Configuration
TCP (HTTPS, SMTP, IMAP, …) TLS 1.2, TLS 1.3 TLS 1.3 tls-version on TCPTransportFactory / Listener (TLS_1_2 or TLS_1_3)
UDP (DNS, CoAP-style services, …) DTLS 1.2, DTLS 1.3 DTLS 1.2 dtls-version on UDPTransportFactory / Listener (DTLS_1_2 or DTLS_1_3)
QUIC (HTTP/3, DoQ, …) TLS 1.3 only TLS 1.3 Not configurable (QUIC requirement)

Version pinning, not negotiation: each listener is configured for exactly one TLS or DTLS protocol version. The engine does not downgrade based on a peer ClientHello. To offer both TLS 1.2 and TLS 1.3 (or both DTLS versions), run two listeners on two ports. This removes cross-version downgrade ambiguity at the deployment boundary.

Not supported: SSL 3.0, TLS 1.0, TLS 1.1, and all non-AEAD cipher suites on every path.

TLS 1.3 engine

HandshakeEngine (RFC 8446) implements a reactive handshake driven by TlsEventSink callbacks — no blocking “run handshake until done” API on the hot path. Scope includes:

  • Full and resumed handshakes, HelloRetryRequest, PSK binders, and stateless session tickets
  • 0-RTT early data with anti-replay (when enabled in config)
  • ALPN (RFC 7301), SNI-based server credential dispatch, optional mTLS
  • Post-handshake NewSessionTicket
  • KeyUpdate on TCP record-layer mode only (RFC 8446 §4.6.3); forbidden over QUIC per RFC 9001
  • Named group selection including hybrid post-quantum groups (RFC 10024) when running on Java 25+ with ML-KEM/ML-DSA available in the JCA provider

Default TLS 1.3 cipher suites (preference order): TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384. ChaCha20-Poly1305 is listed first for constant-time AEAD on diverse clients; AES-128-GCM follows for AES-NI hardware; AES-256-GCM last for policy-driven preference only.

Default named groups (preference order): X25519_MLKEM768, X25519, SECP256R1, SECP384R1.

TLS 1.2 engine

Tls12HandshakeEngine (RFC 5246) is a separate state machine from TLS 1.3, sharing only the crypto floor (KeyExchange, CertificateVerifier, Prf). It exists for legacy interoperability (IMAPS, older clients, some STARTTLS deployments) with a deliberately narrow profile.

What TLS 1.2 supports

  • Key exchange: ECDHE only, fixed to secp256r1 (no static RSA, no other curves, no X25519 on this path)
  • Cipher suites: ECDHE + AEAD only — AES-GCM (RFC 5289) and ChaCha20-Poly1305 (RFC 7905). Suite choice must match server certificate key type (EC vs RSA).
  • Extended Master Secret (RFC 7627) — mandatory on every handshake
  • Secure renegotiation indication (RFC 5746) — sent; actual renegotiation is never offered or accepted
  • Session resumption: RFC 5077 stateless tickets only (not RFC 5246 session-ID caching)
  • ALPN (RFC 7301), SNI credential dispatch, optional mTLS
  • Server signatures: ECDSA and RSA PKCS#1 v1.5 for CertificateVerify (no Ed25519 codepoint on TLS 1.2 wire; no RSA-PSS for the engine’s own signatures)

Default TLS 1.2 cipher suites (preference order): TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256, TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256, TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256, TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256, TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384, TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384. Same ChaCha-first ordering as TLS 1.3; suite choice must still match server certificate key type (EC vs RSA).

Setting named-groups on a TLS 1.2 listener has no effect; the property is ignored with a warning.

DTLS 1.2 and DTLS 1.3

UDP endpoints select a DTLS version the same way TCP selects TLS: dtls-version pins DTLS_1_2 or DTLS_1_3. Each remote address gets its own session object on the shared datagram socket.

DTLS 1.2 (RFC 6347)

  • Wraps Tls12HandshakeEngine with datagram reassembly, flight retransmission, replay windows, and epoch-aware keys
  • Optional HelloVerifyRequest cookie exchange (require-cookie, cookie-secret) for anti-amplification on servers
  • Uses TLS 1.2 cipher suite set and secp256r1 ECDHE constraints
  • max-fragment-size (default 1024) and max-dtls-peers (default 4096; 0 = unlimited) bound memory

DTLS 1.3 (RFC 9147)

  • Wraps HandshakeEngine in DTLS mode with unified headers, QUIC-style AEAD/header protection (PacketProtection), minimal ACK (content type 26), and HelloRetryRequest cookie hook
  • Uses TLS 1.3 cipher suites and configurable named groups
  • Continuous transcript across cookie retry (no engine rebuild)

QUIC integration

QUIC always uses TLS 1.3. QuicTlsClientEngine and QuicTlsServerEngine adapt HandshakeEngine to QUIC CRYPTO stream framing and RFC 9001 key schedule labels. ALPN negotiates application protocols (h3, doq, etc.). Server identity uses the same keystore or PEM properties as TCP/TLS and DTLS listeners (see Security — Server identity across transports).

Security practices

Explicit choices

  • AEAD-only record protection on all paths; no CBC
  • Forward secrecy via ECDHE (TLS 1.2 fixed curve; TLS 1.3 configurable groups)
  • Extended Master Secret mandatory on TLS 1.2
  • Version pinning per listener (see above)
  • Hostname verification enabled by default on clients (verify-hostname / HandshakeConfig)
  • Certificate validation via PKIX (CertificateVerifier) or custom X509TrustManager; optional SPKI pinning (pinned-cert-fingerprint)
  • DTLS amplification control — cookie exchange, peer admission on listeners (CIDR/rate limits before new sessions), pending datagram caps
  • Confidentiality limits — AES-GCM record counts tracked; TLS 1.3 supports KeyUpdate on TCP; TLS 1.2 closes when limit reached (no KeyUpdate in 1.2)
  • Anti-replay for 0-RTT and DTLS replay windows

Implicit / operational practices

  • Handshake callbacks run on the connection loop thread; cross-thread work uses explicit offload with deferred callback replay
  • SecurityInfo after securityEstablished() exposes negotiated cipher, ALPN, peer chain — handlers should not parse TLS records themselves
  • Trust material comes from configured truststores, JVM default trust, or explicit trust managers — no implicit trust-all in production paths
  • Java 25+ recommended when hybrid PQC named groups are required

Configuration for implementers

Configuration flows: gumdroprc / Listener → TransportFactory → HandshakeConfig (built per connection). Protocol services rarely touch handshake configs directly; they set listener properties or configure a factory in client code.

Listener and gumdroprc (server)

<listener class="org.bluezoo.gumdrop.http.HTTPListener">
    <property name="port">443</property>
    <property name="secure">true</property>
    <property name="tls-version">TLS_1_3</property>
    <property name="keystore-file">keystore.p12</property>
    <property name="keystore-pass">secret</property>
    <property name="cipher-suites">
        TLS_AES_128_GCM_SHA256:TLS_CHACHA20_POLY1305_SHA256
    </property>
    <property name="named-groups">X25519:SECP256R1</property>
    <property name="need-client-auth">false</property>
    <property name="truststore-file">truststore.p12</property>
    <property name="truststore-pass">secret</property>
    <property name="sni-hostnames">
        <map>
            <entry key="example.com" value="example-cert"/>
        </map>
    </property>
    <property name="sni-default-alias">default-cert</property>
</listener>

UDP listeners use dtls-version instead of tls-version and may set DTLS-specific properties (require-cookie, max-fragment-size, max-dtls-peers). See DNS for DoT/DoQ examples.

Programmatic client (factory)

TCPTransportFactory factory = new TCPTransportFactory();
factory.setSecure(true);
factory.setTlsVersion(TlsVersion.TLS_1_3);
factory.setKeystoreFile("client.p12");
factory.setKeystorePass("secret");
factory.setTruststoreFile("trust.p12");
factory.setTruststorePass("secret");
factory.setApplicationProtocols("h2", "http/1.1");
factory.setCipherSuites("TLS_AES_128_GCM_SHA256");
factory.setNamedGroups("X25519");
factory.start();

ClientEndpoint endpoint = new ClientEndpoint(factory, "example.com", 443);
endpoint.connect(new MyProtocolHandler());

UDP clients mirror this with UDPTransportFactory, setDtlsVersion(DtlsVersion.DTLS_1_3), and protocol-specific ALPN (e.g. dot, doq).

ALPN

Application-Layer Protocol Negotiation selects the protocol above TLS (HTTP/2 vs HTTP/1.1, h3 on QUIC, dot for DoT, etc.).

  • Server: protocol listeners set defaults — e.g. HTTPListener offers h2 and http/1.1; HTTP3Listener sets h3
  • Custom service: setApplicationProtocols(String...) on TCPTransportFactory / UDPTransportFactory
  • After handshake: negotiated protocol is available from SecurityInfo.getApplicationProtocol() and passed to ProtocolHandler.securityEstablished(SecurityInfo)

SNI and server credentials

Server Name Indication lets one IP/port serve multiple certificates:

  • sni-hostnames map (exact or *.example.com wildcards) → keystore alias
  • sni-default-alias when no hostname matches
  • Programmatic: setServerCredentialsResolver(ServerCredentialsResolver) takes precedence over fixed ServerCredentials
  • Clients set SNI automatically from the connect hostname (except UNIX domain sockets)

Client certificates (mTLS)

<property name="need-client-auth">true</property>
<property name="truststore-file">client-ca.p12</property>
<property name="truststore-pass">secret</property>

Clients present an identity via setClientCredentials(ServerCredentials) or by loading a client keystore into the factory. Server-side need-client-auth=true maps to ClientAuthPolicy.REQUIRE.

Cipher suites

Colon-separated IANA names on cipher-suites. Unrecognized names are logged and skipped. Use TLS 1.3 names when tls-version is TLS_1_3 (or DTLS 1.3); use TLS 1.2 names when pinned to TLS 1.2 / DTLS 1.2.

Named groups (TLS 1.3 / DTLS 1.3)

Colon-separated group names: X25519, SECP256R1, SECP384R1, X25519_MLKEM768, SECP256R1_MLKEM768, SECP384R1_MLKEM1024. Hybrid groups require Java 25+ JCA support for ML-KEM/ML-DSA.

Protocol handlers and SecurityInfo

ProtocolHandler implementations receive cleartext application data from the framework. For TLS endpoints:

  • Call endpoint.startTLS() (or rely on implicit TLS / STARTTLS advertisement) — the framework runs the handshake
  • Implement securityEstablished(SecurityInfo info) to learn cipher suite, peer certificates, ALPN, and session timing
  • Use HandshakeSecurityInfo / Tls12SecurityInfo / Dtls12SecurityInfo / Dtls13SecurityInfo for type-specific details when needed

Do not instantiate HandshakeEngine or record engines in normal protocol code; use transport factories unless you are extending the TLS stack itself.
