Gumdrop TLS & DTLS

← Back to Main Page

Gumdrop ships a complete in-tree transport-security stack in org.bluezoo.gumdrop.crypto and org.bluezoo.gumdrop.tls. TCP listeners, UDP listeners, and QUIC all use this implementation — there is no dependency on JSSE SSLEngine or third-party TLS libraries on the data path. JCA is used only for primitive operations (signatures, key agreement, AEAD via Cipher, PKIX path validation). Everything is pure Java bytecode in the same JVM as the rest of the framework, with no native library build step. By contrast, Netty typically relies on the JDK's JSSE for TCP TLS, and its incubator QUIC and HTTP/3 transport uses native code (Cloudflare quiche with BoringSSL behind JNI), which adds platform-specific artifacts and deployment constraints.

Cipher suites and protocol versions are curated for secure defaults rather than mirroring JSSE's permissive “support everything” posture. TLS is applied consistently across protocols together with IAM and rate limiting (see Security).

This page describes scope, deliberate design choices, security practices, configuration for protocol-handler authors, and pointers to RFC conformance matrices. For certificates, keystores and pinning see Certificates and keystores; for IAM, rate limiting and quotas see Security.

Architecture

The stack splits cleanly into cryptography and protocol state:

  • org.bluezoo.gumdrop.crypto — HKDF, TLS 1.2 PRF, ECDHE key exchange, named groups (including the RFC 10024 hybrid post-quantum groups), signature schemes (including ML-DSA), and PKIX certificate verification helpers.
  • org.bluezoo.gumdrop.tls — handshake state machines (HandshakeEngine for TLS 1.3, Tls12HandshakeEngine for TLS 1.2), record layers for TCP and DTLS, session tickets, ALPN, SNI credential dispatch, and alert handling.

Transport endpoints wire engines into the reactor model:

  • TCP — TcpEndpoint → TlsRecordState / Tls12RecordState → TlsRecordEngine / Tls12RecordEngine
  • UDP — UdpEndpoint → one Dtls12Session or Dtls13Session per remote peer → Dtls12RecordEngine / Dtls13RecordEngine
  • QUIC — QuicTlsClientEngine / QuicTlsServerEngine share the same TLS 1.3 HandshakeEngine core (RFC 9001 profile)

Handshake CPU work (key exchange, certificate verification, signatures) can be offloaded to CryptoExecutor while record AEAD stays on the connection’s SelectorLoop thread. Event callbacks from the handshake always marshal back to the loop thread before touching connection state.

Java 25 baseline and post-quantum TLS

Gumdrop 3 requires Java 25 (LTS) or newer. That bar is intentional: modern JDK cryptography exposes ML-KEM and ML-DSA through the standard JCA, which the in-tree TLS engine uses for hybrid post-quantum key exchange (RFC 10024) and for PKIX validation of post-quantum certificates. Hybrid groups are offered by default in TLS 1.3, DTLS, and QUIC; signature schemes include ML-DSA alongside classical algorithms. See Named groups and Signature schemes and certificate keys for the details, and SecurityInfo.getNamedGroup() (see Security practices) to confirm what negotiated on a live connection.

Protocol versions and deployment model

Transport Supported Default Configuration
TCP (HTTPS, SMTP, IMAP, …) TLS 1.2, TLS 1.3 negotiate (prefers TLS 1.3) TlsConfig.tlsVersion() (NEGOTIATE, TLS_1_2 or TLS_1_3)
UDP (DNS, CoAP-style services, …) DTLS 1.2, DTLS 1.3 negotiate (prefers DTLS 1.3) TlsConfig.dtlsVersion() (NEGOTIATE, DTLS_1_2 or DTLS_1_3)
QUIC (HTTP/3, DoQ, …) TLS 1.3 only TLS 1.3 Not configurable (QUIC requirement)

One version per connection, chosen once. The default, NEGOTIATE, inspects the peer’s first handshake flight once and picks TLS 1.3 if it is offered, otherwise TLS 1.2 (DTLS likewise); a client in this mode offers TLS 1.3 and keeps TLS 1.2 as the fallback. A single record engine then runs for the whole connection. There is no version renegotiation, and the engines never switch mid-connection. To refuse the older version, pin the listener or client to TLS_1_3 or DTLS_1_3; to serve only legacy peers, pin TLS_1_2 or DTLS_1_2. A pinned endpoint rejects a peer that offers only the other version.

Not supported: SSL 3.0, TLS 1.0, TLS 1.1, and all non-AEAD cipher suites on every path.

TLS 1.3 engine

HandshakeEngine (RFC 8446) implements a reactive handshake driven by TlsEventSink callbacks — no blocking “run handshake until done” API on the hot path. Scope includes:

  • Full and resumed handshakes, HelloRetryRequest, PSK binders, and stateless session tickets
  • 0-RTT early data with anti-replay (when enabled in config)
  • ALPN (RFC 7301), SNI-based server credential dispatch, optional mTLS
  • Post-handshake NewSessionTicket
  • KeyUpdate on TCP record-layer mode only (RFC 8446 §4.6.3); forbidden over QUIC per RFC 9001
  • Named group selection including hybrid post-quantum groups (RFC 10024); X25519MLKEM768 is preferred by default
  • Post-quantum authentication with ML-DSA: see Signature schemes and certificate keys
  • record_size_limit (RFC 8449) — HandshakeConfig.setRecordSizeLimit() / setRecordSizeLimitEnabled(); enforced on TCP and DTLS record layers (QUIC negotiates the extension but uses QUIC frame sizing on the wire)
  • Certificate compression (RFC 8879) — compress_certificate with Brotli (micula) and zlib; enabled by default via HandshakeConfig.setCertificateCompressionEnabled()
  • Encrypted Client Hello (RFC 9849) — HPKE (RFC 9180) with DHKEM(X25519, HKDF-SHA256) and HKDF-SHA256, using AES-128-GCM (the suite RFC 9849 section 9 requires), AES-256-GCM or ChaCha20-Poly1305. A client takes the first supported suite in an ECHConfig’s own order and skips configs offering none; a server only opens a suite its config advertises, and keeps the first flight’s suite across a HelloRetryRequest. Other KEMs and KDFs are ignored. Client GREASE, server retry_configs, and HelloRetryRequest inner transcript handling. Server keys on secure listeners: ech-config-list-file, ech-private-key-file, optional ech-required in server.xml. The config list file is the whole published ECHConfigList and is sent as retry_configs on rejection. The private key file holds one raw 32-byte key or any number of keys, one per line as 64 hex digits (blank lines and # comments ignored); each key is paired with the config whose public key it matches, and a ClientHello is opened with the key of the config_id it names, so a client with an unknown id is rejected with retry_configs. To rotate keys, publish the old and new configs together and list both keys, update the DNS HTTPS ech record (RFC 9848), and drop the old config and key once cached records have expired. Gumdrop only reads these records; publishing them (RFC 9848) is up to the operator. Clients: the HTTP-family clients (HttpClient, WebSocketClient, ConnectUdpClient) look up the DNS HTTPS ech SvcParam themselves before connecting. The SMTP, IMAP, POP3, FTP, Redis, LDAP and MQTT clients do so only when TlsConfig.clientEchDnsDiscovery(true) is set (default off); the lookup is skipped for cleartext dials, socket paths, addresses, literal IPs and localhost, and a failed lookup never stops the connection. Every client can also use TlsConfig.clientEchConfigListFile() and clientEchGreaseEnabled(). Precedence: a list found in DNS is used first; the file is the fallback when DNS supplies none; GREASE applies only when no real config is used and is never required. TlsConfig.clientEchRequired(true) refuses servers that reject ECH: the client completes the exchange on the outer hello only far enough to verify the server against the offered config’s public_name (certificate and Finished), then aborts with ech_required before sending anything else, and never retries on its own. Only once the server has authenticated are its retry_configs trusted; the first usable config is then kept for later connections through the same transport factory. Without clientEchRequired a rejected offer is not fatal and the connection continues on the outer hello with the same public_name verification. If a HelloRetryRequest already shows the server rejecting ECH, a client that requires ECH aborts immediately.

Default TLS 1.3 cipher suites (preference order): TLS_AES_256_GCM_SHA384, TLS_AES_128_GCM_SHA256, TLS_CHACHA20_POLY1305_SHA256. AES-GCM is listed first: it is hardware-accelerated and constant-time on the processors servers run on, and costs both ends less than ChaCha20-Poly1305. ChaCha20-Poly1305 remains available for a client that prefers or only offers it, such as one without AES hardware. This is the order the JDK uses.

Default named groups (preference order): X25519MLKEM768, x25519, secp256r1, secp384r1.

TLS 1.2 engine

Tls12HandshakeEngine (RFC 5246) is a separate state machine from TLS 1.3, sharing only the crypto floor (KeyExchange, CertificateVerifier, Prf). It exists for legacy interoperability (IMAPS, older clients, some STARTTLS deployments) with a deliberately narrow profile.

What TLS 1.2 supports

  • Key exchange: ECDHE only, over X25519 (preferred) or secp256r1 (RFC 8422); the server picks the first of its groups the client offers (no static RSA, no other curves)
  • Cipher suites: ECDHE + AEAD only — AES-GCM (RFC 5289) and ChaCha20-Poly1305 (RFC 7905). Suite choice must match server certificate key type (EC vs RSA).
  • Extended Master Secret (RFC 7627) — mandatory on every handshake
  • Secure renegotiation indication (RFC 5746) — sent; actual renegotiation is never offered or accepted
  • Session resumption: RFC 5077 stateless tickets only (not RFC 5246 session-ID caching)
  • ALPN (RFC 7301), SNI credential dispatch, optional mTLS
  • Record size limit (RFC 8449) on TCP TLS 1.2 and DTLS 1.2 via Tls12HandshakeConfig
  • Server signatures: ECDSA and RSA PKCS#1 v1.5 for CertificateVerify (no Ed25519 codepoint on TLS 1.2 wire; no RSA-PSS for the engine’s own signatures)

What TLS 1.2 does not support

Default TLS 1.2 cipher suites (preference order): TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384, TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384, TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256, TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256, TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256, TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256. Same AES-GCM-first ordering as TLS 1.3; suite choice must still match server certificate key type (EC vs RSA).

On a TLS 1.2 listener namedGroups selects among x25519 and secp256r1, in the order given; when unset both are used, X25519 first. Hybrid post-quantum groups and other curves are TLS 1.3 only: they are ignored with a warning, and a list with no usable entry falls back to the default pair.

DTLS 1.2 and DTLS 1.3

UDP endpoints select a DTLS version the same way TCP selects TLS: dtlsVersion pins DTLS_1_2 or DTLS_1_3. Each remote address gets its own session object on the shared datagram socket.

DTLS 1.2 (RFC 6347)

  • Wraps Tls12HandshakeEngine with datagram reassembly, flight retransmission, replay windows, and epoch-aware keys
  • Optional HelloVerifyRequest cookie exchange for anti-amplification on servers: TlsConfig.requireCookie(true). The cookie is computed from cookieSecret(byte[]); leave it unset for a random secret per listener, or give every instance behind one address the same secret so a cookie issued by one is accepted by another
  • Uses TLS 1.2 cipher suite set and the same x25519 / secp256r1 ECDHE groups
  • Memory is bounded by TlsConfig.maxFragmentSize(int) (default 1024) and, on any UDP listener, maxDtlsPeers(int) (default 4096; 0 = unlimited)

DTLS 1.3 (RFC 9147)

  • Wraps HandshakeEngine in DTLS mode with unified headers, QUIC-style AEAD/header protection (PacketProtection), minimal ACK (content type 26), and a HelloRetryRequest cookie exchange controlled by the same requireCookie and cookieSecret settings
  • Uses TLS 1.3 cipher suites and configurable named groups
  • Continuous transcript across cookie retry (no engine rebuild)
  • Server-side Encrypted Client Hello (RFC 9849) with the same ech-config-list-file, ech-private-key-file and ech-required settings as TCP and QUIC listeners (see above); they are ignored for DTLS 1.2

QUIC integration

QUIC always uses TLS 1.3. QuicTlsClientEngine and QuicTlsServerEngine adapt HandshakeEngine to QUIC CRYPTO stream framing and RFC 9001 key schedule labels. ALPN negotiates application protocols (h3, doq, etc.). Server identity uses the same keystore or PEM properties as TCP/TLS and DTLS listeners (see Certificates and keystores).

The QUIC transport itself is also in-tree, pure Java and event-driven: every connection is multiplexed on the same SelectorLoop threads as the rest of the framework and no thread is dedicated to a connection. As far as we know, Gumdrop is the only asynchronous pure-Java QUIC implementation. The one other pure-Java implementation we know of, Kwik, has client and server roles but a thread-based design: every connection, on the server as well as the client, gets its own receiver thread and its own sender thread (which sleeps in a wait loop), plus single-thread executors for callbacks and timers; application streams are read and written through blocking java.io streams, and on the server one shared thread reads the socket and queues each datagram to the receiver thread of the connection it belongs to. The remaining Java options (such as Netty’s incubator codec) wrap native code.

Security practices

Explicit choices

  • AEAD-only record protection on all paths; no CBC
  • Forward secrecy via ECDHE (TLS 1.2 fixed curve; TLS 1.3 configurable groups)
  • Extended Master Secret mandatory on TLS 1.2
  • Version policy per listener or client: negotiate (prefer 1.3) or pin one version (see above)
  • Hostname verification enabled by default on clients (HandshakeConfig.setVerifyHostname); TlsConfig.verifyPeer(false) turns off peer verification altogether and is for tests only
  • Certificate validation via PKIX (CertificateVerifier) or custom X509TrustManager; optional certificate or SPKI pinning (see pinning)
  • DTLS amplification control — cookie exchange, peer admission on listeners (CIDR/rate limits before new sessions), pending datagram caps
  • Confidentiality limits — AES-GCM record counts tracked; TLS 1.3 supports KeyUpdate on TCP; TLS 1.2 closes when limit reached (no KeyUpdate in 1.2)
  • Anti-replay for 0-RTT and DTLS replay windows

Implicit / operational practices

  • Handshake callbacks run on the connection loop thread; cross-thread work uses explicit offload with deferred callback replay
  • SecurityInfo after securityEstablished() exposes negotiated cipher, ALPN, peer chain — handlers should not parse TLS records themselves
  • Trust material comes from configured truststores, JVM default trust, or explicit trust managers — no implicit trust-all in production paths
  • SecurityInfo.getNamedGroup() reports the key exchange group actually negotiated, which is how to confirm a connection used a hybrid post-quantum group

Configuration for implementers

Configuration flows: Listener → TransportFactory → HandshakeConfig (built per connection). Protocol services rarely touch handshake configs directly: you give a listener or client a TlsConfig and the framework configures the factory.

Transparent TLS

All endpoints support transparent TLS; protocol handlers never see records. The framework handles:

  • Implicit TLS - endpoint starts encrypted (HTTPS, IMAPS, POP3S)
  • STARTTLS - upgrade from cleartext to TLS mid-session
  • Client authentication - mutual TLS, with client certificates required
  • SNI - Server Name Indication for virtual hosting
  • ALPN - Application Layer Protocol Negotiation (HTTP/3, HTTP/2)
  • DTLS - TLS for UDP protocols
  • QUIC - always TLS 1.3 via the in-tree engine

To enable TLS, configure the keystore on any listener: 

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
SmtpServer smtps = SmtpServer.compose()
    .listener(new SmtpListener().port(465).secure(true).tls(tls))
    .sessionProvider(SmtpServerSessionProviders.relay()
        .hostname("relay.example.com"))
    .server();

The sections below cover the underlying listener and factory properties in detail.

Listener (server)

A listener takes all of its TLS settings from one TlsConfig: 

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret")
    .tlsVersion(TlsVersion.TLS_1_3)
    .cipherSuites("TLS_AES_128_GCM_SHA256:TLS_CHACHA20_POLY1305_SHA256")
    .namedGroups("X25519:SECP256R1")
    .requireClientAuth(false)
    .trustManager((X509TrustManager)
            TlsUtils.loadTrustManagers(Path.of("truststore.p12"), "secret", "PKCS12")[0])
    .sni("example.com", "example-cert")
    .sniDefaultAlias("default-cert");

Http2Listener listener = new Http2Listener().port(443).secure(true).tls(tls);

Whether a listener uses TLS at all is decided by secure(boolean). The configuration is copied when tls() is called. UDP listeners use dtlsVersion(DtlsVersion) on the TlsConfig instead of tlsVersion and may set DTLS-specific options (requireCookie, cookieSecret, maxFragmentSize on the TlsConfig, and maxDtlsPeers on the listener). See DNS for DoT/DoQ examples.

Programmatic client

In the client examples on this page, gumdrop is the Gumdrop instance returned by Gumdrop.boot(); a client is given it when it connects.

Every Gumdrop client takes a TlsConfig through tls(), and decides whether to use TLS with secure(boolean): 

TlsConfig tls = TlsConfig.keystore(Path.of("client.p12"), "secret")
    .cipherSuites("TLS_AES_128_GCM_SHA256")
    .namedGroups("X25519");

HttpClient client = new HttpClient("example.com", 443).secure(true).tls(tls);
client.connect(gumdrop, new MyHttpClientHandler());

UDP-based protocols (DoQ, DoT, DoH) are connected by the DNS resolver, which negotiates the protocol-specific ALPN (dot, doq) itself.

ALPN

Application-Layer Protocol Negotiation selects the protocol above TLS (HTTP/2 vs HTTP/1.1, h3 on QUIC, dot for DoT, etc.).

  • Server: protocol listeners set defaults — e.g. HttpListener offers h2 and http/1.1; Http3Listener sets h3
  • Custom service: setApplicationProtocols(String...) on TcpTransportFactory / UdpTransportFactory
  • After handshake: negotiated protocol is available from SecurityInfo.getApplicationProtocol() and passed to ProtocolHandler.securityEstablished(SecurityInfo)

SNI and server credentials

Server Name Indication lets one IP/port serve multiple certificates:

  • TlsConfig.sni(hostname, alias) (exact or *.example.com wildcards) → keystore alias
  • TlsConfig.sniDefaultAlias() when no hostname matches
  • Programmatic: setServerCredentialsResolver(ServerCredentialsResolver) takes precedence over fixed ServerCredentials
  • Clients set SNI automatically from the connect hostname (except UNIX domain sockets)

Client certificates (mTLS)

TlsConfig tls = TlsConfig.keystore(Path.of("server.p12"), "secret")
    .requireClientAuth(true)
    .trustManager((X509TrustManager)
            TlsUtils.loadTrustManagers(Path.of("client-ca.p12"), "secret", "PKCS12")[0]);

Clients present an identity through their TlsConfig (serverCredentials(), or a keystore or PEM files). Server-side requireClientAuth(true) maps to ClientAuthPolicy.REQUIRE.

Cipher suites

Colon-separated IANA names on cipherSuites. Unrecognized names are logged and skipped. Use TLS 1.3 names when tlsVersion is TLS_1_3 (or DTLS 1.3); use TLS 1.2 names when pinned to TLS 1.2 / DTLS 1.2. In the default negotiate mode each engine takes the names of its own family from the list and logs a warning for the others, so a list of only TLS 1.3 names leaves TLS 1.2 on its defaults; set tlsVersion if you mean one family.

Named groups (TLS 1.3 / DTLS 1.3)

Colon-separated group names, as registered in the IANA TLS Supported Groups registry (matched case-insensitively): x25519, secp256r1, secp384r1, X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024. An unrecognised name is logged and skipped. The list is what a client offers and what a server accepts, each in its own preference order; a server negotiates the first group in its list that the client also supports, on QUIC as on TCP and DTLS.

Signature schemes and certificate keys (TLS 1.3 / DTLS 1.3 / QUIC)

There is nothing to configure: the scheme follows from the type of the private key. Supported keys, for a server certificate or a client (mTLS) certificate, are RSA (signed with RSASSA-PSS), ECDSA on P-256 or P-384, Ed25519, and the post-quantum ML-DSA-44, ML-DSA-65 and ML-DSA-87 (FIPS 204; mldsa44, mldsa65, mldsa87 on the wire).

  • A signature is only ever made with a scheme the peer listed in its signature_algorithms. If a client lists none that the server’s key can use — an ML-DSA server and a client without ML-DSA, say — the handshake fails with handshake_failure. One listener presents one certificate (per SNI name); there is no automatic fallback from an ML-DSA certificate to a classical one.
  • A peer’s CertificateVerify is rejected with illegal_parameter unless its scheme matches the certificate’s key: the right curve for ECDSA, the right parameter set for ML-DSA, and never RSASSA-PKCS1-v1_5.
  • Certificate chains are validated by the JDK’s PKIX implementation, which verifies ML-DSA signatures on certificates: a classical leaf issued by an ML-DSA CA, or an all-ML-DSA chain, both validate.
  • ML-DSA is TLS 1.3 only. The TLS 1.2 and DTLS 1.2 engines neither offer nor accept it, nor Ed25519; a listener that must also serve TLS 1.2 clients needs an RSA or ECDSA certificate.
  • ML-DSA certificates and signatures are several kilobytes. Over QUIC the handshake then spans several datagrams, and until the client’s address is validated the server may send only three times what it has received (RFC 9000 §8.1), so the handshake can take an extra round trip.

Certificates and keystores

How a server gets its identity, and how a client decides whom to trust. Everything here is passed to a listener or client as a TlsConfig; the options it feeds are described under Configuration for implementers.

All secure listeners (TCP/TLS, DTLS, and QUIC) use the same in-tree TLS stack and accept the same server-identity configuration, so the material below works for every transport. Certificate material is not checked in to the repository; you generate it once, locally.

The simplest form: three PEM files

The lowest-overhead way to give a listener an identity is plain PEM files. No keystore, no password, no format conversion, and the files are readable by curl, openssl, browsers and most other tools as they stand. Gumdrop’s build, tests and documentation use one layout:

FileHoldsUsed by
key.pem The server’s private key (unencrypted PKCS#8) The server: key-file / TlsConfig.pem
cert.pem The server’s certificate (and any intermediates) The server: cert-file / TlsConfig.pem
ca.pem The certificate of the CA that signed cert.pem Clients, as their trust anchor (curl --cacert, PemCredentials.loadTrustManager)

Only ca.pem is ever given to clients. key.pem stays on the server. 

// Server: the identity from two PEM files
TlsConfig tls = TlsConfig.pem(Path.of("etc/tls/cert.pem"), Path.of("etc/tls/key.pem"));
HttpServer http = HttpServer.compose()
    .secureEndpoint(8443, tls)
    .streamHandler(new MyStreamHandler())
    .server();

// Client: trust the CA in ca.pem, and nothing else
X509TrustManager trust = PemCredentials.loadTrustManager(Path.of("etc/tls/ca.pem"));

In server.xml for the servlet container, the same identity is: 

<listener port="8443" secure="true" cert-file="tls/cert.pem" key-file="tls/key.pem"/>

Generating them: ant tls-certs

From a checkout, one command creates the three files in etc/tls/ (gitignored), valid for localhost, 127.0.0.1 and ::1: 

ant tls-certs

It uses mkcert when it is installed, and openssl with a private CA otherwise. If neither is found the build stops and tells you how to install them for your system:

mkcert (recommended)openssl (fallback)
macOSbrew install mkcertbrew install openssl
Debian / Ubuntusudo apt install mkcertsudo apt install openssl
Fedorasudo dnf install mkcertsudo dnf install openssl
Windowswinget install FiloSottile.mkcert winget install ShiningLight.OpenSSL.Light, or the copy that comes with Git for Windows (found automatically)

mkcert is preferred because its CA can be added to your operating system’s trust store, which makes browsers and other tools trust the certificate with no further steps. With openssl you add ca.pem to the trust store yourself, or point a client at it directly. Programs installed somewhere unusual can be named with -Dmkcert.executable=... and -Dopenssl.executable=....

Ant targetWhat it does

tls-trust-install Adds the CA to the operating system trust store (mkcert only; may ask for your password)
tls-trust-uninstall Removes it again

Useful properties: -Dtls.dir= (output directory), -Dtls.names="localhost example.test 10.0.0.5" (host names and addresses), -Dtls.keytype=rsa (default is EC P-256) and -Dtls.generator=openssl. The header of ant/tls.xml lists them all.

The CA is created inside the checkout (etc/tls/ca/), not in mkcert’s per-user location, so nothing outside the checkout changes until you run tls-trust-install. After that, anyone who can read etc/tls/ca/rootCA-key.pem can create certificates your browser trusts: keep it private, and run ant tls-trust-uninstall tls-clean when you are finished with it.

To check a running server without touching the trust store, give curl the CA: 

curl --cacert etc/tls/ca.pem https://localhost:8443/

Without Ant

The files are ordinary PEM, so any tool can make them. With mkcert: 

mkcert -ecdsa -cert-file cert.pem -key-file key.pem localhost 127.0.0.1 ::1
cp "$(mkcert -CAROOT)/rootCA.pem" ca.pem

With only OpenSSL 1.1.1 or later, a self-signed certificate is a single command (it signs itself, so it is also its own trust anchor): 

openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 365 \
    -keyout key.pem -out cert.pem -subj "/CN=localhost" \
    -addext "subjectAltName=DNS:localhost,IP:127.0.0.1,IP:::1"
cp cert.pem ca.pem

Using Java keystores and truststores instead

Everything above also works with Java keystores, which suit deployments that already manage certificates that way. A keystore (PKCS#12, or JKS) holds the identity, and a truststore holds the trust anchors, in place of key.pem + cert.pem and ca.pem:

PEMJava keystore
Server identity cert-file, key-file; TlsConfig.pem(cert, key) keystore-file, keystore-pass, optional keystore-format (PKCS12 by default, or JKS); TlsConfig.keystore(path, pass)
Trust anchors PemCredentials.loadTrustManager(Path) TlsUtils.loadTrustManagers(path, pass, format)
Passwordnonerequired
Several identities in one file (SNI)no, one pair per listener yes, selected by alias

A listener takes one form or the other, not both. To build the keystore and truststore from the PEM files: 

ant tls-keystore          # etc/tls/keystore.p12 and etc/tls/truststore.p12, password "changeit"

or by hand: 

# PKCS#12 keystore: the server key and certificate, with the CA in the chain
openssl pkcs12 -export -in cert.pem -inkey key.pem -certfile ca.pem \
    -name server -out keystore.p12 -passout pass:changeit

# PKCS#12 truststore: the CA as a trust anchor (needs only the JDK)
keytool -importcert -noprompt -alias ca -file ca.pem \
    -keystore truststore.p12 -storetype PKCS12 -storepass changeit

# JKS, if something still wants it
keytool -importkeystore -srckeystore keystore.p12 -srcstoretype PKCS12 \
    -destkeystore keystore.jks -deststoretype JKS

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "changeit");
X509TrustManager trust = (X509TrustManager)
        TlsUtils.loadTrustManagers(Path.of("truststore.p12"), "changeit", "PKCS12")[0];

Going the other way, from an existing keystore back to PEM: 

openssl pkcs12 -in keystore.p12 -nokeys -out cert.pem                 # certificate(s)
openssl pkcs12 -in keystore.p12 -nocerts -nodes -out key.pem          # private key (PKCS#8)

PEM file format

With cert-file and key-file (or TlsConfig.pem) the certificate file must contain the full chain, leaf first and then intermediates. The private key file must be unencrypted PEM: a PKCS#8 -----BEGIN PRIVATE KEY----- block holding an RSA, EC, Ed25519 or ML-DSA key (the last two are for TLS 1.3 only), or a SEC1 -----BEGIN EC PRIVATE KEY----- block. The traditional RSA format (-----BEGIN RSA PRIVATE KEY-----) is not supported; convert it with openssl pkcs8 -topk8 -nocrypt -in old.pem -out key.pem. This applies on every transport.

Co-located HTTPS and HTTP/3

A typical deployment shares one port between an HTTPS listener on TCP and an HTTP/3 listener on UDP. secureEndpoint() pairs them and gives both the same identity: 

TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
HttpServer http = HttpServer.compose()
    .secureEndpoint(8443, tls)
    .streamHandler(new ServletRequestHandler(container))
    .server();

Both listeners must present the same certificate identity (same subject and SAN). A browser learns about HTTP/3 from the Alt-Svc header on the HTTP/2 connection and only tries QUIC if the certificate matches.

Certificate pinning

Pinning adds a check on top of normal chain validation. Hand a pinning trust manager to TlsConfig.trustManager(); any client or listener that takes a TlsConfig can use it. All of them live in org.bluezoo.gumdrop.util unless noted, and take colon-separated lowercase SHA-256 hex fingerprints. With no delegate they validate the chain against the JVM's default trust first; pass an X509TrustManager as the first argument to validate against your own trust anchors instead.

  • PinnedCertTrustManager pins the whole leaf certificate. Give it the fingerprints of both the current and the next certificate for zero-downtime rotation.
  • SpkiPinnedCertTrustManager pins the SubjectPublicKeyInfo instead, so a renewed certificate with the same key still matches (the RFC 7858 §4.2 strict profile for DNS over TLS).
  • org.bluezoo.gumdrop.dns.client.DaneTrustManager authenticates a server against DNSSEC-validated TLSA records (RFC 6698, RFC 7671). The DNS resolver builds it when it finds secure TLSA records.
TlsConfig tls = new TlsConfig()
    .trustManager(new PinnedCertTrustManager(
        "ab:cd:ef:01:23:...", "12:34:56:78:..."));
HttpClient client = new HttpClient("api.example.com", 443).secure(true).tls(tls);

Protocol handlers and SecurityInfo

ProtocolHandler implementations receive cleartext application data from the framework. For TLS endpoints:

  • Call endpoint.startTLS() (or rely on implicit TLS / STARTTLS advertisement) — the framework runs the handshake
  • Implement securityEstablished(SecurityInfo info) to learn cipher suite, peer certificates, ALPN, and session timing
  • Use HandshakeSecurityInfo / Tls12SecurityInfo / Dtls12SecurityInfo / Dtls13SecurityInfo for type-specific details when needed

Do not instantiate HandshakeEngine or record engines in normal protocol code; use transport factories unless you are extending the TLS stack itself.
