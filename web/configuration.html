Application Composition

← Back to Main Page

A Gumdrop 3 application is assembled in Java: you boot a Gumdrop instance, build protocol servers (and clients) from listeners and handlers, and give them to it. There is no general configuration file; Gumdrop is the one object that owns the reactor loops, timers and executors that everything shares. This page is about that composition and the instance's lifecycle. What a particular protocol's listeners and handlers look like is on its own page, linked from the main page.

Composition model

  1. Boot a Gumdrop instance.
  2. Build each protocol server from its listeners (port, TLS, limits) and a handler or session provider (the application logic).
  3. Add the servers to the instance. Clients are given the instance when they connect.
Gumdrop gumdrop = Gumdrop.boot();       // worker loops, timers, executors

Server server = ...;                    // composed as described on the protocol's page
gumdrop.addServer(server);              // started now, since the instance is running

SomeClient client = ...;
client.connect(gumdrop, handler);       // a client dials on the same instance

gumdrop.awaitShutdown();                // block until shut down

Application logic is never put in a server subclass. A server delegates each decision to the handler you compose onto it, usually as a chain of staged handlers, each handed a state object whose methods are the valid responses (accept, reject, and so on). The answer may be given later, from a callback, which is how a decision can wait for a database or a directory without blocking a loop. See Design.

Composers and fluent configuration

Wiring is done with fluent methods that are named for the setting and return the object, so a server, a listener or a client reads as one expression. A server is built with its compose() method, which returns a composer; server() validates it and returns the server:

  • listener(...) adds a listener. A listener is configured the same way (port, secure, tls, bindWildcard, timeouts, connection limits) and returns itself, so the settings chain after the constructor.
  • The handler or session provider, and settings that apply to the whole server such as the realm, are further composer methods.
  • TLS is always one TlsConfig, given to a listener or client with tls(...) and switched on with secure(true); see TLS & DTLS.
  • Clients are plain fluent objects: configure, then connect.

The exceptions are objects that follow someone else's convention, such as the JavaBean-style classes of the Servlet API and the JNDI resources of a servlet container, which keep their setXxx methods.

The Gumdrop instance

Gumdrop.boot() creates and starts an instance; Gumdrop.boot(GumdropConfig) does so with settings: 

Gumdrop gumdrop = Gumdrop.boot(GumdropConfig.create()
        .workerThreads(8)
        .drainTimeoutMs(15000));
SettingDefaultMeaning
workerThreads twice the processors (system property gumdrop.workers) Number of SelectorLoop worker threads
drainTimeoutMs 25000 (system property gumdrop.drainTimeoutMs, or the environment variable GUMDROP_DRAIN_TIMEOUT_MS) How long shutdown waits for in-flight connections; 0 closes at once

The instance owns the worker loops, the accept loop for TCP listeners, the shared timer, the storage executor (for blocking disk work off the loops) and the crypto executor. It also holds the one TelemetryConfig that every listener, endpoint and client on it reports to; set it with telemetryConfig(...) before adding servers (see Telemetry). A process normally has one instance, and every server and client in it shares the same threads, which is what lets a peer listen and dial on one (see Peer-to-peer).

For a host that supplies its own event loop, and for unit tests, Gumdrop.embedded(loop, executor) returns an instance that starts no threads: you own the loop, the executor runs the storage and crypto work, and there is no accept loop, shared timer or shutdown hook.

Lifecycle

  • Adding servers. addServer on a running instance starts the server at once and registers its TCP listeners with the accept loop; removeServer stops it. Listeners bind on the accept loop, so a port that cannot be bound is reported after addServer returns, not thrown from it.
  • Running. awaitShutdown() blocks the calling thread until shutdown has finished; an interrupt (Ctrl+C) counts as a request to shut down. Gumdrop.serve(servers...) is boot, add the servers, and awaitShutdown in one call.
  • Shutting down. shutdown() is graceful: the instance stops accepting connections, waits up to the drain timeout for in-flight ones to finish, lets each protocol say goodbye, flushes telemetry, and stops the loops. It is idempotent, and it also runs from a JVM shutdown hook, so SIGTERM shuts the instance down in the same way. shutdownNow() skips the drain and the goodbyes, for a second Ctrl+C. The instance also shuts down by itself when no listener and no active connection or client remains, and can be started again with start().
  • Readiness. isReady() is true once every listener has bound and the instance is not draining, isDraining() is true during a graceful shutdown, and getBindFailures() lists listeners that could not bind (for example because the port is in use). They are meant for a health or readiness probe.

Declarative configuration

The one declarative file is the servlet container's server.xml, read by its launcher (bin/gumdrop.sh) and turned into the same composition: a Container with its realms and contexts on an HttpServer. It covers only the container, its contexts and its HTTP listeners; everything else is composed in Java. See Servlet container — server.xml.

Moving from Gumdrop 2.x

Gumdrop 2.x used gumdroprc XML with reflective dependency injection. That has been removed: ConfigurationParser, ComponentRegistry and the example etc/gumdroprc.* files are gone, and there is no XML fallback. The migration guide maps 2.x names and patterns to 3.0.
