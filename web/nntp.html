Gumdrop NNTP Server

← Back to Main Page

Gumdrop provides an NNTP (Network News Transfer Protocol) news reader server following RFC 3977. It serves newsgroups to news readers such as Thunderbird, slrn, tin and pan, and to any other client of the protocol. Newsgroups are kept in a mailbox store, so the same Maildir or mbox storage used by the IMAP and POP3 servers can be read as news. Like all Gumdrop protocol implementations, the NNTP server uses the event-driven, non-blocking architecture, and articles are streamed to the client in constant memory however large they are. An NNTP client is also provided.

Protocol Support

The server runs in reader mode: it implements the commands a news reader uses to browse and read news, as defined in RFC 3977. Commands are case insensitive and are limited to 512 octets, as the RFC requires. The server answers one command at a time, in order, so clients may pipeline their commands.

Session commands

  • CAPABILITIES - lists what the server supports (VERSION 2, READER, LIST, OVER, HDR)
  • MODE READER - accepted; the server is always in reader mode
  • DATE - the server's time in UTC
  • HELP - a list of commands
  • QUIT - ends the session

Selecting and reading articles

  • GROUP - selects a newsgroup and returns the estimated article count and the first and last article numbers
  • LISTGROUP - as GROUP, and lists the article numbers in the group, optionally only those in a range
  • ARTICLE, HEAD, BODY - an article, its headers, or its body, by number, by message-id, or (with no argument) the current article
  • STAT - whether an article exists, without sending it
  • LAST, NEXT - move the current article back or forward

Posting, TLS and authentication

  • POST - accepts an article from a client when posting is allowed (postingAllowed); otherwise it is refused with 440. The article is read dot-unstuffed and handed to the handler. The stock handler holds a posted article in memory (up to 1 MiB, larger ones get 441), requires the From, Subject and Newsgroups headers, and appends it to the mailbox of each listed newsgroup that exists
  • STARTTLS (RFC 4642) - upgrades a plain connection to TLS. It is advertised only on a listener with TLS configured and only before TLS is in use. After the upgrade the client starts again: the selected newsgroup and any login are forgotten
  • AUTHINFO USER and AUTHINFO PASS (RFC 4643) - log in against the listener's realm. The command is available when a realm is set. Where TLS can be had, passwords are refused (483) until the connection is secure. After a login the newsgroup store is opened for that user, and the selected newsgroup is forgotten. Failed logins count towards the listener's lockout (maxAuthFailures)

AUTHINFO SASL

AUTHINFO SASL (RFC 4643 section 2.4) offers PLAIN, LOGIN, SCRAM-SHA-256 and EXTERNAL to the extent that the listener's realm supports them (getSupportedSASLMechanisms(); SCRAM needs getScramCredentials). They are advertised in CAPABILITIES as AUTHINFO USER SASL and SASL PLAIN LOGIN SCRAM-SHA-256 EXTERNAL. PLAIN, LOGIN and EXTERNAL are offered, and accepted, only on a secure connection (483 otherwise); EXTERNAL takes the identity from the TLS client certificate through the realm's authenticateCertificate, and an optional authorization identity must be allowed by authorizeAs. An initial response may follow the mechanism name, = stands for an empty one, and the client cancels with *. A successful SCRAM exchange ends with 283 and the server's signature. Failures count towards the listener's lockout.

Listings

  • LIST ACTIVE [wildmat] - newsgroups with their highest and lowest article numbers and posting status. A plain LIST means LIST ACTIVE
  • LIST NEWSGROUPS [wildmat] - newsgroups with descriptions
  • LIST OVERVIEW.FMT - the fields of the overview database
  • NEWGROUPS - newsgroups created since a date and time
  • OVER (and the older XOVER) - overview information (subject, author, date, message-id, references, size) for a range of articles, one article by message-id, or the current article. News readers use this to build their thread lists
  • HDR (and the older XHDR) - one header field for a range of articles, or the :bytes metadata item

Wildmats follow RFC 3977 section 4.2: * and ? match any run of characters and any one character, [...] matches a set, and a comma separated list may exclude names with a leading ! (comp.*,!comp.lang.misc). The class org.bluezoo.gumdrop.nntp.Wildmat is available to your own handlers.

Response codes

Responses use the codes of RFC 3977: for example 211 (group selected), 220 to 223 (article follows or exists), 224 (overview follows), 411 (no such newsgroup), 412 (no newsgroup selected), 420 to 423 (no current, next, previous or numbered article), 430 (no article with that message-id) and 500 or 501 (unknown command or bad syntax). A multi-line response is sent dot-stuffed and ends with a line containing only a dot. Article lines always end in CRLF whatever line endings the stored message has.

Newsgroups and Articles

The stock handler, DefaultNntpHandler, serves the mailboxes of a MailboxStore as newsgroups. The mapping is:

  • Newsgroup names - a mailbox is a newsgroup. The store's hierarchy delimiter is shown as a dot, so the mailbox comp/lang/java of a Maildir store is the newsgroup comp.lang.java
  • Article numbers - an article's number is its message number in the mailbox. The first article is number 1. A message marked deleted is not an article
  • Message-IDs - the article's Message-ID header. A message without one is given a message-id made from its unique id, so that every article has one
  • Overview - read from the raw headers at the start of each message (folded headers are unfolded), not from the message body, so a listing of a large group does not read the articles themselves
  • Whose store - the store is opened for the anonymousUser of the listener (default news) the first time a command needs it, and closed when the connection ends

To make a group, create a mailbox with that name in the store of the anonymous user. Deliver articles to it as you would deliver mail, for example with the SMTP server's mailbox delivery.

Streaming

ARTICLE, HEAD and BODY read the message in chunks from the mailbox's asynchronous content interface, convert line endings, dot-stuff, and wait for the connection to drain before reading the next chunk. Nothing is read off the I/O thread, and an article of any size takes the same small amount of memory. (Mailbox backends without asynchronous reads, such as mbox, load the message first.)

Handlers

The protocol work (CAPABILITIES, DATE, HELP, MODE, QUIT, LIST OVERVIEW.FMT, argument parsing, current group and article tracking, article streaming) is handled for you. Your code decides policy through a staged handler, in the same style as the SMTP, IMAP and POP3 servers:

  1. A ClientConnected handler is called for each new connection, and accepts it (or rejects it) through its ConnectedState, supplying the greeting and a ReaderHandler
  2. The ReaderHandler answers the reader commands: it is called to select a group, list groups or articles, retrieve an article, and produce overview and header listings, and replies through the GroupState, ListState, ArticleState and OverState it is given

The reader handler is called off the I/O thread, so it may block on storage. Lists are written an entry at a time, so a handler can list any number of groups or articles without holding them in memory. To serve news from something other than a mailbox store, implement ReaderHandler and supply it through your own NntpServerSessionProvider. 

public class MyHandler implements ClientConnected, ReaderHandler {

    public void connected(ConnectedState state, Endpoint endpoint) {
        state.acceptConnection("My news server", false, this);
    }

    public void selectGroup(GroupState state, MailboxStore store, String group) {
        ...
        state.selected(mailbox, group, count, low, high, this);
    }

    ...
}

Configuration

News servers are configured in Java. The composer holds the settings shared by every listener, and each NntpListener holds its own transport settings.

NntpServer.compose() settings

  • listener(NntpListener) - add a listener; at least one is required
  • sessionProvider(NntpServerSessionProvider) - the handler factory; use MailboxStoreNntpSessionProvider to serve a mailbox store
  • realm(Realm) - the authentication realm
  • anonymousUser(String) - the user whose store serves readers (default: news)
  • postingAllowed(boolean) - whether readers are told they may post (default: false)
  • authenticationRequired(boolean) - whether clients must log in (AUTHINFO) before they can read or post; until then other commands get 480 (default: false; needs a realm)

MailboxStoreNntpSessionProvider settings

  • mailboxFactory(MailboxFactory) - where the newsgroups are kept (Maildir or mbox)
  • greeting(String) - the text of the greeting (default: NNTP server ready)

NntpListener settings

  • port(int) - listening port (default: 119, or 563 when secure)
  • bindWildcard() and addresses(InetAddress...) - where to bind
  • secure(boolean) - implicit TLS (NNTPS)
  • tls(TlsConfig) - certificate and key
  • maxConnections(int) and maxConnectionsPerIP(int) - connection caps
  • rateLimit(String), maxAuthFailures(int), authLockoutTimeMs(long) - abuse protection
  • allowedNetworks and blockedNetworks - CIDR allow and block lists
  • idleTimeoutMs, readTimeoutMs, connectionTimeoutMs - timeouts
  • realm(Realm), anonymousUser(String), postingAllowed(boolean) and authenticationRequired(boolean) - as the composer's, per listener

Example configuration

Newsgroups kept in a Maildir store, served on port 119 and, with implicit TLS, on port 563: 

TlsConfig tls = TlsConfig.pem(Paths.get("cert.pem"), Paths.get("key.pem"));
MailboxFactory spool = new MaildirMailboxFactory(Paths.get("/var/spool/news"));

NntpServer server = NntpServer.compose()
        .listener(new NntpListener().port(119))
        .listener(new NntpListener().port(563).secure(true).tls(tls))
        .sessionProvider(new MailboxStoreNntpSessionProvider()
                .mailboxFactory(spool)
                .greeting("Example news server"))
        .anonymousUser("news")
        .server();

Gumdrop gumdrop = Gumdrop.boot();
gumdrop.addServer(server);
gumdrop.join();

With the store above, the mailboxes of the user news under /var/spool/news are the newsgroups.

Security

  • NNTPS (port 563) - implicit TLS; the connection is encrypted from the start (RFC 8143)
  • Limits - the listener's connection caps, rate limit, network allow and block lists, and timeouts apply as for the other mail protocols
  • STARTTLS and AUTHINFO - give a listener a tls configuration and a realm, and set authenticationRequired(true) for a private server. Passwords are not accepted in the clear when TLS is available
  • Command size - lines over 512 octets are refused and discarded without being buffered

Telemetry

When the telemetry configuration has an exporter that takes traces, each connection produces a trace with a session span and, after a login, an authenticated span; with metrics enabled (the default) each listener records connections, session duration, commands, authentications by mechanism, articles read and posted, article bytes sent and STARTTLS upgrades. The names are listed under Telemetry. A listener's metrics are available from NntpListener.getMetrics().

Client

org.bluezoo.gumdrop.nntp.client.NntpClient connects to a news server. It reads the greeting and CAPABILITIES, upgrades with STARTTLS and logs in with AUTHINFO USER/PASS as configured, and then gives your NntpClientHandler an NntpSession to issue commands on.

NntpClient settings

  • new NntpClient(host, port) - the server (119, or 563 for NNTPS)
  • secure(boolean) and tls(TlsConfig) - implicit TLS (NNTPS) and the TLS settings, such as trust
  • startTls(NntpClient.StartTls) - NEVER (default), IF_OFFERED (upgrade when the server offers it, otherwise carry on in the clear) or REQUIRED (fail if it is not offered)
  • credentials(user, password) - log in with AUTHINFO USER/PASS once TLS is set up as configured. With IF_OFFERED and a server that does not offer STARTTLS, the password is sent in the clear
  • saslMechanism(String) - log in with AUTHINFO SASL instead of USER/PASS: SCRAM-SHA-256, PLAIN, EXTERNAL, OAUTHBEARER (the password is the access token) or XOAUTH2. The server must offer the mechanism. SCRAM-SHA-256 is the choice for a connection without TLS; use PLAIN only under TLS
  • commandTimeoutMs(long) - how long to wait for an answer (default 60 seconds; 0 waits for ever)
  • selectorLoop and dnsResolver - where to run and how to resolve the host

Session commands

Commands may be issued from any thread. They are sent one at a time, in the order issued, and each reports to a callback on the connection's event loop.

  • group(name, callback) - the group's count and article range
  • stat(number, callback) and stat(messageId, callback)
  • listActive(wildmat, entries, callback) - one NewsgroupEntry per newsgroup as its line is read
  • over(first, last, entries, callback) - one OverviewEntry per article as its line is read
  • article, head and body - the text is passed to your NntpConsumer<ByteBuffer> dot-unstuffed, with line endings kept, in pieces of whatever size the connection delivers; the buffer is valid only during the call
  • articleWithAttachments(number, handler, callback) (also by message-id) - an article with its attachments taken out, see below
  • postWithAttachments(article, attachments, callback) - POST with files attached, see below
  • post(article, callback) - the article with any line endings; dot-stuffing and the terminator are added
  • command(line, multiline, content, callback) - any other command; the callback gets the status whatever its code
  • quit() - the session takes no more commands and the connection is closed when the server has answered

A command that the server refuses fails with an NntpException carrying the response code (0 if the connection itself failed). 

new NntpClient("news.example.com", 119)
        .startTls(NntpClient.StartTls.REQUIRED)
        .credentials("alice", "secret")
        .connect(gumdrop, new NntpClientHandler() {
            public void connected(final NntpSession session, NntpGreeting greeting) {
                session.listActive("comp.*", new NntpConsumer<NewsgroupEntry>() {
                    public void accept(NewsgroupEntry group) {
                        System.out.println(group.getName() + " " + group.getLow()
                                + "-" + group.getHigh());
                    }
                }, new NntpCallback<Void>() {
                    public void completed(Void result) {
                        session.quit();
                    }
                    public void failed(NntpException error) {
                        session.quit();
                    }
                });
            }
            public void error(Exception cause) { cause.printStackTrace(); }
            public void disconnected() { }
        });

Attachments

News readers do not use MIME multiparts for files. They put them in the body of the article as uuencoded blocks, from a line begin 644 name to an end line, and that is how files travel on Usenet. articleWithAttachments finds those blocks as the article arrives and decodes them, in constant memory however the article is split on the wire. Your org.bluezoo.gumdrop.mime.UuScanner.Handler is given:

  • text(data) - the article text outside the files, headers included, in order and in pieces of any size
  • begin(mode, name) - a file starts, with the permissions and name from the begin line
  • content(data) - decoded bytes of the file, in pieces of any size
  • end(complete) - the file ends; false if the article (or the connection) ended before the end line

Buffers are valid only during the call. Lines that merely look like a begin line are text, and a begin line split across network reads is found all the same. The same scanner is public as UuScanner in the MIME package, for articles you already have.

To post files, give postWithAttachments the article (headers, an empty line and the text) and a list of NntpAttachment (name, mode, content). Each file is uuencoded and appended to the body after the text, as news readers do, and a final line ending is supplied if the text lacks one. The files are encoded a line at a time into the post; the encoder is public as UuEncoder in the MIME package for other uses. A post goes as one POST, so very large files are better split into parts, as is the custom on binary newsgroups; the stock server handler accepts articles of up to 1 MiB. 

session.articleWithAttachments(number, new UuScanner.Handler() {
    public void text(ByteBuffer data) { /* the message */ }
    public void begin(int mode, String name) { out = new FileOutputStream(name); }
    public void content(ByteBuffer data) { /* write data to out */ }
    public void end(boolean complete) { out.close(); }
}, new NntpCallback<Void>() { /* completed, or failed */ });

Limitations

  • The server is a reader server. It does not accept articles from other servers (IHAVE) and has no NEWNEWS. AUTHINFO SASL offers PLAIN, LOGIN, SCRAM-SHA-256 and EXTERNAL (not OAUTHBEARER or GSSAPI)
  • The client does not do GSSAPI or LOGIN for AUTHINFO SASL, IHAVE, NEWNEWS or compression. A LIST ACTIVE or OVER entry is delivered once the line after it has begun to arrive (or the list ends), and an entry line over 64 KiB is skipped
  • The stock handler's POST keeps the whole article in memory while it is received, so it limits articles to 1 MiB; a handler of your own can write the article out as it arrives (PostSink)
  • With the stock handler, looking up an article by message-id searches the current group only, because a mailbox store has no index of message-ids; a lookup with no group selected finds nothing
  • Mailboxes record no creation time, so NEWGROUPS reports no new groups
  • LIST ACTIVE opens each mailbox to count its messages, and LIST NEWSGROUPS gives empty descriptions
  • The line count of the overview (:lines) is left empty
