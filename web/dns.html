Gumdrop DNS Server

← Back to Main Page

Gumdrop includes a DNS server that demonstrates the framework's UDP protocol support. DnsServer is the transport and protocol shell (listeners, validation, cookies, MQTYPE); it does not forward or serve zones by itself. You attach one composed DnsQueryHandler (or a chain) for application logic. Gumdrop includes two sibling built-in handlers for common cases — AuthoritativeZoneHandler and UpstreamRelayHandler — plus support for your own handlers. It serves as a practical DNS service and as a reference for UDP-based protocols.

Gumdrop also includes a separate multicast DNS (mDNS, RFC 6762) and DNS-SD (RFC 6763) implementation in the org.bluezoo.gumdrop.mdns package: it claims and defends a .local hostname on the local network, can query for other hosts' records, and can auto-advertise Gumdrop's own configured services (mail, web, DNS, etc.) so they're discoverable via Bonjour/Avahi/dns-sd -B.

Architecture

The DNS server is built on Gumdrop's UdpEndpoint abstraction, which provides non-blocking UDP I/O using the same SelectorLoop architecture as TCP servers. Each DNS query arrives as a datagram, is parsed, processed, and the response is sent back—all within the event-driven framework.

Query Processing Flow

  1. Receive - UDP datagram arrives, parsed into DnsMessage
  2. Validate - cookies, EDNS, opcode dispatch
  3. Handler - your DnsQueryHandler (authoritative, relay, or custom)
  4. MQTYPE merge - optional RFC 10029 multi-type merge
  5. Send - serialize response and send UDP datagram back to client

Core Components

  • DnsServer - protocol shell; delegates to your DnsQueryHandler
  • DnsQueryHandler - pluggable logic; see query handlers
  • DnsListener, DoTListener, DoQListener - transport listeners (see Listeners)
  • DnsMessage - parses and serializes DNS wire format
  • DnsQuestion - represents a query question
  • DnsResourceRecord - represents answer records
  • DnsCache - TTL-aware cache used by UpstreamRelayHandler (not by the bare DnsServer shell)

Features

The DnsServer shell handles listeners, wire format, cookies, and metrics for every deployment. What happens inside a query — zones, forwarding, caching, or custom policy — is entirely your DnsQueryHandler. Outbound lookups from SMTP, HTTP, and other services use DnsResolver (client), which is separate from DnsServer.

DnsServer shell

  • UDP, DoT, and DoQ listeners sharing one DnsQueryHandler
  • Wire parse/serialize, opcode dispatch, optional RFC 10029 MQTYPE merge
  • RFC 7873 DNS cookies at the protocol edge (see Protocol compliance)
  • DnsServerMetrics query/response counters for every deployment
  • Default handler when none is set: empty NOERROR (no upstream, no zones)

DTLS on DnsListener

For secure DNS (DNS over DTLS, RFC 8094), DnsServer can be configured with TLS credentials via the same secure/keystore-file/ keystore-pass properties used for DoT, and optional dtls-version / cipher-suites as documented in TLS & DTLS. DTLS session state (one in-tree DTLS session per peer) is maintained per remote address on the shared UDP socket, so a single DnsListener serves many concurrent DTLS clients without one client's handshake interfering with another's. Handshake flights are retransmitted with exponential backoff (RFC 6347 §4.2.4) when a client is slow or a packet is lost, and a handshake that never completes is dropped without affecting any other client's session.

Protocol Compliance

Gumdrop's DNS implementation goes beyond basic query/response handling with comprehensive protocol compliance across multiple RFCs.

EDNS0 (RFC 6891)

UpstreamRelayHandler and DnsResolver advertise EDNS0 by including an OPT pseudo-record in outgoing upstream queries. This signals the maximum UDP payload size (4096 bytes by default), allowing larger responses without TCP fallback. EDNS0 options also carry DNS cookies and padding. AuthoritativeZoneHandler answers from zone data; EDNS0 on responses follows what the handler and wire code attach for each query.

DNSSEC Validation (RFC 4033–4035, RFC 5155)

DNSSEC validation is optional and configured separately for the outbound client and for the upstream relay:

  • DnsResolver — setDnssecEnabled(true) validates answers from configured resolvers (see below).
  • UpstreamRelayHandler — dnssecEnabled(true) validates upstream answers before returning them to clients of your DnsServer.

When validation is enabled, the component sets DO in EDNS0 queries, fetches DNSSEC records as needed, and checks the chain of trust to configured trust anchors. The bare DnsServer shell does not validate DNSSEC by itself.

Supported algorithms (per RFC 8624):

  • RSA/SHA-256 (algorithm 8)
  • RSA/SHA-512 (algorithm 10)
  • ECDSA P-256/SHA-256 (algorithm 13)
  • ECDSA P-384/SHA-384 (algorithm 14)
  • Ed25519 (algorithm 15)
  • Ed448 (algorithm 16)

Supported DS digest types: SHA-1 (1), SHA-256 (2), SHA-384 (4).

All cryptographic operations use java.security from the java.base module and are purely CPU-bound — no blocking I/O, fully safe for the NIO event loop. DNSKEY and DS records needed for chain-of-trust validation are fetched asynchronously through the existing resolver callback model.

Configuration:

// Enable DNSSEC on the client resolver
DnsResolver resolver = new DnsResolver();
resolver.setDnssecEnabled(true);
resolver.addServer("8.8.8.8");
resolver.open();

// DNSSEC validation on upstream answers (UpstreamRelayHandler)
DnsServer service = DnsServer.compose()
    .listener(new DnsListener())
    .handler(UpstreamRelayHandler.builder()
        .upstreamServers("8.8.8.8")
        .dnssecEnabled(true)
        .build())
    .server();

When UpstreamRelayHandler has DNSSEC enabled, it sets DO on upstream queries and strips DNSSEC records from responses to clients that did not request them (no DO bit). The AD (Authenticated Data) flag is preserved from validated upstream responses.

DNS Message Compression (RFC 1035 section 4.1.4)

Outgoing DNS messages use name compression as specified in RFC 1035 section 4.1.4. Repeated domain name suffixes are replaced with pointers to earlier occurrences, reducing message size on the wire. This is especially effective for responses containing multiple records with shared suffixes.

DNS Cookies (RFC 7873)

DnsServer (all handlers) and DnsResolver support DNS cookies as an EDNS0 option for lightweight source verification. DnsServer validates or generates server cookies on ingress before calling your handler. DnsResolver stores server cookies per upstream for reuse on later queries. This is independent of upstream forwarding: an authoritative-only server still benefits from cookie handling at the shell.

DNS over TLS — DoT (RFC 7858)

The DoT client transport includes several optimizations and security features:

  • TLS session resumption (RFC 5077) — the TLS session cache is configured to allow session tickets, reducing handshake latency on reconnections
  • TCP Fast Open (RFC 7413) — when available, DoT connections use TCP Fast Open to send data during the TCP handshake, saving a round trip
  • SPKI fingerprint verification (RFC 7858 section 4.2) — for the Strict privacy profile, the client can be configured with SHA-256 hashes of the server's Subject Public Key Info (SPKI). After the TLS handshake, the server's leaf certificate public key is verified against the configured pins via SpkiPinnedCertTrustManager
  • Connection pooling (RFC 7766) — TCPDNSConnectionPool maintains persistent TCP connections to upstream servers with configurable maximum connections, idle timeout, and connection lifetime

DNS over QUIC — DoQ (RFC 9250)

DoQ support includes error handling, session resumption, and connection reuse:

  • Error codes (RFC 9250 section 4.3) — the DoQ listener sends proper DoQ application error codes (DOQ_NO_ERROR through DOQ_EXCESSIVE_LOAD) via QUIC RESET_STREAM frames for malformed queries, oversized messages, and server errors
  • 0-RTT early data (RFC 9250 section 4.5) — the QUIC transport enables early data, allowing QUERY and NOTIFY messages to be sent during session resumption without waiting for the full handshake. Session tickets are cached per server
  • Connection reuse (RFC 9250 section 5.5.1) — DoQConnectionPool maintains persistent QUIC connections per upstream server. Subsequent queries open new streams on the existing connection rather than establishing new QUIC sessions, with automatic eviction of idle connections
  • Padding (RFC 9250 section 5.4) — all DoQ messages include EDNS(0) padding aligned to 128-byte blocks (RFC 8467) to mitigate traffic analysis
  • Zone transfers — AXFR/IXFR use the same multi-message length-prefixed framing as DoT/TCP on a single QUIC stream; the client reads until STREAM FIN. DoQClientTransport delivers multiple answers via onReceiveSequence.

DNS over HTTPS — DoH (RFC 8484)

DoHClientTransport provides DNS resolution over HTTPS, sending queries as HTTP POST requests with application/dns-message content type. The response body contains the raw DNS wire-format answer.

  • Uses Gumdrop's existing HttpClient infrastructure (HTTP/2 with TLS)
  • Configurable URI path (default /dns-query)
  • Default port 443 with HTTPS
  • Works through HTTP proxies and CDNs — useful in environments where UDP and port 853 are blocked

Query handlers

Every query reaches your logic through the DnsQueryHandler interface. Gumdrop provides two full built-in implementations as sibling classes — neither is part of DnsServer, and neither wraps or requires the other:

  • AuthoritativeZoneHandler — serve your own zones (primary/secondary, UPDATE, transfers).
  • UpstreamRelayHandler — forward to resolvers with caching and optional DNSSEC validation.

For anything else — split horizon, blocklists, dynamic SRV, integration with your app — implement DnsQueryHandler yourself or subclass SyncDnsQueryHandler; see Custom handlers. You can also compose handlers with DnsQueryHandlers.chain(first, second): when the first handler returns empty NOERROR (defer), the second runs (typical for policy then relay).

Without .handler(...), DnsServer.compose() uses EmptyDnsQueryHandler (empty NOERROR). Attach exactly one handler instance (or a chain) with .handler(...); all listeners on that server share it.

ImplementationRole
AuthoritativeZoneHandler Built-in: zone files; RFC 2136 UPDATE, NOTIFY, AXFR/IXFR. Does not recurse or forward.
UpstreamRelayHandler Built-in: resolver relay with DnsCache, serve-stale, optional DNSSEC. Does not load your zone files.
SyncDnsQueryHandler Base class for your synchronous policy on the selector thread; return null from resolveQuery to defer in a chain.
DnsQueryHandler Interface for full async control (I/O, discovery, custom synthesis).

Typical wiring: .handler(auth) for authoritative only; .handler(relay) for a caching forwarder; .handler(DnsQueryHandlers.chain(policy, relay)) for custom rules then relay. Serving your zones and relaying everything else in one process usually means a custom chain or separate DnsServer instances, because each built-in handler implements one model.

AuthoritativeZoneHandler

Built-in handler for authoritative serving from BIND-style zone files (ZoneFile). Out-of-zone queries receive REFUSED; misses are not forwarded to resolvers. Configure with the builder:

  • zoneFile(Path) - load a zone file from disk on the storage pool at DnsServer start (default READ_ONLY; use zoneFile(path, READ_WRITE) to persist RFC 2136 updates via NIO). Requires $ORIGIN and an SOA at the origin.
  • deferZoneFileLoad(boolean) - when true (default), reading the zone file is deferred to start(Gumdrop) instead of build()
  • zone(ZoneFile) - use an already-loaded zone
  • minimalAnyPolicy(MinimalAnyPolicy) - RFC 8482 minimal ANY (default: enabled)
  • notifyPeer(InetSocketAddress) - RFC 1996 NOTIFY after successful RFC 2136 updates (NOTIFY sent asynchronously on the selector loop)
  • notifyFromNsRecords(boolean) - also NOTIFY in-zone NS names with glue A/AAAA on port 53 (default: true)
  • slaveOf(origin, master) - secondary: AXFR refresh from master over TCP on inbound NOTIFY (async on the selector loop via DnsZoneClient.axfrOverTcp)
  • tsigKey / requireTsig - RFC 2845 / RFC 8945 TSIG for dynamic update (HMAC-MD5 and HMAC-SHA256 wire names match BIND: hmac-md5.sig-alg.reg.int., hmac-sha256.); use TsigKey.fromBase64(name, algorithm, secret) with the same algorithm string as in named.conf. Signed UPDATE requests receive a TSIG-signed response (request MAC included) for nsupdate interop. Signed AXFR/IXFR over TCP receive a TSIG on each framed response message (MAC chained per RFC 8945).

RFC 2136 dynamic update and RFC 1996 NOTIFY are handled via handleNonQueryOpcode. Dynamic updates append to an in-memory ZoneJournal (RFC 1995 IXFR): the client's SOA must appear in the IXFR query authority section. When the journal covers the requested serial range, the server returns TTL=0 deletions and additions; otherwise it falls back to AXFR. Multi-message transfers use length-prefixed framing on DnsTcpListener, DoT, or DoQ; UDP AXFR/IXFR set TC when the response does not fit in 512 octets.

Supported directives: $ORIGIN, $TTL, $INCLUDE filename [origin] (include paths are relative to the file containing the directive). Record types: SOA, NS, A, AAAA, CNAME, MX, TXT, PTR. Wildcard owners (*) are supported. Negative answers follow RFC 2308 (NXDOMAIN vs NODATA with SOA in the authority section). In-zone CNAME records are chased when answering other types. Glue A/AAAA records are added for in-bailiwick NS/MX targets when present in the zone. 

AuthoritativeZoneHandler auth = AuthoritativeZoneHandler.builder()
    .zoneFile(Path.of("example.com.zone"))
    .build();

DnsServer dns = DnsServer.compose()
    .listener(new DnsListener().port(5353))
    .listener(new DnsTcpListener().port(5353))
    .handler(auth)
    .server();

Multiple zones: call zoneFile or zone more than once. The longest matching origin wins when a query name could belong to several zones. See also examples/dns-authoritative/ in the source tree.

UpstreamRelayHandler

Built-in handler for a caching DNS forwarder / proxy. It uses DnsCache and outbound resolver I/O; the DnsServer shell never forwards by itself. Install with .handler(UpstreamRelayHandler.builder()...) or as the second link in DnsQueryHandlers.chain(...). Builder options:

  • upstreamServers(String) - space-separated list of upstream DNS servers
  • useSystemResolvers(boolean) - use /etc/resolv.conf nameservers (default: true)
  • cacheEnabled(boolean) - enable response caching (default: true)
  • serveStaleEnabled(boolean) - RFC 8767: serve expired cache entries when upstream fails (default: true)
  • staleRetentionSeconds(int) - how long expired entries are kept for serve-stale (default: 86400; 0 evicts on expiry)
  • staleAnswerTtl(int) - TTL on stale answers (default: 30, per RFC 8767 section 4)
  • serveStalePolicy(ServeStalePolicy) - override or disable per-query stale policy (default: serve when stale data exists)
  • nxDomainCutPolicy(NxDomainCutPolicy) - RFC 8020: NXDOMAIN for subdomains of a proven-negative name (default: enabled)
  • minimalAnyPolicy(MinimalAnyPolicy) - RFC 8482: answer ANY with a minimal HINFO record (default: enabled)
  • dnssecEnabled(boolean) - validate upstream responses (sets DO on upstream queries; BOGUS answers → SERVFAIL; SECURE answers get AD)
  • trustAnchor(DnssecTrustAnchor) - trust anchor for validation; defaults to an empty store unless you add anchors
  • aggressiveNsecEnabled(boolean) - RFC 8198: synthesize NXDOMAIN/NODATA from validated NSEC/NSEC3 proofs before upstream (default: true when DNSSEC is on)
  • aggressiveNsecPolicy(AggressiveNsecPolicy) - override or disable per-query aggressive synthesis (default: synthesize when a proof covers the QNAME)

When dnssecEnabled is true, the relay validates each upstream answer with DnssecChainValidator, retains SECURE denial proofs in DnsNsecProofCache, and on later cache misses may answer from those proofs without an upstream round trip (RFC 8198). Disable with aggressiveNsecPolicy(AggressiveNsecPolicy.DISABLED) if every query must reach upstream.

Behaviour summary. The relay forwards accepted queries to configured upstreams (tried in order; optional /etc/resolv.conf fallback), with query ID remapping and RFC 5452 response ID checks. It caches answers (TTL-aware, negative caching, configurable size), may serve stale on upstream failure (RFC 8767), and retries truncated UDP responses over TCP. Without this handler, DnsServer does not forward or cache answers.

// Caching forwarder on a non-privileged port
DnsServer dns = DnsServer.compose()
    .listener(new DnsListener().port(5353))
    .handler(UpstreamRelayHandler.builder()
        .upstreamServers("8.8.8.8 1.1.1.1")
        .cacheEnabled(true)
        .build())
    .server();

Upstream server format

Upstream servers can be specified with optional ports:

  • 8.8.8.8 - Google DNS (default port 53)
  • 1.1.1.1 - Cloudflare DNS
  • 192.168.1.1:53 - local router with explicit port
  • [2001:4860:4860::8888]:53 - IPv6 with port

Custom handlers

The built-in handlers cover two common deployments; most real setups also need policy you own. Subclass SyncDnsQueryHandler for quick synchronous rules on the selector thread, implement DnsQueryHandler for async work, or chain either in front of UpstreamRelayHandler.

  • Internal DNS for private networks
  • DNS-based service discovery
  • Split-horizon DNS (different answers for internal/external)
  • Filtering or blocking
  • Custom record types or dynamic responses

Example: internal names then relay

UpstreamRelayHandler relay = UpstreamRelayHandler.builder()
    .upstreamServers("8.8.8.8 1.1.1.1")
    .build();

DnsQueryHandler internal = new SyncDnsQueryHandler() {
    @Override
    protected DnsMessage resolveQuery(DnsMessage query) {
        DnsQuestion question = query.getQuestions().get(0);
        String name = question.getName();
        if (!name.endsWith(".internal.")) {
            return null; // chain to relay
        }
        InetAddress addr = internalHosts.get(name);
        if (addr != null) {
            return query.createResponse(Collections.singletonList(
                DnsResourceRecord.a(name, 300, addr)));
        }
        return query.createErrorResponse(DnsMessage.RCODE_NXDOMAIN);
    }
};

DnsServer dns = DnsServer.compose()
    .listener(new DnsListener().port(5353))
    .handler(DnsQueryHandlers.chain(internal, relay))
    .server();

Example: DNS-based ad blocking

DnsQueryHandler blocklist = new SyncDnsQueryHandler() {
    @Override
    protected DnsMessage resolveQuery(DnsMessage query) {
        String name = query.getQuestions().get(0).getName().toLowerCase(Locale.ROOT);
        if (blockedDomains.contains(name)) {
            return query.createErrorResponse(DnsMessage.RCODE_NXDOMAIN);
        }
        return null; // chain to UpstreamRelayHandler
    }
};

DnsServer dns = DnsServer.compose()
    .listener(new DnsListener())
    .handler(DnsQueryHandlers.chain(blocklist, relay))
    .server();

Example: dynamic service discovery

DnsQueryHandler srvDiscovery = new DnsQueryHandler() {
    @Override
    public void handleQuery(DnsMessage query, SelectorLoop loop,
                            DnsQueryCallback callback) {
        DnsQuestion question = query.getQuestions().get(0);
        if (question.getType() != DnsType.SRV) {
            EmptyDnsQueryHandler.INSTANCE.handleQuery(query, loop, callback);
            return;
        }
        List<ServiceInstance> instances =
            registry.lookup(question.getName());
        if (instances.isEmpty()) {
            EmptyDnsQueryHandler.INSTANCE.handleQuery(query, loop, callback);
            return;
        }
        List<DnsResourceRecord> answers = new ArrayList<>();
        for (ServiceInstance inst : instances) {
            answers.add(DnsResourceRecord.srv(question.getName(), 300,
                inst.getPriority(), inst.getWeight(),
                inst.getPort(), inst.getHostname()));
        }
        callback.onResponse(query.createResponse(answers));
    }
};

Authoritative deployment patterns

The following applies only to AuthoritativeZoneHandler. It is a toolkit for serving and maintaining zones inside Gumdrop, not a drop-in replacement for BIND. How you wire listeners, persistence, NOTIFY, and transfers depends on the role you need. Use the four questions below to pick APIs and configuration; several patterns can coexist on one server (different zones, different settings).

  1. Primary, secondary, or both?
    • Primary only - load or build zones, serve queries, optionally notifyPeer / notifyFromNsRecords after RFC 2136 updates. No slaveOf.
    • Secondary only - slaveOf(origin, master) plus a zone stub or empty SOA at the origin; inbound NOTIFY triggers a full AXFR refresh over TCP (see transfers below).
    • Both - multiple zoneFile / zone calls: some zones primary, some slaveOf for different origins.
  2. Mostly static files or dynamic updates in production?
    • Static - zoneFile(path) with default READ_ONLY; redeploy or reload the file when records change.
    • Dynamic - zoneFile(path, READ_WRITE), tsigKey, and usually requireTsig(true); clients use nsupdate or DnsZoneClient.sendUpdate. Successful updates persist asynchronously on the storage pool.
  3. Zone transfers: never, backup only, or ongoing secondaries?
    • Never - do not expose AXFR to untrusted networks; many embedded deployments only need Q&A plus UPDATE.
    • Backup / tooling - operators pull zones with DnsZoneClient.axfr / ixfr (TCP, optional DoT via TcpDnsClientTransport, optional TsigKey). No slaveOf required.
    • Secondaries - master: NOTIFY after updates; secondary: slaveOf. Large zones: enable DnsTcpListener, DoT, and/or DoQ on the master so multi-message AXFR/IXFR use length-prefixed streams (UDP answers set TC when the zone does not fit in 512 octets).
  4. Trust: open network, private network, TSIG, or TLS?
    • Private network - restrict ports 53/853 with firewall rules; TSIG optional.
    • TSIG - same tsigKey on the handler for UPDATE and (incoming) AXFR/IXFR verification; sign outbound updates and transfer pulls with DnsZoneClient. Built-in slaveOf refresh does not send TSIG today: use a custom job calling axfrOverTcp(..., tsigKey, transport) if the master requires it.
    • TLS - DoT/DoQ listeners on the server; for async client pulls use axfrOverTls or axfrOverTcp with TcpDnsClientTransport.createDoT().

Quick map from pattern to main APIs:

GoalServerClient / automation
Answer queries for my zone AuthoritativeZoneHandler + DnsListener (and TCP/DoT/DoQ if you need large responses or transfers) DnsResolver (stub clients), or any DNS client
Automate record changes READ_WRITE, tsigKey, requireTsig DnsZoneClient.sendUpdate, nsupdate
Notify downstream servers notifyPeer, notifyFromNsRecords Secondaries run Gumdrop (or BIND) with transfer allowed to them
Pull zone from a master (Gumdrop secondary) slaveOf(origin, master) (Master serves AXFR; secondary pulls automatically on NOTIFY)
Pull zone from any master (script/tool) - axfr, ixfr, axfrOverTcp, ixfrOverTcp, optional TSIG / DoT transport
Incremental transfer (IXFR) In-memory ZoneJournal after RFC 2136 updates on this instance ixfr(..., clientSoa) with the slave's current SOA in the authority section

Limits to plan around (not BIND parity): no allow-transfer ACL in the handler (use network policy until one exists); IXFR journal is in-memory and capped (restart or old serials fall back to AXFR); concurrent UPDATE, queries, and AXFR share one in-memory zone without explicit locking (keep change rate modest or serialize writers); NOTIFY and built-in secondary refresh are unsigned cleartext TCP AXFR unless you replace refresh with your own code. For resolver-only deployments, ignore this section and use DNS Resolver (Client).

Configuration

DnsServer.compose() wires listeners, optional TLS, and your query handler. Handler choice is independent of transport: the same AuthoritativeZoneHandler, UpstreamRelayHandler, or custom handler can serve UDP, DoT, and DoQ together.

Listeners

A DnsServer can have multiple listeners. Each listener invokes the same DnsQueryHandler over a different transport. You can combine any of the following:

ListenerClassTransportDescription
DnsListenerorg.bluezoo.gumdrop.dns.DnsListenerUDPStandard DNS over UDP, default port 53
DoTListenerorg.bluezoo.gumdrop.dns.DoTListenerTCP + TLSDNS over TLS (DoT), default port 853
DoQListenerorg.bluezoo.gumdrop.dns.DoQListenerQUICDNS over QUIC (DoQ), default port 853

Attach one or more listeners per server with .listener(...). For example, you can serve plain DNS on 5353 and DoT on 853 from the same server. All listeners on one DnsServer share the same DnsQueryHandler instance you pass to .handler(...).

Listener options

  • .port(int) - listening port (optional). If omitted, defaults are: DnsListener 53, DoTListener 853, DoQListener 853.
  • .addresses(InetAddress...) - bind addresses (default: all interfaces)

TLS/DTLS/QUIC Options (DoTListener, DoQListener)

DoT (TCP+TLS) and DoQ (QUIC) use the same in-tree TLS stack and the same TlsConfig as other listeners. DTLS on DnsListener follows the same rules when .secure(true) is set:

  • .secure(boolean) - enable DTLS/TLS (default: false; DoTListener is always secure)
  • .tls(TlsConfig) - keystore, PEM, or ServerCredentials identity material
  • setNeedClientAuth(boolean) - require client certificates (default: false)
  • setRequireRetry(boolean) - (DoQ only) require RFC 9000 section 8.1.2 Retry before accepting a new connection (default: true; set false for a trusted network)

Example Composition

// DNS proxy on non-privileged port
DnsServer dns = DnsServer.compose()
    .listener(new DnsListener().port(5353))
    .handler(UpstreamRelayHandler.builder()
        .upstreamServers("8.8.8.8 1.1.1.1")
        .cacheEnabled(true)
        .build())
    .server();

// DNS with DoT listener (same TlsConfig as HTTP/SMTP)
TlsConfig tls = TlsConfig.keystore(Path.of("keystore.p12"), "secret");
DnsServer dnsSecure = DnsServer.compose()
    .listener(new DnsListener().port(53))
    .listener(new DoTListener().port(853).secure(true).tls(tls))
    .handler(UpstreamRelayHandler.builder()
        .upstreamServers("8.8.8.8")
        .build())
    .server();

// DNS with UDP, DoT, and DoQ listeners (same keystore on DoT and DoQ)
DnsServer dnsFull = DnsServer.compose()
    .listener(new DnsListener().port(5353))
    .listener(new DoTListener().port(853).secure(true).tls(tls))
    .listener(new DoQListener().port(853).secure(true).tls(tls))
    .handler(UpstreamRelayHandler.builder()
        .upstreamServers("8.8.8.8 1.1.1.1")
        .cacheEnabled(true)
        .build())
    .server();

DNS Resolver (Client)

DnsResolver is an asynchronous DNS client for outbound lookups. It uses non-blocking I/O and delivers results via the DnsQueryCallback interface. Use it when your Gumdrop service needs to resolve names (e.g. MX lookups for SMTP, TXT for SPF/DKIM/DMARC, or A/AAAA for connecting to backends).

Using DnsResolver Inside Gumdrop Services

You can configure a DnsResolver as a component and inject it into services that need DNS. The resolver runs on the event loop. When you set the resolver's SelectorLoop to match the handler's endpoint (see SelectorLoop Affinity below), callbacks are invoked on the same thread as the handler, so you can safely update handler state from the callback without extra locking.

  • SMTP – resolve MX records, TXT for SPF/DKIM/DMARC
  • HTTP – resolve backends, certificate hostnames
  • Custom protocols – any service that needs name resolution

Configure upstream servers (e.g. upstream-servers or use-system-resolvers), then call queryA, queryTXT, queryMX, etc. with a DnsQueryCallback. Results and errors are delivered asynchronously.

SelectorLoop Affinity

When a DnsResolver is used from a Gumdrop service (e.g. an HTTP or SMTP handler), set the resolver's SelectorLoop to the same loop as the connection's endpoint. That way all DNS callbacks run on the same thread as the handler, avoiding cross-thread coordination.

Call setSelectorLoop(SelectorLoop) with the endpoint's loop before calling open(). If you do not set a SelectorLoop, the resolver uses an arbitrary Gumdrop worker loop; callbacks will still be correct but may run on a different thread than the handler that started the query. 

// In a handler that has access to the endpoint's SelectorLoop:
SelectorLoop loop = endpoint.getSelectorLoop();
resolver.setSelectorLoop(loop);
resolver.open();

resolver.queryTXT("_dmarc.example.com", new DnsQueryCallback() {
    public void onResponse(DnsMessage response) {
        // Runs on the same SelectorLoop thread as the handler
        for (DnsResourceRecord rr : response.getAnswers()) {
            if (rr.getType() == DnsType.TXT) {
                String txt = rr.getTxtData();
                // Use result...
            }
        }
    }
    public void onError(String error) {
        // Handle timeout or error
    }
});

In configuration, if your service obtains the resolver by reference (e.g. from the registry), the service's init() or the code that wires the resolver to the handler should set the SelectorLoop from the handler's endpoint when the first request arrives, or use a shared loop if your design assigns one loop per service.

Client Transports

The resolver uses a pluggable DnsClientTransport interface. The default is plain UDP, but you can select any of the following:

TransportClassRFCDefault Port
UDPUdpDnsClientTransport RFC 103553

DoTTcpDnsClientTransport (secure) RFC 7858853
DoQDoQClientTransport RFC 9250853

To use DoT, create a TcpDnsClientTransport with setSecure(true) and optionally configure SPKI fingerprints for the Strict privacy profile. For DoQ, use DoQClientTransport or DoQConnectionPool for persistent connections. For DoH, use DoHClientTransport and optionally set a custom URI path.

Truncated Response Retry

When a UDP response has the TC (truncated) flag set, DnsResolver automatically retries over TCP using standard DNS-over-TCP framing (2-byte length prefix, RFC 1035 section 4.2.2). The retry is transparent to the caller.

Async zone operations (DnsZoneClient)

For RFC 2136 updates, RFC 1996 NOTIFY, and RFC 5936 zone transfers (e.g. secondary refresh), use DnsZoneClient on a Gumdrop SelectorLoop. axfr tries UDP first and retries with axfrOverTcp when the response is truncated. ixfr sends the slave SOA in the authority section (RFC 1995) and retries over TCP when truncated. TCP transfers use RFC 1035 framing and complete when the server closes the connection (multi-message AXFR/IXFR). Pass an optional TsigKey to sign requests and verify responses (including chained TSIG on multi-message TCP transfers). For DNS-over-TLS, pass a configured TcpDnsClientTransport (e.g. TcpDnsClientTransport.createDoT()) to axfrOverTcp / ixfrOverTcp, or use axfrOverTls. Message construction helpers live on DnsZoneOperations.

SRV Record Queries

DnsResolver provides a convenience method for SRV lookups (RFC 2782) commonly used for service discovery: 

resolver.querySRV("_xmpp-server._tcp.example.com",
        new DnsQueryCallback() {
    public void onResponse(DnsMessage response) {
        for (DnsResourceRecord rr : response.getAnswers()) {
            System.out.println(rr.getSRVTarget() + ":"
                + rr.getSRVPort()
                + " (priority=" + rr.getSRVPriority()
                + ", weight=" + rr.getSRVWeight() + ")");
        }
    }
    public void onError(String error) {
        // Handle error
    }
});

Multicast DNS & DNS-SD

The org.bluezoo.gumdrop.mdns package implements multicast DNS (mDNS, RFC 6762) and DNS-SD (RFC 6763). Unlike the unicast dns package's caching proxy, mDNS is a peer protocol: every host on the local network both answers queries about itself and can query others, over a single shared UDP multicast group rather than client/server request-response to a fixed upstream. A Gumdrop instance running MdnsServer claims a .local hostname, defends it against conflicts, answers other hosts' queries for it, and (optionally) publishes DNS-SD records advertising its own other configured services.

Architecture

  • MdnsServer – owns configuration, the probing/announcing state machine for this instance's own hostname, the record cache, and the public query()/lookup() API
  • MdnsListener – the UDP multicast transport: binds port 5353 and joins the mDNS group (224.0.0.251) on every up, multicast-capable, non-loopback, non-point-to-point network interface
  • MdnsCache – the querier-side record cache, with RFC 6762 section 5.2 active refresh and section 10.2 cache-flush semantics
  • DnssdAdvertiser – builds RFC 6763 PTR/SRV/TXT records for this Gumdrop instance's own configured services

mDNS reuses the standard DNS wire format almost entirely — DnsMessage, DnsQuestion, DnsResourceRecord, DnsType, and DnsClass from the dns package are shared as-is between both packages (see Wire Format Extensions below for the two small additions mDNS needed). Everything else — the probing/announcing state machine, the active-refresh cache, and DNS-SD — is specific to the mdns package: mDNS is a continuous, stateful peer rather than the unicast proxy's largely stateless per-request model, so it needed its own cache and its own service/listener pair rather than extending DnsServer/DnsCache directly.

All mutable mDNS state (probe/announce state, the cache, pending timers) is touched only from datagram handling and timer callbacks, both of which are always invoked on the owning MdnsListener's single transport thread — there is no separate synchronization anywhere in the package.

Probing, Announcing & Withdrawal

On start(), MdnsServer runs the RFC 6762 section 8 lifecycle for its own hostname:

  1. Probing (section 8.1) – after a random 0–250ms delay, sends 3 probe queries 250ms apart, each asking whether anyone already has the proposed name and proposing this host's own address record(s) in the authority section
  2. Conflict detection – if a response arrives claiming the name with a different address, or another host wins a simultaneous-probe tie-break (section 8.2, by comparing proposed record data), the host renames itself (e.g. gumdrop → gumdrop-2) and restarts probing; losing a simultaneous-probe tie-break instead just waits one second and re-probes the same name, since that only decided probing order, not an existing claim
  3. Announcing (section 8.3) – once probing succeeds, sends two unsolicited responses (1 second apart) asserting its address record(s), with the cache-flush bit set so other hosts atomically replace anything they had cached under the old address
  4. Answering – while announced, answers matching queries from other hosts, honouring RFC 6762 section 7.1 known-answer suppression and the "QU" unicast-response-requested bit, and randomizing multicast replies by 20–120ms to avoid many responders answering in lockstep (section 6)
  5. Withdrawal (section 10.1) – on stop(), sends a "goodbye" packet: the same records with TTL 0, telling other hosts to remove them immediately

Check getCurrentName() (after isAnnounced() returns true) to find out what name was actually claimed, since it may not be the configured hostname verbatim if a rename happened.

Wire Format Extensions

mDNS repurposes the top bit (0x8000) of two wire-format fields that unicast DNS never uses: the QCLASS field's top bit is the "QU" bit (RFC 6762 section 5.4, a question asking for a unicast rather than multicast reply), and the RR CLASS field's top bit is the "cache-flush" bit (section 10.2, marking a record as the complete, authoritative answer for its name/type). These live on the shared dns package classes, since parsing an ordinary mDNS packet would otherwise fail outright with an "unknown class" error for any question or record using either bit:

  • DnsQuestion.isUnicastResponseRequested() – the QU bit; excluded from equals()/hashCode() since it's a transport hint, not part of question identity
  • DnsResourceRecord.isCacheFlush()
  • DnsResourceRecord.withCacheFlush() – returns a copy of a record with the bit set, for building unique (as opposed to shared, e.g. PTR) records
  • DnsResourceRecord.CACHE_FLUSH_BIT – the raw bit value, for callers constructing a record directly via the RFC 3597 raw-class-preserving constructor
  • DnsResourceRecord.txt(name, ttl, List<String>) – a TXT record from several independent character-strings (one per list entry), as DNS-SD's key=value attribute pairs need, distinct from the existing single-string txt(name, ttl, String) which splits one long value across the 255-byte character-string boundary instead

Querying & the Record Cache

Besides answering for its own hostname, MdnsServer can query for other hosts' records: 

mdnsService.query("printer.local", DnsType.A);
// ... answers arrive asynchronously as other hosts respond ...
List<DnsResourceRecord> answers = mdnsService.lookup("printer.local", DnsType.A);

Answers are kept in an MdnsCache, separate from the unicast DnsCache because mDNS caching works differently in two ways that matter: the cache-flush bit means "this is now the complete record set for this name/type" (anything cached but not re-asserted in a cache-flush batch is removed, though only after a one-second grace period in case a real response arrives split across more than one packet, per section 10.2), and each cached record actively re-queries itself at 80%, 85%, 90%, and 95% of its original TTL (section 5.2) so a lookup() result stays current without the caller needing to re-query. A "goodbye" (TTL 0) record gets the same one-second grace removal as a cache-flush eviction (section 10.1).

DNS-SD Service Advertisement

Once announced, MdnsServer (by default) also publishes RFC 6763 DNS-SD records for this Gumdrop instance's other configured services, so they're discoverable via dns-sd -B _services._dns-sd._udp local. or a Bonjour/Avahi browser. This reads gumdrop.getServers() at announce time, so the mdns server must be added to the Gumdrop instance last — call gumdrop.addServer(...) for every other server first; a server added after mdns won't have its listener ports picked up yet.

For each listener across every service, DnssdAdvertiser maps its getDescription() value to a DNS-SD service type using a deliberately conservative table of long-established Bonjour service types — not the full IANA registry, and not a guess at every protocol Gumdrop can serve:

Listener descriptionDNS-SD service type
http_http._tcp
https_https._tcp
ftp_ftp._tcp
imap_imap._tcp
imaps_imaps._tcp
pop3_pop3._tcp
pop3s_pop3s._tcp
smtp_smtp._tcp

A listener whose description isn't in this table — including internal-only listeners like cluster, and protocols without a clearly-established DNS-SD type such as mqtt, socks, or the WebSocket/HTTP3/DoQ variants — is silently skipped rather than treated as an error, so adding a new protocol listener elsewhere in Gumdrop never needs a matching change here just to avoid breaking. Use excluded-services (see Configuration) to also skip a normally-mapped one, e.g. to avoid advertising Gumdrop's own DNS resolver.

For each eligible listener, three records are generated: a PTR from the service type to a per-instance name (<host>._http._tcp.local), an SRV record for that instance giving its port and target host, and a TXT record (a single empty string, since RFC 6763 section 6.1 requires non-zero-length RDATA even with nothing to say). A PTR from _services._dns-sd._udp.local to each distinct service type advertised (RFC 6763 section 9) lets browsers enumerate what's available without knowing the types in advance. The PTR records are shared resource records and never carry the cache-flush bit; the SRV/TXT records are unique per-instance records and do.

Configuration

MdnsServer Setters

  • setHostname(String) – the label to probe for and advertise as <hostname>.local (optional). If omitted, the JVM's local hostname (domain suffix stripped) is used, falling back to "gumdrop"
  • setAdvertiseServices(boolean) – auto-advertise this instance's other configured services via DNS-SD (default: true)
  • setExcludedServices(String) – space-separated Listener.getDescription() values to never advertise via DNS-SD even if otherwise eligible (e.g. "dns")

MdnsListener Options

  • .port(int) – UDP port (default: 5353). mDNS's port isn't meaningfully configurable in practice — it's part of the protocol, and changing it means real mDNS clients on the network can no longer find this host; the setter exists mainly for testing

Example Composition

MdnsServer mdns = new MdnsServer();
mdns.setHostname("gumdrop");
mdns.setAdvertiseServices(true);
mdns.addListener(new MdnsListener());

// mDNS + DNS-SD auto-advertisement. Must be added to the Gumdrop
// instance LAST: DNS-SD reads every other server's listeners at
// announce time, once they're already registered.
gumdrop.addServer(otherServer1);
gumdrop.addServer(otherServer2);
gumdrop.addServer(mdns);

Note: mDNS's UDP port 5353 is the same port the DNS proxy example above uses for its non-privileged DnsListener (see Configuration) — running both on the same host collides. Use a different port for the unicast DnsListener, or omit it, if running both.

Known Limitations

  • IPv4 only – no ff02::fb IPv6 multicast group support yet
  • RFC 6762 section 8.2's simultaneous-probe tie-break compares a single representative address rather than the full RRset ordering algorithm (a real host usually only advertises one address, so this covers the common case)
  • DNS-SD's SRV/TXT records aren't put through mDNS probing before use, unlike the host's own address record(s)

UDP Protocol Support

The DNS server showcases Gumdrop's UDP protocol support through the UdpEndpoint abstraction, created via UdpTransportFactory. This demonstrates how to build UDP-based services within the event-driven framework.

UdpEndpoint

UdpEndpoint is the UDP equivalent of TcpEndpoint. Unlike TCP, there are no per-client endpoint objects—the server receives datagrams directly and sends responses to the source address. A UdpEndpoint is created by adding a UdpTransportFactory to a UdpListener. 

public abstract class UdpEndpoint extends Endpoint {
    
    // Override to handle incoming datagrams
    protected abstract void receive(ByteBuffer data, InetSocketAddress source);
    
    // Send a response datagram
    public void sendTo(ByteBuffer data, InetSocketAddress destination);
}

Key Differences from TCP

AspectTCP (TcpListener)UDP (UdpEndpoint)
Endpoint modelPer-client TcpEndpoint instances Single endpoint, multiple sources
Message boundariesStream-based, must frame Preserved per datagram
ReliabilityGuaranteed delivery Best-effort, may lose/reorder
TLS supportSSL/TLS DTLS

Building Custom UDP Services

The DNS server serves as a template for building other UDP-based services. Create a UdpListener with a UdpTransportFactory and provide an ProtocolHandler to process datagrams: 

UdpListener server = new UdpListener();
server.setPort(9000);
server.setDescription("my-service");
server.setTransportFactory(new UdpTransportFactory());
server.setHandlerFactory(new ProtocolHandlerFactory() {
    public ProtocolHandler createHandler() {
        return new MyUDPHandler();
    }
});

public class MyUDPHandler implements ProtocolHandler {
    
    @Override
    public void receive(ByteBuffer data, Endpoint endpoint) {
        // Parse the datagram
        MyProtocolMessage request = MyProtocolMessage.parse(data);
        
        // Process and generate response
        MyProtocolMessage response = process(request);
        
        // Send response back
        endpoint.write(response.serialize());
    }
}

The DNS server demonstrates patterns applicable to other UDP protocols:

  • VoIP/media - real-time audio/video streaming
  • SNMP agents - network management
  • Syslog servers - log collection
  • TFTP servers - simple file transfer
