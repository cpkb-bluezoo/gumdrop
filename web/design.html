History

Gumdrop began in 2005, the year Java published the NIO Selector API. Mainstream servers and servlet containers still used thread-per-connection blocking sockets: scalability was bounded by how many threads the JVM and operating system could sustain, not by how many idle connections you needed to hold open.

Gumdrop's first goal was a servlet container built on non-blocking I/O. It was, at that time, the first servlet container to fully decouple incoming connections from servlet worker threads: accept and socket I/O ran on a small selector pool, while application work could use a separate bounded executor. That separation later became the norm; Jetty and Tomcat incorporated similar models as async servlet support matured. The pattern is taken for granted today, but in 2005 it was the central trick that made large numbers of concurrent HTTP clients practical on a single JVM.

Once that architecture existed, the next step was to expose the framework underneath the HTTP stack and reuse it for other wire protocols including FTP and SMTP. Over the years the same reactor, endpoints, and staged handlers grew into the multi-protocol networking framework Gumdrop is now, still carrying a full servlet container on the same core.

Gumdrop fills a similar role to Netty: an extensible, asynchronous, non-blocking foundation for custom network services. The goals overlap, but the architecture and scope differ in ways that matter when you choose a stack or extend one. The sections below describe that design after two decades of refinement on the same event-driven foundation.

Reactor callbacks, not futures

Netty's programming model is built around channels, pipelines, and Future/Promise completion. Gumdrop is reactor-based: a fixed set of loops runs the hot path (accept, read, write, and handler callbacks) without blocking. Application code implements ProtocolHandler (or protocol-specific handler interfaces) that receive synchronous callbacks on a SelectorLoop thread: connected, receive(ByteBuffer), securityEstablished, disconnected, and so on.

Asynchronous vs synchronous

Traditional synchronous servers allocate one thread per connection. A thread blocks on socket read, processes the request, blocks on socket write, and repeats. This model is simple but has fundamental scalability limitations:

  • Thread overhead - each thread consumes stack memory (typically 1MB) and kernel resources; 10,000 connections require 10,000 threads
  • Context switching - the OS scheduler must switch between thousands of threads, consuming CPU cycles
  • Blocking I/O waste - threads spend most time waiting for network I/O, not doing useful work
  • Thundering herd - bursts of activity can exhaust thread pools

Gumdrop's reactor inverts this model. A small, fixed pool of worker threads (default: 2× CPU cores) runs the event loop for every connection, inbound or outbound:

  • Minimal threads - 10,000 connections can be served by 16 threads
  • No blocking - workers never block; when data isn't available, they move to the next ready connection
  • Efficient multiplexing - the OS Selector notifies workers when connections are ready
  • Predictable resource usage - memory and CPU scale with traffic, not connection count

One reactor for every role

The reactor pattern fits any network role. Servers accept many idle connections; clients and relays wait on upstream responses; peer nodes do both at once. In each case the worker thread never blocks on the socket: when one endpoint has no data, the loop services the next ready connection or datagram. That is why Gumdrop uses one architectural style for SMTP relays, HTTP microservices, MQTT brokers, and mesh peers instead of one stack for servers and another for clients.

SelectorLoop architecture

A single AcceptSelectorLoop thread handles accepting new connections on all server ports. When a connection is accepted, the resulting endpoint is assigned to one of a pool of worker SelectorLoop threads using round-robin distribution. Each endpoint is bound to a single worker for its entire lifetime, eliminating race conditions and simplifying state management.

Callbacks, not future pipelines

There is no second style of concurrency to learn for the hot path: you do not compose ChannelFuture chains or hop executor pools for each read. The model is closer to nginx or classic C event loops than to Netty's async/await ergonomics. That keeps relay and proxy code straightforward (server and client endpoints on the same selector thread, with SelectorLoop affinity) and makes backpressure explicit via Endpoint primitives such as pauseRead() and onWriteReady(Runnable) (see Endpoints and handlers).

Stateful wire protocols (SMTP, IMAP, POP3) use a staged handler pattern on top of the same reactor: typed stages instead of a single giant switch, still entirely callback-driven.

Servers and listeners

Gumdrop separates what a protocol server does from where it listens. A Server (such as HttpServer, SmtpServer, or FtpServer) owns application wiring: request or stream handlers, session providers, authentication, and lifecycle. Each server holds one or more Listeners that bind to ports, UNIX sockets, or UDP/QUIC endpoints and accept or receive traffic.

Listeners carry transport configuration: address, TLS or DTLS, ALPN, CIDR filtering, rate limits, and timeouts. Subclasses choose TCP, UDP, or QUIC via createTransportFactory(). One server often has several listeners (for example SMTP on port 25 and 465, or HTTP on TCP 80 and 443 and also QUIC).

Listeners can be static (declared when you compose the server) or dynamic (created at runtime). FTP data channels are the classic example: PASV/EPSV opens a short-lived listener registered on the FtpServer via addDynamicListener() and removed when the transfer ends. Server lifecycle stops static and dynamic listeners together on shutdown.

When AcceptSelectorLoop accepts a connection, the listener's createHandler() builds a ProtocolHandler (or a protocol-specific staged handler). Composition APIs attach session providers or handlers per listener so submission and relay ports can differ without duplicate server instances. See Application composition.

UNIX domain sockets

Any TCP-based listener can also bind to a UNIX domain socket by specifying a path instead of a port. This uses the standard NIO UNIX domain socket support (JEP 380, available on Java 25+). Once accepted, UNIX domain socket connections behave identically to TCP connections — the same SocketChannel, TcpEndpoint, and ProtocolHandler infrastructure is used unchanged.

UNIX domain sockets are useful for local inter-process communication where network overhead is unnecessary and filesystem permissions provide the security boundary. A common pattern is to expose a service on both TCP (for remote clients) and a UNIX socket (for local tools or reverse proxies): 

// TCP listener for remote clients
SmtpListener tcpListener = new SmtpListener().port(25);

// UNIX domain socket for local delivery
SmtpListener unixListener = new SmtpListener();
unixListener.path("/var/run/smtp.sock");

SmtpServer smtp = SmtpServer.compose()
    .listener(tcpListener)
    .listener(unixListener)
    .mailboxFactory(mbox)
    .sessionProvider(SmtpServerSessionProviders.localDelivery()
        .localDomain("example.com"))
    .server();

Calling both path and port(...) on the same listener is a configuration error — they're mutually exclusive. Stale socket files from previous runs are automatically removed on bind, and the socket file is deleted on shutdown.

Clients, servers, and peers

Outbound work uses the same reactor as inbound work. ClientEndpoint dials peers; ClientHandler receives the same style of lifecycle callbacks as server-side handlers (connected, data, security established, disconnected). ClientEndpointPool reuses connections with SelectorLoop affinity. Nothing about the API treats clients as a secondary concern: protocol client libraries (HTTP, SMTP, DNS, MQTT, and others) are built on these primitives alongside the server implementations.

Peer-to-peer nodes register listeners and create client endpoints on one Gumdrop instance, which is the intended way to build mesh or symmetric protocols. When a client is opened from an existing server connection (for example an SMTP relay), it can share the server's SelectorLoop. That SelectorLoop affinity provides:

  • Unified I/O - server and client I/O multiplexed on the same thread
  • No context switching - data flows without thread handoffs
  • Simplified state - no synchronisation needed between endpoints
  • Efficient relay - proxies and gateways operate entirely within their worker thread
  • Zero copy - no need to make copies of data to transfer between threads

Performing hot-path work on the selector thread is efficient but requires non-blocking code. Gumdrop supplies reactor-safe clients and push parsers for DNS, databases, message buses, and bodies of arbitrary size so server, client, and peer handlers can stay on the loop without ad hoc thread pools.

Endpoints and handlers

The architecture decouples transport I/O from protocol logic. Endpoint is the transport-agnostic I/O interface, providing:

  • send(ByteBuffer) - queues data for transmission
  • startTLS() - initiates STARTTLS upgrade
  • close() - closes the endpoint
  • isOpen() - tests whether the endpoint is active
  • getRemoteAddress(), getLocalAddress() - peer addresses
  • pauseRead(), resumeRead() - flow control for incoming data
  • onWriteReady(Runnable) - callback when the write buffer has drained

ProtocolHandler is the callback interface for protocol logic:

  • connected(Endpoint) - called when the endpoint is ready
  • receive(ByteBuffer) - called when data arrives
  • securityEstablished(SecurityInfo) - called after TLS handshake
  • disconnected() - called when the connection or stream is closed
  • error(Exception) - called on unrecoverable I/O or TLS failures

Protocol implementations (HTTP, SMTP, IMAP, etc.) implement ProtocolHandler rather than extending a base class. LineParser replaces the former LineBasedConnection for line-oriented protocols, using composition instead of inheritance. The framework handles read/write buffering, TLS encryption/decryption, and endpoint lifecycle.

Flow control

The Endpoint interface provides transport-level flow control that gives protocol handlers explicit control over the rate of data transfer. This is a simpler, more efficient alternative to the Reactive Streams specification: instead of introducing Publisher/Subscriber abstractions and demand-based signalling, Gumdrop exposes three primitives directly on the transport — pauseRead(), resumeRead(), and onWriteReady(Runnable) — that manipulate the underlying I/O interest set. This provides complete backpressure with zero object allocation overhead and no additional threading.

On TCP endpoints, pauseRead() clears the OP_READ interest on the SelectionKey, causing the selector to stop delivering data from that connection. The kernel TCP receive buffer fills, the TCP window shrinks, and the remote peer naturally slows down. Calling resumeRead() reverses this. For writes, onWriteReady(Runnable) registers a one-shot callback that fires when the transport has drained its write buffer, allowing protocol handlers to feed data in chunks without unbounded memory growth. All TCP-based protocols (SMTP, IMAP, POP3, FTP) and their client counterparts use these primitives for large transfers such as message retrieval, uploads, and file downloads.

Staged handler pattern

Stateful protocols such as SMTP, IMAP, and POP3 present a particular challenge: tracking the current protocol state and understanding what operations are valid at any given moment. This difficulty is compounded by event-driven architectures like Gumdrop, where the complexity of asynchronous callbacks can be bewildering.

Gumdrop addresses this with a staged handler pattern that compartmentalises protocol processing into discrete stages, each with clear goals and decisions:

  • Handler interfaces define callbacks for each protocol stage—the events your code receives at that point in the conversation
  • State interfaces define the operations available to respond—the valid transitions from that stage
  • Type safety ensures you can only perform operations valid for the current protocol state
  • Clear flow makes it obvious what decisions need to be made and what information is available

For example, an SMTP handler progresses through well-defined stages: 

ClientConnected → HelloHandler → MailFromHandler → RecipientHandler → MessageDataHandler

At each stage, the handler receives protocol events (EHLO, MAIL FROM, RCPT TO) and uses the provided state interface to accept, reject, or make policy decisions. The protocol handler manages all protocol mechanics — SASL authentication challenges, TLS negotiation, command parsing — leaving your session provider or handler to focus on business logic without managing sockets or framing.

Inbound and outbound handlers

The same staged pattern applies on the client side. An SMTP client handler receives events from the remote server (greeting, EHLO response, authentication challenges) and uses state interfaces to drive the conversation forward. That symmetry is deliberate: relays, gateways, and P2P nodes pair an inbound staged handler with an outbound one on the same reactor thread.

Built-in servers

Gumdrop ships ready-to-use Server compositions as embeddable, plug-in services. Register them on the same Gumdrop instance as your own handlers to stand up real protocol behaviour in integration tests, local development, or production (for example a DNS forwarder, MQTT broker, or mail sink beside your application). They are part of the framework, not separate products. In many deployments, composing a built-in server with the right session provider or request handler is enough without writing low-level protocol code, and each implementation doubles as a reference for your own handlers.

  • WebDAV - WebDAVRequestHandler serves static files over HTTP from a filesystem root, with optional WebDAV (RFC 4918) authoring and locking
  • Servlet container - ServletRequestHandler hosts JSP and servlet applications with clustering and deployment
  • FTP - FtpServer.compose() with FileSystemFtpSessionProvider (optionally read-only), RoleBasedFtpSessionProvider (roles and quotas), or AnonymousFtpSessionProvider (public read-only distribution)
  • SMTP - SmtpServer.compose() with LocalDeliverySessionProvider for mailbox delivery or SimpleRelaySessionProvider for MX forwarding
  • IMAP and POP3 - ImapServer and Pop3Server with the mailbox session provider, using the configured Realm and MailboxFactory
  • DNS - DnsServer with a caching forwarder (UpstreamRelayHandler) and/or authoritative zones (AuthoritativeZoneHandler); see examples/dns-authoritative/
  • MQTT - MqttServer.compose() with no session provider is a complete MQTT 3.1.1/5.0 broker using the configured Realm
  • SOCKS - SocksServer.compose() with no session provider is a SOCKS4/4a/5 proxy with destination filtering and relay limits, and an optional Realm for SOCKS5 authentication

Handlers in your own HTTP microservices can call other Gumdrop clients on the inbound request's worker thread via SelectorLoop affinity, which keeps gateway and BFF-style chains on the reactor.

Datagram facilities

For UDP-based protocols, UdpEndpoint (via UdpTransportFactory) provides the same event-driven model. The ProtocolHandler interface is reused: receive() delivers individual datagrams and sendTo() addresses responses to the source.

The DNS server demonstrates this abstraction, providing a complete DNS proxy that can be subclassed for custom name resolution. DTLS (TLS for UDP) is supported transparently, with per-remote-address session management handled automatically.

Endpoint lifecycle

Servers provide configurable endpoint lifecycle management:

  • Idle timeout - close endpoints with no activity (default: 5 minutes)
  • Read timeout - maximum wait for data during active read (default: 30 seconds)
  • Connection timeout - time allowed for initial connection and TLS handshake (default: 60 seconds)

Timeouts can be configured with time unit suffixes (ms, s, m, h): 

ImapListener listener = new ImapListener();
listener.idleTimeoutMs(30 * 60 * 1000L);
listener.setReadTimeout("60s");
listener.setConnectionTimeout("2m");
ImapServer imap = ImapServer.compose()
    .listener(listener)
    .realm(realm)
    .sessionProvider(ImapServerSessionProviders.mailbox(maildirFactory))
    .server();

Endpoints track timestamps for creation, last activity, and connection establishment (after TLS handshake for secure endpoints). These are accessible via getTimestampCreated(), getTimestampLastActivity(), and getTimestampConnected().

Standard NIO buffers

Gumdrop uses java.nio.ByteBuffer from the socket through TLS, QUIC, HTTP/2 framing, and application handlers. There is no proprietary ByteBuf type, no separate allocator API, and no reference-counting discipline to master before you can safely pass data into your own code.

If you already work with Java NIO, or you integrate with libraries that consume ByteBuffer, the boundary stays thin. Parsing components (Gonzalez, jsonparser, jprotobuf, line parsers, HPACK/QPACK) all accept incremental receive(ByteBuffer) feeds.

In-tree TLS, DTLS, and QUIC

Gumdrop ships a pure Java TLS 1.2/1.3 and DTLS stack, plus the QUIC implementation used for HTTP/3, all with curated secure defaults and no native libraries. TLS is transparent to protocol handlers: any endpoint can run implicit TLS, STARTTLS, DTLS, or QUIC. Gumdrop 3 requires Java 25 (LTS) so the stack can use the JDK's ML-KEM and ML-DSA for post-quantum key exchange and certificates. See QUIC, TLS & DTLS for the architecture, the Java 25 baseline, cipher profiles, configuration, and RFC conformance.

Push parsing and streaming codecs

From the bottom up, Gumdrop favours push parsers: data arrives in ByteBuffer chunks and codecs emit events as they go. The goal is constant memory and full streaming for large payloads, not buffer-then-parse workflows.

  • Line-oriented protocols (SMTP, IMAP, POP3, FTP control) via LineParser and staged handlers
  • HTTP request/response events, chunked bodies, HTTP/2 frame decoding, HPACK/QPACK
  • XML and JSON microservices via Gonzalez and jsonparser (see Building Microservices)
  • Protobuf via jprotobuf for gRPC and other binary APIs (see gRPC)
  • DNS message parsing for the resolver and server stack (see DNS)

Application handlers are expected to stream: pass each bodyContent(ByteBuffer) chunk straight into a parser instead of materialising the full body first.

Protocols, DNS, telemetry, servlets

Netty's ecosystem is centred on HTTP; other protocols usually mean additional libraries or your own codecs. Gumdrop instead ships first-party protocol implementations on the same reactor, sharing authentication (Security), transport configuration, and the built-in asynchronous DNS client that outbound connections use. The main page lists them all, from HTTP/1.x through HTTP/3 to mail, FTP, DNS, MQTT, SOCKS, WebSocket, gRPC, LDAP, AMQP, and Redis, plus a full servlet container on the same core. OpenTelemetry tracing and metrics are integrated in-tree with OTLP export (see Telemetry), with no separate Java agent.

Performance and deployment size

Gumdrop's core is intentionally smaller than a typical Netty HTTP stack: fewer pipeline layers and no parallel buffer abstraction. It ships as modules, so a deployment includes only the protocols it uses. A typical complete HTTP microservice needs gumdrop-core (1.6 MB), gumdrop-http (0.7 MB), gumdrop-mime (0.1 MB), and gumdrop-telemetry (0.1 MB), about 2.5 MB in all.

Those modules depend on four small libraries: Gonzalez (XML, 150 KB), jsonparser (JSON, 31 KB), jprotobuf (protobuf for OTLP export, 15 KB), and micula (Brotli, used for HTTP content encoding and TLS certificate compression, 437 KB). That brings the complete deployment to about 3.1 MB. The servlet container is a separate gumdrop-servlet module (0.6 MB), and the self-contained servlet fat JAR (gumdrop-container.jar) is about 7.3 MB with its bundled dependencies. See docs/FRAMEWORK-COMPARISON.md in the source tree for sizes versus Netty, Jetty, Tomcat, and Spring Boot. Matched feature for feature (HTTP/1.x to HTTP/3, Brotli, XML and JSON parsing, and OpenTelemetry), the equivalent Netty deployment is about 13.6 MB, because HTTP/3 needs the native quiche addon, Brotli needs native brotli4j, and the OpenTelemetry SDK brings OkHttp and the Kotlin runtime. Neither total includes asynchronous DNS resolution, which is built into Gumdrop's core but an extra add-on in Netty, since it mainly matters for inter-service client calls.

Throughput and CPU are in the same class as Netty for raw HTTP servers, and Gumdrop is ahead on several scenarios in the project's repeatable harness. The scripts live under test/benchmark: paired Gumdrop and Netty servers, same load client, back-to-back runs on loopback. Scenarios include plaintext and TLS HTTP/1.1, JSON POST, HTTP/2, and HTTP/3 (pure Java QUIC on Gumdrop versus Netty's native quiche transport). Treat absolute numbers as directional on a shared machine; the README in the repository records representative results and methodology.
