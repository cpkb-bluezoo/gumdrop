History

Gumdrop began in 2005, the year Java published the NIO Selector API. Mainstream servers and servlet containers still used thread-per-connection blocking sockets: scalability was bounded by how many threads the JVM and operating system could sustain, not by how many idle connections you needed to hold open.

Gumdrop's first goal was a servlet container built on non-blocking I/O. It was, at that time, the first servlet container to fully decouple incoming connections from servlet worker threads: accept and socket I/O ran on a small selector pool, while application work could use a separate bounded executor. That separation later became the norm; Jetty and Tomcat incorporated similar models as async servlet support matured. The pattern is taken for granted today, but in 2005 it was the central trick that made large numbers of concurrent HTTP clients practical on a single JVM.

Once that architecture existed, the next step was to expose the framework underneath the HTTP stack and reuse it for other wire protocols including FTP and SMTP. Over the years the same reactor, endpoints, and staged handlers grew into the multi-protocol networking framework Gumdrop is now, still carrying a full servlet container on the same core.

Gumdrop fills a similar role to Netty: an extensible, asynchronous, non-blocking foundation for custom network services. The goals overlap, but the architecture and scope differ in ways that matter when you choose a stack or extend one. The sections below describe that design after two decades of refinement on the same event-driven foundation.

Reactor callbacks, not futures

Netty's programming model is built around channels, pipelines, and Future/Promise completion. Gumdrop is reactor-based: a small pool of SelectorLoop threads multiplex I/O with java.nio.channels.Selector, and application code implements ProtocolHandler (or protocol-specific handler interfaces) that receive synchronous callbacks on that thread: connected, receive(ByteBuffer), securityEstablished, disconnected, and so on.

There is no second style of concurrency to learn for the hot path: you do not compose ChannelFuture chains or hop executor pools for each read. The model is closer to nginx or classic C event loops than to Netty's async/await ergonomics. That keeps relay and proxy code straightforward (server and client endpoints on the same selector thread, with SelectorLoop affinity) and makes backpressure explicit via Endpoint primitives such as pauseRead() and onWriteReady(Runnable).

Stateful wire protocols (SMTP, IMAP, POP3) use a staged handler pattern on top of the same reactor: typed stages instead of a single giant switch, still entirely callback-driven.

Standard NIO buffers

Gumdrop uses java.nio.ByteBuffer from the socket through TLS, QUIC, HTTP/2 framing, and application handlers. There is no proprietary ByteBuf type, no separate allocator API, and no reference-counting discipline to master before you can safely pass data into your own code.

If you already work with Java NIO, or you integrate with libraries that consume ByteBuffer, the boundary stays thin. Parsing components (Gonzalez, jsonparser, jprotobuf, line parsers, HPACK/QPACK) all accept incremental receive(ByteBuffer) feeds.

In-tree TLS, DTLS, and QUIC

Gumdrop ships a pure Java TLS 1.2/1.3 and DTLS stack, plus a QUIC implementation used for HTTP/3. Cipher suites and protocol versions are curated for secure defaults rather than mirroring JSSE's permissive "support everything" posture. Details are on the TLS & DTLS page.

Netty typically relies on the JDK's JSSE for TCP TLS. For QUIC and HTTP/3, Netty's incubator transport uses native code (Cloudflare quiche with BoringSSL behind JNI), which adds platform-specific artifacts and deployment constraints. Gumdrop's QUIC/TLS path stays in the same JVM bytecode as the rest of the framework, with no native library build step.

Java 25 baseline and post-quantum TLS

Gumdrop 3 requires Java 25 (LTS) or newer. That bar is intentional: modern JDK cryptography exposes ML-KEM and ML-DSA through the standard JCA, which Gumdrop's in-tree TLS engine uses for hybrid post-quantum key exchange (RFC 10024) and for PKIX validation of post-quantum certificates. Hybrid groups are offered by default in TLS 1.3, DTLS, and QUIC; signature schemes include ML-DSA alongside classical algorithms. See TLS & DTLS for cipher profiles, named groups, and how to confirm what negotiated on a live connection.

Staying on a current LTS with first-class post-quantum primitives is part of Gumdrop's broader security posture: curated protocol versions and ciphers rather than JSSE's permissive defaults, plus TLS, IAM, and rate limiting applied consistently across protocols (Security).

Push parsing and streaming codecs

From the bottom up, Gumdrop favors push parsers: data arrives in ByteBuffer chunks and codecs emit events as they go. The goal is constant memory and full streaming for large payloads, not buffer-then-parse workflows.

  • Line-oriented protocols (SMTP, IMAP, POP3, FTP control) via LineParser and staged handlers
  • HTTP request/response events, chunked bodies, HTTP/2 frame decoding, HPACK/QPACK
  • XML and JSON microservices via Gonzalez and jsonparser (see Building Microservices)
  • Protobuf via jprotobuf for gRPC and other binary APIs (see gRPC)
  • DNS message parsing for the resolver and server stack (see DNS)

Application handlers are expected to stream: pass each bodyContent(ByteBuffer) chunk straight into a parser instead of materialising the full body first.

Protocols, DNS, telemetry, servlets

Netty's ecosystem is centred on HTTP; other protocols usually mean additional libraries or your own codecs. Gumdrop ships a coherent set of first-party implementations on the same reactor, sharing authentication (Security), transport configuration, and the built-in asynchronous DNS client that outbound connections use.

That includes HTTP/1.x, HTTP/2, and HTTP/3, mail (SMTP, IMAP, POP3), FTP, DNS (forwarding, authoritative zones, mDNS), MQTT, SOCKS, WebSocket, gRPC, LDAP, AMQP, and Redis clients, plus a full servlet container that scales on the same event-driven core (see Servlet Container). OpenTelemetry tracing and metrics are integrated in-tree with OTLP export (see Telemetry), without requiring a separate Java agent.

Performance and deployment size

Gumdrop's core is intentionally smaller than a typical Netty HTTP stack: fewer pipeline layers and no parallel buffer abstraction. The main gumdrop.jar artifact is on the order of 2.5 MB; a self-contained servlet fat JAR is about 5.2 MB (see docs/FRAMEWORK-COMPARISON.md in the source tree for measured sizes versus Netty, Jetty, Tomcat, and Spring Boot).

Throughput and CPU are in the same class as Netty for raw HTTP servers, and Gumdrop is ahead on several scenarios in the project's repeatable harness. The scripts live under test/benchmark: paired Gumdrop and Netty servers, same load client, back-to-back runs on loopback. Scenarios include plaintext and TLS HTTP/1.1, JSON POST, HTTP/2, and HTTP/3 (pure Java QUIC on Gumdrop versus Netty's native quiche transport). Treat absolute numbers as directional on a shared machine; the README in the repository records representative results and methodology.
