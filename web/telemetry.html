Gumdrop Telemetry and Logging

← Back to Main Page

Gumdrop includes a native telemetry implementation for logging, distributed tracing, metrics, and observability. It speaks the same wire formats and conventions as the OpenTelemetry ecosystem (OTLP export, W3C Trace Context, semantic attributes) but provides its own Java API, designed for Gumdrop's event-driven, multiplexed I/O model. One TelemetryConfig per runtime decides where everything goes: operational log events, HTTP access log entries, QUIC qlog events, traces and metrics. Destinations are objects composed in code: the console through java.util.logging, an OpenTelemetry Collector over OTLP/HTTP or OTLP/gRPC, JSONL files, an access log file in Common Log Format, or a qlog directory, alone or in any combination. Built-in instrumentation is provided for the HTTP, SMTP, IMAP, POP3 and FTP servers and for the session replication cluster. The API enables custom instrumentation and custom log events for any Gumdrop-based service.

Overview

The telemetry system provides:

  • Structured log events - operational events (startup, errors, security decisions) are records with a key and named attributes, not pre-formatted strings, so a console, a collector and a log file can each take what they need from the same event
  • HTTP access logging - one record per completed request, written in Common Log Format or W3C Extended Log File Format, exported through OTLP, or both
  • Distributed tracing - trace requests across service boundaries using W3C Trace Context (traceparent header)
  • Metrics collection - counters, histograms, and gauges with configurable aggregation temporality (delta or cumulative)
  • Hierarchical spans - represent operations as a tree of spans with timing, attributes, and events
  • Composable exporters - the destinations form a tree you build with ordinary objects; each exporter takes only the kinds of record it is configured for
  • OpenTelemetry ecosystem compatibility - exports via OTLP/HTTP or OTLP/gRPC to any OpenTelemetry Collector, or to JSONL files for local analysis; uses W3C Trace Context and familiar span kinds and attributes
  • Never on the I/O thread's critical path - every exporter queues records and delivers them from a thread of its own
  • Zero-dependency - self-contained protobuf serialization; no OpenTelemetry Java SDK or agent on the application classpath (see why Gumdrop does not use the OpenTelemetry SDK)

Core Concepts

  • TelemetryConfig - the one object that holds service identity, exporter settings and the exporter tree. A Gumdrop runtime has exactly one
  • Log event - a record with a level, a key naming what happened, attributes describing it, and optionally an exception and the span it happened in
  • Level - INFO, WARN and ERROR for operational events, ACCESS for HTTP access records and QLOG for QUIC qlog events. Exporters are matched to records by level
  • Exporter - a destination for records, traces and metrics
  • Trace - a collection of spans representing a single request flow; identified by a 128-bit trace ID
  • Span - a unit of work with name, timing, attributes, events, and status; forms parent-child relationships
  • SpanKind - categorises the span's role: SERVER, CLIENT, PRODUCER, CONSUMER, or INTERNAL
  • Attribute - key-value metadata attached to spans and log events (string, boolean, integer, or double)
  • Event - timestamped occurrence within a span (e.g., "message sent", "exception thrown")

Gumdrop API vs OpenTelemetry Java API

Gumdrop deliberately does not adopt the OpenTelemetry Java API (io.opentelemetry.api) or SDK for application instrumentation. Observability backends and collectors are unchanged: you still send standard OTLP to an OpenTelemetry Collector and use the same trace IDs, span kinds, and semantic conventions in your dashboards. What differs is only how you instrument Java code running on Gumdrop.

Why a native API

Gumdrop servers use a small number of worker threads (SelectorLoops). Each worker multiplexes many concurrent connections: it is not a thread-per-connection or thread-per-request model. A single thread may handle events for connection A, then connection B, then a timer or client callback, before returning to A. That design is efficient and is the same model used for non-blocking HTTP clients, OTLP export, and protocol handlers throughout the stack.

The OpenTelemetry Java API is commonly used with implicit context: Context.current() is stored in thread-local storage by default, and many libraries assume that whatever span is “current” on this thread belongs to the operation in progress. On a multiplexed worker that assumption breaks unless every entry and exit point perfectly installs and clears context. A missed Scope close, or an async continuation that runs later on the same thread without restored context, can attach attributes or outbound trace headers to the wrong connection. Under load these mistakes are easy to make and hard to spot in tests.

Gumdrop's telemetry API is built for this runtime:

  • Explicit trace carrier - the active trace lives on the connection (Endpoint.getTrace() / setTrace()) and on request objects (for example HTTP streams), not on an implicit thread slot.
  • Current span within a trace - Trace.startSpan() and Span.makeCurrent() update the current span on that Trace instance. Scopes restore the previous span on the same trace when closed; they do not claim the whole thread for unrelated work.
  • Explicit outbound propagation - the HTTP client propagates traceparent when you call HttpClient.setTrace(...) (or set the header yourself). There is no hidden reliance on thread-local state at send time.
  • Async-friendly discipline - continuations should receive the Trace (or span) they belong to, the same way Gumdrop passes Endpoint and handler state. That matches how built-in instrumentation already works.

Importing the OpenTelemetry Java SDK would add classpath weight and invite use of patterns (global OpenTelemetry, auto-configuration, libraries that read Context.current()) that are a poor fit for multiplexed SelectorLoop servers. Gumdrop 3 standardises on the native org.bluezoo.gumdrop.telemetry types for custom spans and metrics; they are consistent with built-in protocol instrumentation and safe when used with explicit trace and client wiring as documented below.

Could we use the OpenTelemetry API classes alone?

We evaluated using just the API types (io.opentelemetry.api) without the SDK, to give developers who already know OpenTelemetry a familiar vocabulary. We concluded the benefit did not justify the cost:

  • The context model is in the API itself - Context, Scope and Span.current() are part of the API, and their default implementation is thread-local. Adopting the types means adopting the implicit-context idioms that every OpenTelemetry tutorial and instrumentation library teaches, which is precisely what is unsafe on a multiplexed SelectorLoop.
  • Familiarity would be misleading - code that looks like standard OpenTelemetry but must follow different rules (explicit trace, no ambient context) is more likely to be misused than an API that is visibly different. The Gumdrop concepts (trace, span, span kind, attributes, events, metric instruments) map directly onto the OpenTelemetry ones, so the learning cost for an OpenTelemetry user is small.
  • Extra dependency and security surface - Gumdrop keeps its runtime dependencies minimal. Each additional library must be tracked for vulnerabilities and kept up to date, and the API would be a compile-time dependency of every module that creates spans, with its own release cadence.
  • Nothing is lost on the wire - interoperability is defined by OTLP and W3C Trace Context, not by Java classes. Gumdrop implements both directly, so any OpenTelemetry Collector or compatible backend works unchanged.

This is a considered engineering decision rather than a permanent one, and it can be revisited if the trade-offs change.

What this means for you

  • Use Gumdrop types - TelemetryConfig, Trace, Span, and metrics.Meter for custom instrumentation, servlets, protocol handlers, and microservices hosted on Gumdrop.
  • Interoperate at the wire - propagate W3C traceparent to and from other services (Java or not) that use OpenTelemetry, Jaeger, Zipkin, or any collector that understands Trace Context.
  • Do not expect the OTel Java agent or API - dropping the OpenTelemetry Java agent or depending on third-party libraries that require the OTel Java API and implicit context is unsupported and likely to produce incorrect traces on Gumdrop.
  • Prefer explicit propagation for outbound calls - pass state.getTrace() (or the relevant trace) into HttpClient.setTrace() before outbound requests so client spans stay on the same distributed trace; see Distributed Tracing.

If you are migrating from a thread-per-request framework, replace “start span and rely on thread context” with “obtain the trace from the Gumdrop request or endpoint, start child spans on that trace, and pass that trace into clients and async callbacks.” The extra clarity is intentional: it matches how the server actually schedules work.

Configuration

Everything telemetry does is driven by one TelemetryConfig. It holds the identity of the service, the settings the exporters share, and the exporter tree that says where records, traces and metrics go. There is no separate "logging configuration" and no "enabled" flag: what is configured is what happens.

A Gumdrop runtime has exactly one TelemetryConfig. It is set on the runtime with telemetryConfig, before servers are added, and every listener, endpoint, client and component on that runtime reaches it from there. A runtime that is never given one has a default configuration whose only exporter prints operational events through java.util.logging and takes nothing else: Gumdrop logs to the console as it always has, with no telemetry code of your own.

Composing a configuration

Gumdrop configures itself by composition, and telemetry is no exception. You create the configuration, create the exporters you want, arrange them, and hand the result to the runtime: 

TelemetryConfig telemetry = new TelemetryConfig();

// Service identification, shared by every exporter
telemetry.serviceName("mail-gateway")
         .serviceVersion("2.1.0")
         .deploymentEnvironment("production");

// An exporter and its own settings - use HTTPS in production
OtlpExporter otlp = new OtlpExporter()
        .endpoint("https://otel-collector:4318")
        .batchSize(256);

// The exporter tree: a collector, plus the console
telemetry.exporter(new TeeExporter(otlp, new DefaultExporter()));

// Starts the exporters
telemetry.init();

Gumdrop gumdrop = Gumdrop.boot();
gumdrop.telemetryConfig(telemetry);
gumdrop.addServer(server);

Six things are worth knowing about this arrangement.

  • There is always an exporter. A new configuration starts with a DefaultExporter, and exporter will not accept null. If you replace it with an OtlpExporter alone, operational events no longer reach the console; add the DefaultExporter back, as above, if you want both.
  • Exporters are matched by level. Each exporter has a set of record levels it takes (see Log events and levels) and whether it takes traces. Every record is offered to the whole tree and each exporter keeps what is meant for it. The same event can go to the console, to a collector and to a file in one emit.
  • The tree is made of two-way tees. A TeeExporter has exactly two children. For three destinations nest one tee inside another: 
    telemetry.exporter(new TeeExporter(
        new TeeExporter(otlp, new DefaultExporter()),
        accessLog));
    A failure in one child does not stop delivery to the other.
  • Settings are fluent methods named for the setting. As on listeners and clients (port(8080), tls(...), secure(true)), a setting is a method named for it, such as endpoint(...) or batchSize(...), which takes the value and returns the object, so calls chain. The matching getters are getEndpoint() and so on.
  • Each exporter is configured on itself. An endpoint, a batch size or a TLS configuration is a setting of the exporter that uses it, made on the exporter object, so a tree can hold two exporters configured differently. TelemetryConfig holds only what is true of the service as a whole (see Settings).
  • Order of operations. Make the settings of the configuration and of each exporter, set the exporter tree, call init(), then give the configuration to the runtime. An exporter does nothing until init() starts it: that is when it opens its files, connects and starts its thread, and why its settings can be made after it is constructed. init() also registers the JMX bridge and honours the QLOGDIR environment variable (see qlog exporter). An exporter set after init() has run is started at once.

Choosing exporters per record

The exporters that carry operational events (DefaultExporter, OtlpExporter, OtlpGrpcExporter, OtlpFileExporter) take INFO, WARN and ERROR by default. levels changes that. For example, to keep the console to warnings and errors while the collector gets everything, and to send the access log to the collector as well as to a file: 

DefaultExporter console = new DefaultExporter();
console.levels(LogLevel.WARN, LogLevel.ERROR);

OtlpExporter otlp = new OtlpExporter();
otlp.endpoint("https://otel-collector:4318");
otlp.levels(LogLevel.INFO, LogLevel.WARN, LogLevel.ERROR, LogLevel.ACCESS);

AccessLogExporter accessLog = new AccessLogExporter(
        Path.of("/var/log/gumdrop/access.log"),
        AccessLogFormat.CLF, AccessLogUserSelection.PROTOCOL_FIRST);

telemetry.exporter(new TeeExporter(
        new TeeExporter(console, otlp),
        accessLog));

Code that would otherwise do work to build a record can ask whether anyone wants it first with telemetry.accepts(LogLevel.ACCESS); a level nobody accepts costs a single check.

Logging

Gumdrop's operational logging is built on the same structured pipeline as its traces and metrics. A component does not format a message and print it; it states what happened as an event, and the exporters configured on the runtime decide how that event is presented and where it goes. The same event may be printed on the console by a human-readable formatter, shipped to a collector as a structured OTLP log record, and written to a JSONL file, without the component knowing or caring.

Log events and levels

A log event is a LogRecord with:

  • a level, which decides which exporters receive it;
  • a key naming the event, such as warn.server_push_failed. The key is stable and machine-friendly: it is the name a collector indexes, and it is also the key of the human-readable message in the component's resource bundle;
  • zero or more named attributes (string, long, double or boolean) describing the event, in order;
  • optionally a throwable, and the span the event happened in, so that logs can be correlated with traces by trace and span ID.
LevelOTLP severityMeaningTaken by default by
INFOINFO (9)An operational event of note: a server started, a certificate loadedDefault, OTLP and JSONL exporters
WARNWARN (13)A condition that may need attentionDefault, OTLP and JSONL exporters
ERRORERROR (17)An operational failureDefault, OTLP and JSONL exporters
ACCESSINFO (9)One completed HTTP request (see HTTP access log)Access log exporter only
QLOGDEBUG (5)One QUIC or HTTP/3 qlog event (see qlog exporter)qlog exporter only

ACCESS and QLOG records are kept apart from the operational levels deliberately. Access records are numerous and belong in an access log, not on the console; qlog events are numerous again. An exporter that wants them must ask: for example otlp.levels(LogLevel.INFO, LogLevel.WARN, LogLevel.ERROR, LogLevel.ACCESS) sends access records to a collector too.

How an event reaches its destinations

  1. A component obtains an EventLogger from the runtime's TelemetryConfig. The logger remembers the component's class (the instrumentation scope of its events) and its resource bundle.
  2. The component starts an event with info, warn or error, adds attributes, and calls emit(). If no exporter in the tree accepts the level, nothing is built.
  3. The record is offered to the exporter tree. Each TeeExporter passes it to both children; each leaf exporter keeps it if it accepts the level and ignores it otherwise.
  4. Each exporter that kept the record puts it on a bounded queue and returns. A thread of the exporter's own does the work of formatting and writing or sending, so the thread that emitted the event, typically a selector loop handling connections, never waits on a console, a file or the network.

Three guarantees follow from this design. An exporter that throws does not break the code that emitted the event or the other exporters. An exporter that itself logs through the pipeline (reporting a failed write, say) does not re-enter it: such reports go straight to java.util.logging. And a full queue drops records rather than blocking: the default, access log and qlog exporters count what they dropped and report the number when they shut down.

Emitting events from your own code

Your own handlers and servers log the same way the framework does. A class gets its EventLogger once, from the configuration it reaches through the endpoint (or, in other code, from the runtime), and builds events with a short fluent chain: 

public class OrderHandler implements ProtocolHandler {

    private static final ResourceBundle L10N =
            ResourceBundle.getBundle("com.example.orders.L10N");

    private EventLogger events;

    @Override
    public void connected(Endpoint endpoint) {
        events = endpoint.getTelemetryConfig().getLogger(OrderHandler.class, L10N);
        events.info("info.order_session_opened")
              .attr("remote", endpoint.getRemoteAddress().toString())
              .emit();
    }

    void paymentFailed(String orderId, long cents, IOException e) {
        events.error("err.payment_failed")
              .attr("order", orderId)
              .attr("cents", cents)
              .thrown(e)
              .emit();
    }
}
  • getLogger(Class, ResourceBundle) returns the same logger for the same class and bundle every time, so it may be called freely.
  • attr has overloads for String, long, double and boolean. Names are what a collector sees; the order is what the console message sees (see below).
  • span(span) stamps the record with the trace and span IDs of a Span, so a collector can show the event beside its trace.
  • endpoint.getTelemetryConfig() never returns null. A component with no endpoint can use gumdrop.getTelemetryConfig().
  • There is no static logging method. Events always go through the configuration of the runtime they belong to; that is what makes two runtimes in one JVM, or a test that records events, possible.

Messages and localisation

The key of an event is looked up in the resource bundle of the emitting class. The attributes, in the order they were added, are the positional MessageFormat arguments of the message: 

# L10N.properties
err.payment_failed=Payment for order {0} failed ({1} cents)

Gumdrop's bundles are provided for English, German, Spanish and French, and the console follows the JVM's default locale. Only the DefaultExporter performs this lookup. OTLP and JSONL exporters do not render the message at all: they carry the key as the event name and the attributes by name, so that a backend can group, count and alert on a stable key rather than on text that changes with the locale or the wording. The bundle is a presentation concern of the console, not part of the event.

Events on the wire

OTLP/HTTP, OTLP/gRPC and JSONL all serialise an operational record as an OTLP LogRecord:

OTLP fieldContent
instrumentation scopeThe name of the emitting class; log records are grouped by scope
event_nameThe record's key, such as warn.server_push_failed
severity number and textFrom the level (table above)

trace ID, span IDPresent when the event was tied to a span
exception.typeThe class name of the throwable, if any
exception.message, exception.stacktraceOnly when includeExceptionDetails(true)
resourceService name, version, namespace, instance ID, environment and any added resource attributes

There is no pre-formatted body. A record's body is used only for events that are themselves data, such as the contents of a qlog event.

Fine-grained logging stays on JUL

Events at the three operational levels are the ones an operator reads. The detailed tracing of a protocol exchange, at the FINE, FINER and FINEST levels of java.util.logging, remains plain JUL in the code. It is for developers diagnosing a problem, it is cheap to leave disabled, and logging.properties is exactly the right tool for turning it on for one package: 

# logging.properties
handlers=java.util.logging.ConsoleHandler
java.util.logging.ConsoleHandler.level=ALL
java.util.logging.ConsoleHandler.formatter=org.bluezoo.gumdrop.util.LaconicFormatter
org.bluezoo.gumdrop.level=INFO
org.bluezoo.gumdrop.smtp.level=FINEST

The DefaultExporter publishes operational events through the same JUL loggers, named after the emitting class, so the same logging.properties governs them: handlers, formatters and levels all apply, and a per-package level can silence or isolate the events of one package just as it silences its fine-grained output. The default LaconicFormatter prints the level, the rendered message and any stack trace and nothing else.

Shutdown and failure

  • Orderly shutdown. When the runtime shuts down it closes the servers first and then flushes and shuts down the exporter tree, so the events of the shutdown itself, and everything still queued, are delivered. Flushing waits for a bounded time, so an unreachable collector cannot hold the shutdown up indefinitely.
  • Events after shutdown. Once the default exporter has shut down, its thread is gone and a late event is published synchronously on the emitting thread, so nothing is lost at the very end.
  • No handler left. If the JUL logger has no handler by then (the JVM resets LogManager as it exits), the default exporter writes the line to standard error in the laconic form instead of discarding it.
  • Connection errors. Read errors, write errors and unexpected disconnects are recorded with their exception before the connection's trace ends. Protocol connections use try-finally so that spans are ended even when exceptions occur.
  • Forcing a flush. telemetry.getExporter().forceFlush() exports everything pending immediately. During development, a lower flushIntervalMs makes data visible sooner.

Gumdrop no longer registers a JVM shutdown hook for telemetry. Shutting the runtime down is what flushes it, so call gumdrop.shutdown() (and join()) rather than letting the JVM exit.

The OTLP exporters and the JSONL file exporter queue what they are given and send it in batches. They share these settings, made on the exporter before init():

Two exporters in one tree may be set differently, for instance a collector that is sent metrics every ten seconds and a file that is sent them every minute. The DefaultExporter has only levels; the access log and qlog exporters take their destination and queue size as constructor arguments.

Traces are produced only if some exporter in the tree wants them. With the default configuration, which has none, no trace is ever created and the instrumentation costs nothing. Metrics (see Metrics) are collected, at each exporter's metrics interval, by the exporters that carry them: the OTLP and JSONL exporters. The JMX bridge reads them directly and needs no exporter.

Default exporter (java.util.logging)

The DefaultExporter is what every runtime has until you change it, and the reason Gumdrop's console output looks as it always has. Each operational record is published as a java.util.logging record through the logger named after the emitting class, carrying the resource bundle, the key and the attribute values as parameters. The configured handler and formatter (by default ConsoleHandler and LaconicFormatter) then render the localised message. Because it is ordinary JUL, logging.properties, additional handlers such as FileHandler or SocketHandler, and per-package levels all keep working. See Fine-grained logging. 

DefaultExporter console = new DefaultExporter();       // queue of 4096 records
console.levels(LogLevel.WARN, LogLevel.ERROR);      // quieter console
telemetry.exporter(console);

Records are queued and published by a thread of the exporter's own. The exporter takes no endpoint and no other setting.

Tee exporter

A TeeExporter delivers everything to exactly two children, in order, and a failure in the first does not skip the second. It is the only way exporters are combined, and because a tee is itself an exporter, any number of destinations are a nest of tees. The same exporter may appear as a child of more than one tee. 

telemetry.exporter(new TeeExporter(
        new TeeExporter(otlp, console),
        new TeeExporter(accessLog, jsonl)));

OTLP exporters (HTTP and gRPC)

The OTLP exporters send logs, traces and metrics to an OpenTelemetry Collector, or to any backend that speaks OTLP. Two exporters are provided, one per transport:

  • OtlpExporter - OTLP/HTTP, protobuf bodies posted to /v1/traces, /v1/logs and /v1/metrics. The collector's default port is 4318.
  • OtlpGrpcExporter - OTLP/gRPC, gRPC-framed protobuf sent to the collector's TraceService, LogsService and MetricsService. The collector's default port is 4317. Use it when the collector or the network path only accepts gRPC.

Both have the same settings, so changing from one to the other changes the class and the port, nothing else. As well as the batching settings above:

HTTPS should be used in production to protect sensitive telemetry data including trace context, service identifiers, and custom attributes.

TelemetryConfig telemetry = new TelemetryConfig();
telemetry.serviceName("my-service");

otlp.endpoint("https://otel-collector:4318");   // /v1/... is appended

        PemCredentials.loadTrustManager(Path.of("/etc/gumdrop/otel-ca.pem"))));

telemetry.exporter(new TeeExporter(otlp, new DefaultExporter()));
telemetry.init();
OTLP/gRPC
TelemetryConfig telemetry = new TelemetryConfig();
telemetry.serviceName("my-service");

OtlpGrpcExporter otlp = new OtlpGrpcExporter();
otlp.endpoint("https://otel-collector:4317");
otlp.tls(new TlsConfig().trustManager(
        PemCredentials.loadTrustManager(Path.of("/etc/gumdrop/otel-ca.pem"))));
otlp.headers("Authorization=Bearer token123");

telemetry.exporter(new TeeExporter(otlp, new DefaultExporter()));
telemetry.init();

For gRPC the exporter uses the host, port and scheme of each endpoint URL. The path is always the standard OpenTelemetry service method (/opentelemetry.proto.collector.trace.v1.TraceService/Export, .../logs.v1.LogsService/Export and .../metrics.v1.MetricsService/Export), so anything after the port is ignored. An https endpoint is secured with TLS (using the exporter's TlsConfig), and an http endpoint uses a plain connection. With no port in the URL, 4317 is used.

Each signal goes to its own endpoint, taken from the base endpoint of the exporter unless tracesEndpoint, logsEndpoint or metricsEndpoint overrides it. A signal with no endpoint is not exported: with no logs endpoint the exporter takes no log records, and with no traces endpoint it does not ask for traces. To export only metrics to one collector and logs to another, set the two endpoints and nothing else.

Architecture
  • The exporter has a small runtime of its own (a single worker thread) and uses Gumdrop's native HTTP client on it, with TLS and ALPN. Exporting never borrows the selector loops that serve your connections, and an exporter that fails cannot disturb them.
  • Records, traces and metric batches are queued per signal (up to maxQueueSize) and sent in batches of up to batchSize, or every flushIntervalMs, whichever comes first. Metrics are collected every metricsIntervalMs.
  • The exporter starts at init(), not when it is constructed. Until then it takes nothing, so an exporter that is never initialised costs nothing and sends nothing.
  • Large payloads are chunked for efficient transfer. gRPC mode uses the same protobuf encoding with gRPC framing.
  • If a queue is full, further items are dropped (noted at the FINE level), never blocked on.
  • Failed exports are reported through java.util.logging.
TLS Configuration

TLS is configured with a TlsConfig, the same object used for Gumdrop's listeners and clients, set on the exporter with tls. For an HTTPS endpoint the part that matters is the trust the exporter extends to the collector. Give it a trust manager built from the CA certificate that signed the collector's certificate, in PEM form: 

X509TrustManager trust = PemCredentials.loadTrustManager(Path.of("/etc/gumdrop/otel-ca.pem"));
otlp.tls(new TlsConfig().trustManager(trust));

A truststore in PKCS12 or JKS form is loaded with TlsUtils.loadTrustManagers(path, password, KeystoreFormat.PKCS12), which returns the trust managers of the store; pass the X509TrustManager among them to trustManager.

The same TlsConfig carries the exporter's own identity if the collector requires mutual TLS, and verifyPeer(false) turns certificate verification off, which is for tests and never for production. If no TlsConfig is set and the endpoint uses HTTPS, the default JVM truststore is used. This is suitable when the collector uses a certificate signed by a well-known CA.

JSONL file exporter

The OtlpFileExporter writes telemetry data to local files in OpenTelemetry OTLP JSON Lines format. Each line is a complete OTLP JSON object (ExportTraceServiceRequest, ExportLogsServiceRequest, or ExportMetricsServiceRequest) followed by a newline. Operational log events are written exactly as they would be sent to a collector.

The file exporter is useful for:

  • Local development - inspect telemetry output without running a collector
  • Offline analysis - process JSONL files with standard tools (jq, grep, custom scripts)
  • Debugging - capture telemetry data for later review
  • Batch ingestion - feed JSONL files into pipelines or data lakes
  • Testing - verify instrumentation produces correct spans, events and metrics
Architecture
  • Separate .jsonl files for each signal type (traces, logs, metrics) as required by the specification
  • A signal with no path is written to stdout
  • A background thread handles serialization and flushing, avoiding blocking the caller
  • Buffered I/O with configurable buffer size (fileBufferSize, default 8KB)
  • Files are opened in append mode; parent directories are created automatically
  • Graceful shutdown flushes all pending data before closing files
Configuration
TelemetryConfig telemetry = new TelemetryConfig();
telemetry.serviceName("my-service");

OtlpFileExporter files = new OtlpFileExporter(
        Path.of("/var/log/otel/traces.jsonl"),
        Path.of("/var/log/otel/logs.jsonl"),
        Path.of("/var/log/otel/metrics.jsonl"));
files.fileBufferSize(16384);
files.metricsIntervalMs(60000);

telemetry.exporter(files);
telemetry.init();

Besides the batching settings, the file exporter has one of its own: fileBufferSize, the size in bytes of the I/O buffer of each file (default 8192). The files are opened, and the thread that writes them started, by init().

Pass null for any path to send that signal to stdout. The no-argument constructor, new OtlpFileExporter(), writes every signal to stdout, which is the simplest way to see telemetry output during development. Because the file exporter takes the operational levels by default, it is a replacement for the console as well as a companion to it; combine it with a DefaultExporter in a tee if you want both.

Working with JSONL output
# View traces with jq
cat /var/log/otel/traces.jsonl | jq .

# Show the log events of one component
jq -c '.resourceLogs[].scopeLogs[]
  | select(.scope.name | startswith("org.bluezoo.gumdrop.smtp"))
  | .logRecords[] | {event: .eventName, severity: .severityText}' /var/log/otel/logs.jsonl

# Find slow spans (duration > 1s)
cat /var/log/otel/traces.jsonl | jq '
  .resourceSpans[].scopeSpans[].spans[]
  | select(.endTimeUnixNano - .startTimeUnixNano > 1000000000)'

# Count metrics by name
cat /var/log/otel/metrics.jsonl | jq -r '
  .resourceMetrics[].scopeMetrics[].metrics[].name' | sort | uniq -c

# Tail traces in real time
tail -f /var/log/otel/traces.jsonl | jq .

HTTP access log

Every HTTP server that completes a request (HTTP/1.1, HTTP/2 and HTTP/3, including requests served by the servlet container) emits one record of level ACCESS, if any exporter takes that level. The access log is not a separate feature with its own switches: it is the AccessLogExporter placed in the tree. 

AccessLogExporter accessLog = new AccessLogExporter(
        Path.of("/var/log/gumdrop/access.log"),
        AccessLogFormat.CLF,
        AccessLogUserSelection.PROTOCOL_FIRST);
telemetry.exporter(new TeeExporter(new DefaultExporter(), accessLog));

The constructor opens the file, creating it if necessary and appending if it exists, and throws IOException if it cannot. A second constructor takes the size of the queue (default 8192 records). Writing is done by a thread of the exporter's own, so a slow disk never slows a request; records that do not fit the queue are counted and reported at shutdown.

Formats
  • AccessLogFormat.CLF - Common Log Format, one line per request: 
    192.0.2.7 - alice [08/Oct/2026:14:03:21 +0000] "GET /orders/17 HTTP/1.1" 200 5123
  • AccessLogFormat.ELFF - W3C Extended Log File Format, tab separated, with a #Version and #Fields preamble written when the file is created. The fields are date time c-ip cs-method cs-uri-stem sc-status sc-bytes cs-username cs-version.
Which user is logged

A request can carry two identities: the protocol user the HTTP layer authenticated (for instance by TLS client certificate or the Authorization header), and the application user a servlet established later. AccessLogUserSelection says which the line shows:

ValueUser field
PROTOCOLThe protocol user only
APPLICATIONThe application user only
PROTOCOL_FIRSTThe protocol user, else the application user
APPLICATION_FIRSTThe application user, else the protocol user
BOTHELFF only: the protocol user in cs-username and the application user in an extra x-gumdrop-app-user column. CLF behaves as PROTOCOL_FIRST
Access records as structured events

Because the access log is a stream of records and not a file writer, the same requests can go elsewhere too. An access record has the event name http.server.request and these attributes, which follow the OpenTelemetry HTTP semantic conventions:

AttributeContent
client.addressThe client host
http.request.methodThe request method
http.request.targetThe request target, as it appeared in the request
network.protocol.versionFor example HTTP/1.1
http.response.status_codeThe response status
http.response.body.sizeResponse body bytes sent
enduser.idThe protocol user, when authenticated
gumdrop.application.userThe application user, when known

Add LogLevel.ACCESS to the levels of an OTLP or JSONL exporter and each request is exported with those attributes, carrying the trace and span ID of the request when it was traced. The access log is independent of trace sampling: a request that was not sampled is still logged. 

// access log file for operators, access events to the collector for analysis
otlp.levels(LogLevel.INFO, LogLevel.WARN, LogLevel.ERROR, LogLevel.ACCESS);
telemetry.exporter(new TeeExporter(
        new TeeExporter(otlp, new DefaultExporter()),
        accessLog));

qlog exporter

For debugging QUIC and HTTP/3, the QUIC transport emits its connection events as QLOG records. The QlogExporter writes them as qlog files that tools such as qvis can load: one file per connection, named {group id}_{vantage point}.sqlog, in the JSON-SEQ serialisation (each record is a 0x1E byte, a JSON text and a newline). The revision of the drafts followed is QlogExporter.QLOG_REVISION. 

telemetry.exporter(new TeeExporter(
        new DefaultExporter(),
        new QlogExporter(Path.of("/var/log/gumdrop/qlog"),
                QlogExporter.DEFAULT_QUEUE_SIZE)));

The directory is created if needed. The queue is large (65536 events by default) because a trace with holes is of little use; if it still fills, the loss is counted and reported at shutdown. Nothing is emitted, and no event is built, unless a QlogExporter is in the tree.

QLOGDIR. The QUIC interoperability test runner asks an implementation for qlog output by setting the QLOGDIR environment variable. TelemetryConfig.init() honours it: if QLOGDIR names a directory and the exporter tree has nothing that takes QLOG records, a QlogExporter writing there is added to the tree. An explicit QlogExporter you composed yourself takes precedence.

Writing an exporter

Implement TelemetryExporter to send events somewhere else (a syslog daemon, a message queue, a test fixture). The interface has three export methods (a log record, a trace, a list of metrics), the two questions accepts(LogLevel) and acceptsTraces(), init, which TelemetryConfig.init() calls to start the exporter, and flush, forceFlush and shutdown. Give the exporter its own methods for its settings, named for the setting and returning the exporter as the provided ones are, and start its threads and open its files in init so that they can be set after construction. To share the batching settings, extend BatchingExporter. Rules for a well-behaved exporter:

  • export is called on the thread that produced the data, often a selector loop. Put the item on a bounded queue and return; do the slow work on a thread of your own.
  • Answer accepts honestly. A level you do not accept costs the producer a single check; a level you accept and ignore makes it build records for nothing.
  • Do not log through the EventLogger pipeline about your own failures. Use plain java.util.logging; an event emitted from inside export is discarded to prevent a loop.
  • Honour shutdown: it is called once, after a flush, when the runtime shuts down.

Tests can use the same interface: an exporter that keeps records in a list makes event assertions trivial.

Custom Instrumentation

Custom servers and handlers can add their own instrumentation using the telemetry API. Traces and spans are described here; for operational log events from your own code, see Emitting events from your own code. A log event can be tied to a span with span(...), so that the two are correlated in the backend.

Creating Traces

// Get the telemetry config from the connection's endpoint
TelemetryConfig config = endpoint.getTelemetryConfig();

// Create a new trace with root span. The result is null when no exporter
// in the tree takes traces, so tracing costs nothing in that case.
Trace trace = config.createTrace("Process Order", SpanKind.SERVER);

// Or continue from incoming traceparent
String traceparent = request.getHeader("traceparent");
Trace trace = config.createTraceFromTraceparent(traceparent, "Process Order", SpanKind.SERVER);

Working with Spans

// Add attributes to current span
trace.addAttribute("order.id", orderId);
trace.addAttribute("customer.id", customerId);
trace.addAttribute("order.total", 149.99);

// Add events to mark significant points
trace.addEvent("Payment validated");
trace.addEvent("Inventory reserved");

// Start a child span for a sub-operation
Span childSpan = trace.startSpan("Query Database", SpanKind.CLIENT);
try {
    // ... database operation ...
    childSpan.setStatusOk();
} catch (Exception e) {
    childSpan.recordException(e);
} finally {
    childSpan.end();
}

// End the trace (exports automatically)
trace.end();

Span Status

// Set status explicitly
span.setStatusOk();
span.setStatusError("Validation failed");
span.setStatus(SpanStatus.UNSET);

// Record exception (sets ERROR status and adds event)
span.recordException(exception);

Example: Custom Endpoint Handler

public class MyProtocolHandler implements ProtocolHandler {
    
    private Trace endpointTrace;
    
    @Override
    public void connected(Endpoint endpoint) {
        // Create endpoint-level trace
        TelemetryConfig config = endpoint.getTelemetryConfig();
        endpointTrace = config.createTrace("MyProtocol endpoint", SpanKind.SERVER);
        if (endpointTrace != null) {
            endpointTrace.addAttribute("net.peer.ip", endpoint.getRemoteAddress().toString());
        }
    }
    
    protected void processRequest(MyRequest request) {
        // Start a span for this request
        Span requestSpan = null;
        if (endpointTrace != null) {
            requestSpan = endpointTrace.startSpan("Process request");
            requestSpan.addAttribute("request.type", request.getType());
        }
        
        try {
            // Process request...
            if (requestSpan != null) {
                requestSpan.addEvent("Request processed");
                requestSpan.setStatusOk();
            }
        } catch (Exception e) {
            if (requestSpan != null) {
                requestSpan.recordException(e);
            }
            throw e;
        } finally {
            if (requestSpan != null) {
                requestSpan.end();
            }
        }
    }
    
    @Override
    public void disconnected() {
        if (endpointTrace != null) {
            endpointTrace.end();
        }
    }
}

Observable Instruments

Observable instruments use callbacks invoked at collection time, ideal for values maintained externally: 

// Observable gauge for memory usage
meter.gaugeBuilder("process.memory.used")
    .setDescription("Used memory in bytes")
    .setUnit("bytes")
    .buildWithCallback(new ObservableCallback() {
        public void observe(ObservableMeasurement measurement) {
            Runtime rt = Runtime.getRuntime();
            measurement.record(rt.totalMemory() - rt.freeMemory());
        }
    });

// Observable counter for OS statistics
meter.observableCounterBuilder("process.cpu.time")
    .setDescription("CPU time used by process")
    .setUnit("ns")
    .buildWithCallback(new ObservableCallback() {
        public void observe(ObservableMeasurement measurement) {
            measurement.record(getProcessCpuTime());
        }
    });

Aggregation Temporality

Metrics can be exported with different temporalities:

  • DELTA - Values represent change since last export. Preferred for push-based systems and stateless collectors.
  • CUMULATIVE - Values represent total since process start. Preferred for Prometheus-style scrapers.

Temporality and the collection interval are settings of the exporter that sends the metrics, so each destination can have its own: 

otlp.metricsTemporality(AggregationTemporality.DELTA);
otlp.metricsIntervalMs(30000);

Distributed Tracing

Gumdrop supports W3C Trace Context for distributed tracing across services.

Incoming Traces

When a request includes a traceparent header, the server continues that trace rather than starting a new one. The format is: 

traceparent: 00-{trace-id}-{span-id}-{flags}

Example: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

Outgoing Requests

When making outbound requests with the HTTP client, call client.setTrace(state.getTrace()) before connect(). The traceparent header is then added automatically to every request, so the distributed trace remains connected without manual header handling:

In the client examples on this page, gumdrop is the runtime returned by Gumdrop.boot(); a client is given it when it connects. 

HttpClient client = new HttpClient(loop, downstreamHost, downstreamPort);
client.setTrace(state.getTrace());  // Propagates traceparent automatically
client.connect(gumdrop, new HttpClientHandler() {
    public void onConnected(Endpoint endpoint) {
        HttpRequest request = client.post("/api", responseHandler);
        request.header("Content-Type", "application/json");
        request.endMessage();
    }
    // ...
});

If you omit setTrace(), no traceparent header is sent and the downstream service will start a new trace. You can still add the header manually via request.header("traceparent", trace.getTraceparent()) if needed, but automatic propagation is preferred.

This creates a connected chain of spans across services, visible in trace visualization tools.

JMX Bridge

When metrics are enabled, Gumdrop exposes OpenTelemetry metrics via JMX MBeans. This allows JMX-based monitoring tools (jconsole, VisualVM, Prometheus JMX exporter) to access the same metrics without requiring OTLP export. OpenTelemetry remains the single source of truth; the JMX bridge reads from it on each attribute access.

_countTotal number of recorded values
_sumSum of all recorded values
_minMinimum recorded value
_maxMaximum recorded value

Example attributes for HTTP server metrics:

  • http_server_requests - Total requests (counter)
  • http_server_active_requests - Requests in progress (gauge)
  • http_server_active_connections - Active connections (gauge)
  • http_server_request_duration_count, _sum, _min, _max - Request duration histogram

Configuration

The JMX bridge is enabled by default when metrics are enabled. Disable it with: 

TelemetryConfig telemetry = new TelemetryConfig();
telemetry.metricsEnabled(true);
telemetry.jmxBridgeEnabled(false);
telemetry.init();

The bridge registers automatically during TelemetryConfig.init() and unregisters on shutdown. No OTLP or file exporter is required; the JMX bridge works with metrics alone.

Using with Monitoring Tools

jconsole / VisualVM: Connect to the Gumdrop process and navigate to org.bluezoo.gumdrop → Telemetry to view metric values.

Prometheus JMX Exporter: Configure the Prometheus JMX Exporter to scrape the Gumdrop JVM. The exporter will discover the Telemetry MBean and expose its attributes as Prometheus metrics.
